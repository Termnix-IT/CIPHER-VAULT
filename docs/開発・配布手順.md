# 開発・配布手順

リポジトリルートで実行します。アプリの使い方は[README](../README.md)、公開操作は[リリース手順](リリース手順.md)を参照してください。

## 前提条件

- OS: Web/API開発はWindows / macOS / Linux。デスクトップ配布物は対象OS上で生成する
- Node.js: 開発・配布物の作成には `22.12.0` 以上（Electronの取得ツールとViteが要求するため）。生成済みWeb/API配布版の実行には `22` 以上
- npm: 利用可能であること
- 作業ディレクトリ: リポジトリルート

```powershell
cd "C:\path\to\CIPHER-VAULT"
```

依存関係が未導入の場合は最初に実行します。

```powershell
npm install
```

## 起動パターン

### 1. 開発用 Web 版を起動する

```powershell
npm run dev
```

起動後のアクセス先:

- Web: `http://localhost:5173`
- API: `http://localhost:3001`

開発用APIは `--dev` で起動し、Web画面のOriginとして `http://localhost:5173` と `http://127.0.0.1:5173` を許可します。本番の `npm run start` ではこの例外を追加しません。別のポートを使う場合は、API起動前に `PASSWORD_MANAGER_WEB_ORIGIN` へ実際の画面Originを指定します（複数の場合はカンマ区切り）。これはCORSの許可ではなく、Viteプロキシ経由のOrigin検査用です。APIへ直接変更要求を送る場合の必要なヘッダーとトークン取得手順は[設計](設計.md#web版)を参照してください。

Web画面はファイル保存で自動反映されます。APIの変更は `Ctrl+C` で停止して `npm run dev` を再実行します。APIだけを監視起動する場合は、別のターミナルで次のコマンドを使います。

```powershell
# フロントエンド（APIは起動しない）
npm run dev:web
```

```powershell
# API（変更時に自動再起動）
npm --workspace apps/api run dev:watch
```

監視が不要なら `npm run dev:api` でAPIだけをビルド・起動できます。

### 2. 開発用 Electron 版を起動する

ViteとElectronを起動し、preload / IPCを含む画面操作を確認します。

```powershell
npm run dev:desktop
```

### 3. ビルド済み Electron 版を起動する

開発サーバーを使わず、ビルド済みアセットで起動します。

```powershell
npm run build:desktop
npm run start:desktop
```

### 4. ビルド済みWeb/API版を起動・配布する

```powershell
npm run build
npm run start
```

APIがビルド済みWebアセットを配信します。ブラウザで `http://localhost:3001` を開きます。

WindowsでNode.jsを使う配布フォルダを生成する場合は、PowerShellから実行します。

```powershell
npm run package
```

生成された `release/` を丸ごと渡し、受け取り側はNode.js 22以上とnpmが使える環境で `start.bat` または `start.ps1` を実行します。両方とも同梱の `start.mjs` を使います。初回は `npm ci --omit=dev --no-audit --no-fund` で、同梱lockfileのランタイム依存を導入してからAPIを起動します。導入には通信が必要です。[npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) はmanifestとlockfileが一致しなければ失敗し、lockfileを更新しません。

配布物には `package.json`・`package-lock.json` と、APIのCSP生成に必要な共有パッケージの `packages/shared/package.json`・`dist/` も含みます。これらを取り除かないでください。生成時はルートlockfileを種に、npmの `--package-lock-only --ignore-scripts --offline` で配布用の依存だけを残し、各パッケージの版・取得先・integrity・依存情報が元の同じ配置の記録と一致することを検査します。新しい解決が必要になった場合は生成を止め、ソース側で依存更新・監査・検証を行ってください。開発依存やElectron更新用依存はWeb配布へ含めません。

起動処理は導入成功後だけ `node_modules/.cipher-vault-runtime` に照合値を保存します。導入失敗ではAPIを起動せず、次回に再試行します。manifest・lockfile・共有パッケージのmanifest、NodeのモジュールABI・OS・archが変わった場合も再導入します。この記録は手動のファイル削除や改変を検出する保証ではありません。依存が破損した場合は配布フォルダ内の `node_modules` だけを削除して再起動し、`data` は保持してください。

生成物は一時領域で完成・検査してから `release/` へ移します。生成失敗では以前の配布物を置き換えず、既存データの停止条件も置換直前に再確認します。lockfileはnpmパッケージの固定と取得時のintegrity検査に使い、OS別のネイティブ実行可否や、install scriptが別途取得する成果物まで同じハッシュで固定するものではありません。データ保護とネイティブ依存については[日常の保守フロー](#日常の保守フロー)を参照してください。

## デスクトップ版のパッケージ化手順

### 1. 配布物を作成する

Windows 向けの `installer` と `portable` を生成します。

```powershell
npm run package:desktop
```

このコマンドで行われること:

1. `npm run build:desktop`
2. `npm run build:native-transport` で実行OS/arch用のhelperを生成
3. `electron-builder --win nsis portable --publish never`（生成のみ。公開しません）で `dist-desktop/` へ出力

依存更新などの検証では、既存の成果物と区別できる専用フォルダを指定します。

```powershell
npm run package:desktop -- --config.directories.output=dist-desktop/validation
```

この指定も生成だけを行います。バージョンを据え置いて作った検証用の成果物は公開せず、公開時は版を揃えて通常のリリース手順で再生成してください。生成成功に加え、ASARへのDB・ログ混入がないこと、更新情報のsetup名・サイズ・SHA512、preload・ネイティブ依存・フォントとライセンスの同梱、exeへのアイコン埋め込みを確認します。アプリの起動確認は専用の一時保管庫で行い、インストール後の更新適用とは区別します。

### Linux/macOSの評価パッケージ

パッケージ化には既存のelectron-builderを使い、対象OSのx64またはarm64パッケージを生成します。コマンドは異なるOSや未対応archではビルド前に停止します。Windows向けの既存コマンドと保存先は変更しません。

| 対象OS上で実行するコマンド | 出力先と形式 |
|---|---|
| `npm run package:desktop:linux` | `dist-desktop/linux/` のAppImage・tar.gz・展開済みアプリ |
| `npm run package:desktop:mac` | `dist-desktop/macos/` のzip・dmg・`.app` |

すべて `--publish never` を使用します。ファイル名には版・OS・archが入り、Linux x64のAppImageだけはbuilder標準の `x86_64` 表記になります。生成できるarchと検証済みの構成は別です。Linux x64は隔離したWSL Ubuntu 22.04で評価し、macOSとarm64の実行結果は別途確認します。macOSは `identity: "-"` のローカルad-hoc署名を使い、Developer ID署名・notarizationは行いません。一般配布やGatekeeperの受入を完了したものとして公開しないでください。

AppImageはtoolset `1.0.3` を固定し、既定の起動引数に `--no-sandbox` を加えません。FUSEが使えない環境の検証では [AppImage公式の展開方式](https://docs.appimage.org/user-guide/troubleshooting/fuse.html)で `--appimage-extract` 後の `AppRun` を起動します。FUSEマウント、デスクトップ登録、各Linuxディストリビューションのuser namespace / AppArmor条件まで検証する試験ではありません。sandboxを無効にして起動成功に置き換えないでください。

生成後はNode.js 24と画面を起動できる環境で次を実行します。Linuxのheadless環境では `xvfb-run -a` を各コマンドの前に付けます。

```sh
npm run test:packaging-contract
npm run test:desktop-package
# Linux / macOSで、実際のアーカイブも展開して検証
npm run test:desktop-artifacts
```

`test:desktop-package` は既定の展開先を使用します。専用の出力先なら `npm run test:desktop-package -- <展開済みアプリのパス>`、macOSでは `.app` を指定します。`test:desktop-artifacts -- <出力先>` も指定できます。両者は生成済みの同じ版・実行OS・archの成果物を前提とします。

配布物のASARについて、共有ランタイム・preload・ネイティブSQLite・資格保護adapter・ローカルフォントとライセンスの同梱、DB・接続資格ファイル（`.cvkey`）・ログ・開発用テスト・nativeソースの除外を確認します。helperはASAR外の `resources/native-transport/`（macOSは `Contents/Resources/native-transport/`）へ、実行ファイル・manifest・ライセンス2件だけを配置します。検査ではhelperのOS・arch・アプリ版と余分なファイルがないことも照合します。

続いてアプリ全体をソース外の一時ディレクトリへコピーし、起動引数で一時 `user-data-dir` を指定します。Electronのinspectorでもアプリ準備前に一時 `userData` / `sessionData` を設定して本番の起動処理を実行します。これはsafeStorage初期化時のLocal Stateも検証profileへ隔離するためです。コピー先のASAR内モジュールと実際の `process.resourcesPath` を使い、同梱helperの資格発行・OS peer照会・一時登録DBでのTLS相互認証を確認します。実OS providerで保護できた場合は、暗号化した接続資格を保存し、アプリを実際に終了・再起動してから同じ登録との再認証・失効を確認します。資格は実アプリ内で生成し、秘密鍵をinspectorの引数・戻り値へ渡しません。認証試験には独立した合成sessionを使い、製品の保管庫sessionを解除しません。開発フォルダのhelperへfallbackせず、製品コードにテスト用IPCも追加しません。

LinuxでOS保護が利用不能なら、資格ファイルを作らず拒否することを確認します。保護成功を必須にする検証環境では `CIPHER_VAULT_EXPECT_KEY_PROTECTION=1`、利用不能を必須にする環境では `=0` を指定します。実ユーザーのkeyringを試験用に解除・初期化せず、専用DBusと一時keyringを用意してください。macOSのKeychainとLinux Secret Portalは、provider契約の単体試験だけで実OSの受入完了とは扱いません。

配布内の合成client登録も `LocalPairingCoordinator` を通し、公開リクエストのsnapshot・fingerprint確認・明示承認からTLS相互認証へ進みます。これは登録画面の操作試験ではなく、配布された管理サービスと接続層の結合試験です。[初回登録の確認サービス](設計.md#初回登録の確認サービス)の未接続範囲と区別してください。

実際のsandboxとpreloadを通じ、初期設定・エントリ登録・v2移行・監査・暗号化backup・再起動後の解除・終了時の鍵消去とDB閉鎖も確認します。OS idle照会だけは試験中に模擬し、実OS通知・クリップボード・更新の受入は別途行います。macOSのzip / dmgは署名も検査し、dmgを読み取り専用でマウントした後は解除してから一時領域を削除します。

### 2. Windowsの配布物とアイコン

`dist-desktop/` にsetup・portable・更新情報・展開済みの `win-unpacked/` を生成します。添付ファイルは[リリース手順](リリース手順.md#配布物を確認する)、配布形式の違いは[README](../README.md#入手起動)を参照してください。

アイコンの原本・再生成方法は[手動更新とアイコン](手動更新とアイコン.md#アイコン)にまとめています。`package.json` の `build.win.signAndEditExecutable` はtrueを維持します。

### 4. データ保存先

デスクトップ版の DB は `apps/api/data` ではなく、実行ユーザーの `userData` 配下に保存されます。

Windows の例:

```text
C:\Users\<ユーザー名>\AppData\Roaming\CIPHER VAULT\data\password-manager.db
```

この保存先は Electron の `app.getPath("userData")` を基準に決まります。

DB接続はimport時に作らず、起動処理が明示的に開きます。未知形式や読取専用で検査できないDBでは、初期化せず停止します。DBや `-wal` / `-shm` / `-journal` を削除して再試行せず、原本を保持してください。旧形式・接続API・旧列追加・読取専用の条件は[DBの接続と形式判定](設計.md#dbの接続と形式判定)を参照してください。

### 5. 既存版からの更新

setup版のアプリ内更新と旧版への上書き手順は[手動更新とアイコン](手動更新とアイコン.md#利用方法)を参照してください。

## CIと依存監査

WebはVite 8とReact plugin 6を使用し、Rolldown/OxcとLightning CSSでJS・CSSを処理します。実験的なReact Compilerは有効にしていません。`apps/web/vite.config.ts` の `build.target` はVite 5相当の `chrome87` / `edge88` / `firefox78` / `safari14` を明示し、ツール更新で出力目標が変わることを避けています。この指定だけで各旧ブラウザの実機動作を確認したことにはなりません。Electronのfile画面に必要な `base: "./"` とCSPの生成も維持します。

`.github/workflows/ci.yml` はpush・PR・手動実行で起動します。同じリポジトリ・ブランチの重複実行は最新の1件にまとめます。Windows 2025 / Node.js 24でデスクトップを一度ビルドし、境界・API・セッション・更新・接続・MCP・画面の試験を生成済み成果物に対して実行します。単独の `npm run test:*` は必要なビルドを含みます。CIでは同じビルドを繰り返しません。

依存監査は別ジョブで `npm audit --package-lock-only --audit-level=low` を実行します。本番・開発・ビルド依存のlow以上と監査エラーを失敗とし、install scriptは実行しません。全依存の監査が本番依存も含むため、本番依存だけの二重監査は行いません。指摘は依存元・到達条件・修正版を確認し、未検証の除外や強制更新で通さないでください。

CoreジョブはUbuntu 24.04 / macOS 15とNode.js 24を使います。API・Electron・native helperを一度ビルドし、CoreをNodeとElectronのNodeモードで実行します。セッションと接続の試験も残し、Windows専用の配布試験は含めません。

配布アプリの別ジョブはWindows 2025、Ubuntu 22.04、macOS 15で固定依存と `test:packaging-contract`、ネイティブ生成、`test:desktop-package` を実行します。Windowsは展開アプリだけを生成し、Linux/macOSは `test:desktop-artifacts` も実行します。LinuxはXvfbを使い、通常のChromium sandboxを維持して評価するため、CoreジョブとOSを分けています。新しいUbuntuのAppArmor条件は別途受入が必要です。Ubuntu 22.04 runnerは [2027年4月17日の終了予定](https://github.com/actions/runner-images/issues/14254)までに置き換えます。macOSは署名用secretを使わないad-hoc署名です。CI構成、実際のrunner結果、各OS実機での受入を区別し、構成だけでOS対応完了とはしません。

UbuntuのCoreジョブはPython 3・makeとElectronの共有ライブラリ `libnspr4`・`libnss3`・`libasound2t64` とnative helper用のClang・zlib開発ファイルを準備してから依存を導入します。NodeモードでもElectron実行ファイルの共有ライブラリが必要です。Linuxを手元で評価する場合も、Node用のビルドツールと利用するElectronの実行環境を用意してください。macOSでは [node-gypの前提](https://github.com/nodejs/node-gyp#installation)に沿ったPythonとXcode Command Line Toolsが必要です。Electron 45のバイナリは [初回利用時に取得](https://www.electronjs.org/docs/latest/tutorial/installation#binary-download-step)されるため、`npm ci` だけでは実行ファイルの展開が済んでいない場合があります。

ワークフローの権限は `contents: read`、checkout後の認証情報の保持は無効です。外部ActionsはコミットSHAで固定し、npmのダウンロードキャッシュだけを再利用します。パッケージ生成は評価用で、アップロード・リリース、秘密の注入、DB・profile・クリップボードの成果物保存は行いません。インストール済みアプリの更新適用、実OS通知は、これらのジョブでは確認していません。

依存更新は、同じ版のパッケージが複数経路に存在する場合もあるため、`npm explain <package>` とlockfileで親と実行経路を確認してから行います。更新順は次のとおりです。

1. criticalを含む開発・ビルド経路の親パッケージを優先します。`concurrently` の固定された `shell-quote` と、`electron-builder` / `@electron/rebuild` の `tar` を、親の修正版から確認します。各変更でクリーンインストールと該当回帰を実行し、builder変更では公開しない配布物の生成・起動も確認します。
2. Babel・PostCSS・tsx等の変換・解析・取得系も、既存の許容範囲と親パッケージの互換性を確認して更新します。`fixAvailable` だけを理由に強制更新せず、更新後の全体・本番監査を取り直します。
3. Viteのmajor更新は別の変更に分けます。React plugin・Node.js要件を確認し、ビルド済みfile画面、Vite開発画面とHMR、HTTP版、CSP、フォント、バックアップを再検証します。

Viteを呼び出す検証スクリプトはWebワークスペースの `package.json` を基点に解決します。npmによる配置が変わることがあるため、ルートの `node_modules/vite` へhoistされる前提を置かないでください。

本番依存に新しいhigh以上が出た場合は、この順番より優先して到達条件と修正版を確認します。`npm audit fix --force` の一括適用や、criticalが開発依存であることだけを理由にした恒久除外は行いません。

## 日常の保守フロー

「ツール → 接続の管理」はデスクトップ版で保管庫を解除してから使います。初回に有効化し、対応する接続元が作った `.cvpair` を選択します。接続元に表示された完全な照合値との一致を確認して登録し、一覧の「接続情報を保存」から `.cvconnection` を接続元へ渡します。保存先には新しい名前を指定してください。停止は登録を保持し、取り消しは接続を失効させます。Codexの候補検索MVPは次節を参照してください。ブラウザ拡張と認証付きの操作実行は未実装です。

### Codex MCPによる候補検索MVP

Windows、Node.js 24、ソースから起動するアプリを対象とします。配布済みexeにはソース変更が反映されないため、既存の配布アプリを終了してから、新しいコードを起動してください。ビルド済みnative helperが必要で、初回生成には前述の.NET/native toolchainを使います。通常起動した保管庫を本人が解除し、接続登録と検索許可を行います。マスターパスワードをMCPへ渡す操作はありません。

1. リポジトリで `npm ci`、`npm run build:desktop`、必要なら `npm run build:native-transport` を行い、`npm run start:desktop` で新しいコードを起動します。
2. 別のPowerShellをリポジトリで開き、次を実行します。`pair` の明示操作で接続専用profileを作り、native dialogで新しい `.cvpair` を保存します。表示された照合値を確認できるよう、このターミナルを保持してください。

   ```powershell
   $mcpProfile = Join-Path $env:LOCALAPPDATA 'CIPHER-VAULT-MCP\codex'
   node .\apps\mcp\src\index.mjs pair --profile $mcpProfile
   ```

3. アプリを解除して「ツール → 接続の管理」を開き、有効化します。「接続リクエストを選択」で保存したファイルを開き、ターミナルと完全なSHA-256照合値が一致することを確認して登録します。登録一覧の「接続情報を保存」で、新しい `.cvconnection` を保存します。
4. 次を実行し、アプリで保存した接続情報をnative dialogから選びます。`configured` になれば接続情報の取り込みが完了しています。保存された接続先を別hostへ自動で差し替えることはしません。

   ```powershell
   node .\apps\mcp\src\index.mjs import --profile $mcpProfile
   node .\apps\mcp\src\index.mjs status --profile $mcpProfile
   ```

5. Codexへstdio serverを登録します。既に同名の登録がある場合は、その用途を確認してから扱ってください。`config` コマンドは同等のTOMLを表示するだけで、設定ファイルへ書き込みません。

   ```powershell
   $mcpEntry = (Resolve-Path .\apps\mcp\src\index.mjs).Path
   codex mcp add cipher_vault -- node $mcpEntry serve --profile $mcpProfile
   # 手動設定用のTOMLを表示する場合
   node .\apps\mcp\src\index.mjs config --profile $mcpProfile
   ```

6. CodexでMCP設定を再読み込みし、必要ならアプリを再起動して新しいチャットを開きます。`search_candidates` にサービス名を渡すとアプリの確認ダイアログが開き、本人が今回だけ許可した場合に最大20件を返します。起動設定の共有と現在のチャットへのtool反映は別です。[Codexの公式MCP設定](https://learn.chatgpt.com/docs/extend/mcp)も参照してください。

返すURLはoriginだけで、ログインID・パスワード・メモを返しません。保管庫のロック、接続の停止・取消、確認の拒否や期限切れでは検索できません。`status` は公開の登録状態の確認であり、保管庫の解除状態や検索許可を保証しません。資格はOS保護されていても、同一OSアカウントの侵害まで隔離できるとは扱いません。

`npm run test:mcp` はビルドと候補検索/SDKの対象試験、実Electronと一時保管庫を使うstdio統合試験です。既存のnative helperを使います。`node scripts/run-mcp-tests.mjs --codex` は、認証済みのCodex CLIを一時設定・一時作業directoryで起動し、合成候補の検索を1回実行します。通常のCodex設定や認証ファイルを書き換えませんが、モデル利用量を消費します。本人の保管庫や接続profileは試験に使用しません。今回のMVPでは配布物の再検証と他OSの追加試験を省略しています。

接続設定は `app.getPath("userData")/local-connections` へ保存し、Vault本体のDBや暗号化backupに混ぜません。保護不能、資格の消失・期限切れ、形式異常では接続機能だけを停止し、資格を勝手に再生成しません。まずアプリを終了し、OS鍵保護と保存先が利用できる状態で再起動してください。既存ファイルを復元できない場合は、アプリ停止中に `local-connections` 全体を別名で保管してから、有効化と全接続元の新規pairingをやり直します。旧host pinは新しい接続先に使えません。保管した原本やVault本体を削除する必要はありません。

`npm run build:native-transport` は対象OS上でhelperをNative AOTとして生成します。SDKは `native/local-transport/global.json` の.NET 10.0.303を使用します。WindowsはVisual Studio 2022以降のC++ build tools、LinuxはClang・libc開発ファイル・zlib開発ファイル、macOSはXcode Command Line Toolsが必要です。[Native AOTの前提](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)を参照してください。生成先は `dist-desktop/native-transport/<platform>-<arch>/` で、中間出力・NuGet cache・CLI設定も `dist-desktop/` 内へ分離します。同じbinaryを `cipher-vault-native-host`（Windowsは `.exe`）としても出力し、呼び出されたファイル名でNative Messaging専用launcherへ分岐します。両方の実行ファイルを配布対象に含めます。RuntimeのMIT licenseとthird-party notices、版・OS・arch・署名前のtransportの `buildSha256` を記した `native-transport.json` を同時に生成します。署名が実行ファイルを変更するため、このdigestを配布後のファイル認証には使いません。macOSでは両helperをapp bundleの署名対象に含めます。SDK/native runtimeの更新はnpm監査の対象外なので、SDKの版と生成manifestを別途確認します。

OSイベント・コピー期限・入力契約・KDF・解除試行制御・セッションを変更した場合は `npm run test:sessions` も実行します。共通入力契約のUTF-8境界・未知項目・引数個数と、旧実装の固定出力とのKDF互換性、同時実行・試行待機を確認し、時計とタイマーを注入して期限境界・時計変更・旧世代の応答も検証します。`npm run test:desktop-session` はElectronを実起動し、独立した一時 `userData` で初期設定・登録・ロック・再解除・KDF中のIPC取消と試行待機・HTTPと共通の不正入力・旧長文の取得・OS通知によるロック・実時間30秒のコピー期限・renderer喪失・通常終了時の消去を自動確認します。クリップボードAPIは試験中ずっと差し替え、OSの実クリップボードを読み書きしません。OS通知と画面ロック状態の照会結果もElectron内で模擬し、実際の画面ロック・スリープは行いません。各OSの実通知と実クリップボードの形式・アクセス可否は、実機受入確認として区別してください。5分経過はテストプロセス内の壁時計で模擬し、実際の5分放置試験とは区別します。実時間の5分放置を確認する場合は、PowerShellで `$env:CIPHER_VAULT_QA_REAL_IDLE = "1"` を設定して同じコマンドを実行し、終了後に `Remove-Item Env:CIPHER_VAULT_QA_REAL_IDLE` で戻します。既存の `userData` や開発用DBは使いません。

Electronビルドでは型検査後に `prepare-preload.mjs` が単一の `preload.cjs` を生成し、旧生成物の `preload.js` / `preload.mjs` を削除します。sandboxを解除して読み込みエラーを回避せず、生成物と限定APIを上記テストで確認してください。画面のCSPと開発時例外は[設計](設計.md#画面のsandboxとcsp)を参照してください。

フォントと原ライセンス・取得元記録は `apps/web/public/fonts/` に置き、ViteのpublicアセットとしてWeb・Electron両配布へコピーします。配布時にライセンスファイルを除外しないでください。

デスクトップ配布のNode.jsはElectronに含まれ、単独では差し替えません。Electronを更新して `npm run package:desktop` で配布物を再生成します。Web/API配布版はNode.jsを同梱せず、利用者の環境のランタイムを使います。

デスクトップ配布ではbetter-sqlite3のOS/arch別Node-APIバイナリをASAR外へ展開します。`build.npmRebuild: false` で不要なElectron ABI向けの再ビルドを避け、生成後のアプリでSQLiteの読み書きを確認します。共通パッケージはルートの本番依存にも宣言し、開発用workspaceへの参照だけに依存しません。ABIに依存するネイティブ依存を追加する場合は、この設定を見直してください。

Web/API向けの `npm run package` は空の `release/data` を生成します。開発用DBはコピーしません。既存の `release/data` にデータがある場合は停止するため、既存のreleaseフォルダ全体を安全な場所へ移してから実行します。

検証値を移行するv0.2.1の変更では、移行後の旧版利用に制約があります。[v0.2.1の修正](リリースノート/v0.2.1.md)を先に確認してください。

### 変更に応じた検証

変更した範囲の試験を選びます。サービス・画面の `npm run test:*` は必要なビルドを含み、配布物の試験は生成済み成果物を使います。生成物が変わっていなければ、成功済みのビルドや試験を繰り返す必要はありません。

| 変更範囲 | コマンド |
|---|---|
| サービス・HTTP・保存・暗号・移行・復旧 | Windowsは `npm run test:api`、他OSは `npm run test:core` |
| WindowsのWeb配布だけ | `npm run test:windows-release`（`test:api` にも含む） |
| 入力・KDF・セッション・OS連動・コピー期限 | `npm run test:sessions` |
| sandbox・preload・IPC・CSP | `npm run test:security` |
| 更新 | `npm run test:updates` と[実更新の確認](手動更新とアイコン.md#検証) |
| 通常画面・開発画面・HTTP画面 | 対象に合わせて `test:desktop-session` / `test:desktop-dev` / `test:web-policy` |
| v2の画面・種類別入力・中断復旧 | 対象に合わせて `test:desktop-v2` / `test:desktop-item-types` / `test:desktop-maintenance` |
| OS capability・接続層 | 対象に合わせて `test:desktop-platform` / `test:local-endpoint` / `test:native-transport` |
| 接続管理・ブラウザ専用入口・MCP | 対象に合わせて `test:desktop-connections` / `test:browser-host` / `test:mcp` |
| 配布構成・native依存 | `package:desktop` 後に `test:desktop-package`。Linux/macOSは `test:desktop-artifacts` も実行 |

表中の `test:*` / `package:*` は `npm run` で実行します。画面変更はビルドだけで完了とせず、影響する操作と表示を確認します。単体・画面・配布物では検出できる不具合が異なるため、異なる層の試験を重複扱いで削除しません。

試験は一時DB・profileを使い、利用中の保管庫を初期化・上書きしません。Coreは同じ一覧をNodeとElectronのNodeモードで実行し、失敗・起動エラー・signal終了で後続を止めます。Windows専用モードを他OSで呼ぶと失敗します。better-sqlite3 13以降はNode-APIを使い、ランタイムごとのABI切替は不要です。

暗号互換は独立した固定ベクトルも維持します。期待値を実装から再生成して通さず、形式変更時は別実装との一致を確認してください。容量・nonce上限の試験には数百MiBの一時領域、Windowsのクリーン配布試験には依存取得の通信が必要です。

接続試験には生成済みhelperと、対象により実OS鍵保護が必要です。Linuxの肯定検証は専用DBus・一時keyringを使い、固定鍵fallbackを成功扱いにしません。OS権限・鍵保護を模擬した試験と実providerの受入を区別します。`test:browser-host` は画面を利用できる環境、`test:local-endpoint` はWindowsでPowerShell 7、他OSでPython 3、`test:native-transport` の攻撃fixture生成はOpenSSLを使います。これらは配布アプリの追加要件ではありません。

`node scripts/test-packaged-browser-host.mjs <展開した評価パッケージ>` は、配布launcherの未登録起動だけを確認します。ブラウザ登録・資格の復元を確認する試験ではありません。実OS通知・実電源断・macOS実機・更新インストールの受入は、自動試験と分けて記録します。sandboxによるrename・junctionの拒否は実装の失敗と区別し、必要なら同じ一時データの試験を許可された環境で再実行します。

## トラブルシューティング

### `npm run start:desktop` で起動しない

以下を順に確認します。

1. 先に `npm run build:desktop` を実行しているか
2. `apps/electron/dist/apps/electron/src/main.js` が存在するか
3. 以前の `Electron` プロセスが残っていないか

### `npm run package:desktop` で失敗する

以下を確認します。

1. `npm install` をやり直す
2. `better-sqlite3` の再ビルドが通る環境か確認する
3. `build/icon.ico` が存在するか確認する
4. `npm run build:desktop` 単体が成功するか確認する

### アイコンが古いまま見える

まず `build/icon.ico` の再生成と `signAndEditExecutable: true` を確認し、配布物を作り直します。false では Electron の標準アイコンが残ります。
正しいアイコンが exe に埋め込まれていても表示が古い場合は、Windows のアイコンキャッシュの影響を切り分けます。ビルド時の winCodeSign 展開エラーについては [手動更新とアイコン](手動更新とアイコン.md) を参照してください。

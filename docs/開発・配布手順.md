# 開発・配布手順

リポジトリルートで実行します。アプリの使い方は[README](../README.md)、公開操作は[リリース手順](リリース手順.md)を参照してください。

## 前提条件

- OS: Windows（開発・配布ともWindowsだけを対象とする）
- Node.js: 開発・配布物の作成には `22.12.0` 以上（Electronの取得ツールとViteが要求するため）。生成済みWeb/API配布版の実行には `22` 以上
- npm: 利用可能であること
- 作業ディレクトリ: リポジトリルート

```powershell
cd "C:\path\to\CIPHER-VAULT"
```

依存関係が未導入の場合は最初に実行します。

```powershell
npm install
```

## 起動パターン

### 1. 開発用 Web 版を起動する

```powershell
npm run dev
```

起動後のアクセス先:

- Web: `http://localhost:5173`
- API: `http://localhost:3001`

開発用APIは `--dev` で起動し、Web画面のOriginとして `http://localhost:5173` と `http://127.0.0.1:5173` を許可します。本番の `npm run start` ではこの例外を追加しません。別のポートを使う場合は、API起動前に `PASSWORD_MANAGER_WEB_ORIGIN` へ実際の画面Originを指定します（複数の場合はカンマ区切り）。これはCORSの許可ではなく、Viteプロキシ経由のOrigin検査用です。APIへ直接変更要求を送る場合の必要なヘッダーとトークン取得手順は[設計](設計.md#web版)を参照してください。

Web画面はファイル保存で自動反映されます。APIの変更は `Ctrl+C` で停止して `npm run dev` を再実行します。APIだけを監視起動する場合は、別のターミナルで次のコマンドを使います。

```powershell
# フロントエンド（APIは起動しない）
npm run dev:web
```

```powershell
# API（変更時に自動再起動）
npm --workspace apps/api run dev:watch
```

監視が不要なら `npm run dev:api` でAPIだけをビルド・起動できます。

### 2. 開発用 Electron 版を起動する

ViteとElectronを起動し、preload / IPCを含む画面操作を確認します。

```powershell
npm run dev:desktop
```

### 3. ビルド済み Electron 版を起動する

開発サーバーを使わず、ビルド済みアセットで起動します。

```powershell
npm run build:desktop
npm run start:desktop
```

### 4. ビルド済みWeb/API版を起動・配布する

```powershell
npm run build
npm run start
```

APIがビルド済みWebアセットを配信します。ブラウザで `http://localhost:3001` を開きます。

WindowsでNode.jsを使う配布フォルダを生成する場合は、PowerShellから実行します。

```powershell
npm run package
```

生成された `release/` を丸ごと渡し、受け取り側はNode.js 22以上とnpmが使える環境で `start.bat` または `start.ps1` を実行します。両方とも同梱の `start.mjs` を使います。初回は `npm ci --omit=dev --no-audit --no-fund` で、同梱lockfileのランタイム依存を導入してからAPIを起動します。導入には通信が必要です。[npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) はmanifestとlockfileが一致しなければ失敗し、lockfileを更新しません。

配布物には `package.json`・`package-lock.json` と、APIのCSP生成に必要な共有パッケージの `packages/shared/package.json`・`dist/` も含みます。これらを取り除かないでください。生成時はルートlockfileを種に、npmの `--package-lock-only --ignore-scripts --offline` で配布用の依存だけを残し、各パッケージの版・取得先・integrity・依存情報が元の同じ配置の記録と一致することを検査します。新しい解決が必要になった場合は生成を止め、ソース側で依存更新・監査・検証を行ってください。開発依存やElectron更新用依存はWeb配布へ含めません。

起動処理は導入成功後だけ `node_modules/.cipher-vault-runtime` に照合値を保存します。導入失敗ではAPIを起動せず、次回に再試行します。manifest・lockfile・共有パッケージのmanifest、NodeのモジュールABI・OS・archが変わった場合も再導入します。この記録は手動のファイル削除や改変を検出する保証ではありません。依存が破損した場合は配布フォルダ内の `node_modules` だけを削除して再起動し、`data` は保持してください。

生成物は一時領域で完成・検査してから `release/` へ移します。生成失敗では以前の配布物を置き換えず、既存データの停止条件も置換直前に再確認します。lockfileはnpmパッケージの固定と取得時のintegrity検査に使い、OS別のネイティブ実行可否や、install scriptが別途取得する成果物まで同じハッシュで固定するものではありません。データ保護とネイティブ依存については[日常の保守フロー](#日常の保守フロー)を参照してください。

## デスクトップ版のパッケージ化手順

### 1. 配布物を作成する

Windows 向けの `installer` と `portable` を生成します。

```powershell
npm run package:desktop
```

このコマンドで行われること:

1. `npm run build:desktop`
2. `electron-builder --win nsis portable --publish never`（生成のみ。公開しません）で `dist-desktop/` へ出力

依存更新などの検証では、既存の成果物と区別できる専用フォルダを指定します。

```powershell
npm run package:desktop -- --config.directories.output=dist-desktop/validation
```

この指定も生成だけを行います。バージョンを据え置いて作った検証用の成果物は公開せず、公開時は版を揃えて通常のリリース手順で再生成してください。生成成功に加え、ASARへのDB・ログ混入がないこと、更新情報のsetup名・サイズ・SHA512、preload・ネイティブ依存・フォントとライセンスの同梱、exeへのアイコン埋め込みを確認します。アプリの起動確認は専用の一時保管庫で行い、インストール後の更新適用とは区別します。

生成後は、画面を起動できるWindows環境で次を実行します。

```powershell
npm run test:packaging-contract
npm run test:desktop-package
```

`test:desktop-package` は既定の展開先 `dist-desktop/win-unpacked` を使用します。専用の出力先なら `npm run test:desktop-package -- <展開済みアプリのパス>` を指定します。

配布物のASARについて、共有ランタイム・preload・ネイティブSQLite・ローカルフォントとライセンスの同梱と、DB・ログ・開発用テストの除外を確認します。v0.5.0で外部アプリの接続を削除したため、旧版で同梱していた接続用helper（`resources/native-transport/`）が残っていないことも確認します。

続いてアプリ全体をソース外の一時ディレクトリへコピーし、起動引数で一時 `user-data-dir` を指定します。Electronのinspectorでもアプリ準備前に一時 `userData` / `sessionData` を設定して本番の起動処理を実行します。コピー先のASAR内モジュールを使い、製品コードにテスト用IPCは追加しません。

実際のsandboxとpreloadを通じ、初期設定・エントリ登録・v2移行・監査・暗号化backup・再起動後の解除・終了時の鍵消去とDB閉鎖も確認します。OS idle照会だけは試験中に模擬し、実OS通知・クリップボード・更新の受入は別途行います。

### 2. Windowsの配布物とアイコン

`dist-desktop/` にsetup・portable・更新情報・展開済みの `win-unpacked/` を生成します。添付ファイルは[リリース手順](リリース手順.md#配布物を確認する)、配布形式の違いは[README](../README.md#入手起動)を参照してください。

アイコンの原本・再生成方法は[手動更新とアイコン](手動更新とアイコン.md#アイコン)にまとめています。`package.json` の `build.win.signAndEditExecutable` はtrueを維持します。

### 4. データ保存先

デスクトップ版の DB は `apps/api/data` ではなく、実行ユーザーの `userData` 配下に保存されます。

Windows の例:

```text
C:\Users\<ユーザー名>\AppData\Roaming\CIPHER VAULT\data\password-manager.db
```

この保存先は Electron の `app.getPath("userData")` を基準に決まります。

DB接続はimport時に作らず、起動処理が明示的に開きます。未知形式や読取専用で検査できないDBでは、初期化せず停止します。DBや `-wal` / `-shm` / `-journal` を削除して再試行せず、原本を保持してください。旧形式・接続API・旧列追加・読取専用の条件は[DBの接続と形式判定](設計.md#dbの接続と形式判定)を参照してください。

### 5. 既存版からの更新

setup版のアプリ内更新と旧版への上書き手順は[手動更新とアイコン](手動更新とアイコン.md#利用方法)を参照してください。

## CIと依存監査

WebはVite 8とReact plugin 6を使用し、Rolldown/OxcとLightning CSSでJS・CSSを処理します。実験的なReact Compilerは有効にしていません。`apps/web/vite.config.ts` の `build.target` はVite 5相当の `chrome87` / `edge88` / `firefox78` / `safari14` を明示し、ツール更新で出力目標が変わることを避けています。この指定だけで各旧ブラウザの実機動作を確認したことにはなりません。Electronのfile画面に必要な `base: "./"` とCSPの生成も維持します。

`.github/workflows/ci.yml` はpush・PR・手動実行で起動します。同じリポジトリ・ブランチの重複実行は最新の1件にまとめます。Windows 2025 / Node.js 24でデスクトップを一度ビルドし、境界・API・セッション・更新・画面の試験を生成済み成果物に対して実行します。単独の `npm run test:*` は必要なビルドを含みます。CIでは同じビルドを繰り返しません。

依存監査は別ジョブで `node scripts/audit-dependencies.mjs` を実行します。このスクリプトは `npm audit --package-lock-only --json` の結果を読み、本番・開発・ビルド依存のlow以上と監査エラーを失敗とします。install scriptは実行しません。全依存の監査が本番依存も含むため、本番依存だけの二重監査は行いません。指摘は依存元・到達条件・修正版を確認し、未検証の除外や強制更新で通さないでください。

修正版がなく、到達経路を確認できた指摘だけを、スクリプト冒頭の `accepted` に期限付きで登録できます。登録には脆弱性ID・パッケージ名・許可する親パッケージ・期限・理由を書きます。期限切れ、指摘が出なくなった場合、許可した親以外から到達する場合はCIが失敗するので、そのときは登録を見直すか削除します。

現在の登録は `GHSA-g3hv-75wg-m249`（minimatch 11.0.1未満、期限2026-12-31）の1件です。minimatch は `electron-builder` 経由で配布物の生成時だけに使われ、globパターンはこのリポジトリの設定から渡されます。修正は11系だけにあり、`@electron/asar`・`glob@7`・`dir-compare` が使う3系はAPIが異なるため、`overrides` で11系へ置き換えると配布物の生成が壊れます。`npm audit fix --force` は `electron-builder` を20系へ戻すため使いません。`electron-builder`（`app-builder-lib`・`@electron/asar`）と `dir-compare` が11系へ移った版を出したら、更新して登録を削除します。

配布アプリの別ジョブはWindows 2025で固定依存と `test:packaging-contract`、展開アプリの生成、`test:desktop-package` を実行します。

Electron 45のバイナリは [初回利用時に取得](https://www.electronjs.org/docs/latest/tutorial/installation#binary-download-step)されるため、`npm ci` だけでは実行ファイルの展開が済んでいない場合があります。

ワークフローの権限は `contents: read`、checkout後の認証情報の保持は無効です。外部ActionsはコミットSHAで固定し、npmのダウンロードキャッシュだけを再利用します。パッケージ生成は評価用で、アップロード・リリース、秘密の注入、DB・profile・クリップボードの成果物保存は行いません。インストール済みアプリの更新適用、実OS通知は、これらのジョブでは確認していません。

依存更新は、同じ版のパッケージが複数経路に存在する場合もあるため、`npm explain <package>` とlockfileで親と実行経路を確認してから行います。更新順は次のとおりです。

1. criticalを含む開発・ビルド経路の親パッケージを優先します。`concurrently` の固定された `shell-quote` と、`electron-builder` / `@electron/rebuild` の `tar` を、親の修正版から確認します。各変更でクリーンインストールと該当回帰を実行し、builder変更では公開しない配布物の生成・起動も確認します。
2. Babel・PostCSS・tsx等の変換・解析・取得系も、既存の許容範囲と親パッケージの互換性を確認して更新します。`fixAvailable` だけを理由に強制更新せず、更新後の全体・本番監査を取り直します。
3. Viteのmajor更新は別の変更に分けます。React plugin・Node.js要件を確認し、ビルド済みfile画面、Vite開発画面とHMR、HTTP版、CSP、フォント、バックアップを再検証します。

Viteを呼び出す検証スクリプトはWebワークスペースの `package.json` を基点に解決します。npmによる配置が変わることがあるため、ルートの `node_modules/vite` へhoistされる前提を置かないでください。

本番依存に新しいhigh以上が出た場合は、この順番より優先して到達条件と修正版を確認します。`npm audit fix --force` の一括適用や、criticalが開発依存であることだけを理由にした恒久除外は行いません。

## 日常の保守フロー

OSイベント・コピー期限・入力契約・KDF・解除試行制御・セッションを変更した場合は `npm run test:sessions` も実行します。共通入力契約のUTF-8境界・未知項目・引数個数と、旧実装の固定出力とのKDF互換性、同時実行・試行待機を確認し、時計とタイマーを注入して期限境界・時計変更・旧世代の応答も検証します。`npm run test:desktop-session` はElectronを実起動し、独立した一時 `userData` で初期設定・登録・ロック・再解除・KDF中のIPC取消と試行待機・HTTPと共通の不正入力・旧長文の取得・OS通知によるロック・実時間30秒のコピー期限・renderer喪失・通常終了時の消去を自動確認します。クリップボードAPIは試験中ずっと差し替え、OSの実クリップボードを読み書きしません。OS通知と画面ロック状態の照会結果もElectron内で模擬し、実際の画面ロック・スリープは行いません。各OSの実通知と実クリップボードの形式・アクセス可否は、実機受入確認として区別してください。5分経過はテストプロセス内の壁時計で模擬し、実際の5分放置試験とは区別します。実時間の5分放置を確認する場合は、PowerShellで `$env:CIPHER_VAULT_QA_REAL_IDLE = "1"` を設定して同じコマンドを実行し、終了後に `Remove-Item Env:CIPHER_VAULT_QA_REAL_IDLE` で戻します。既存の `userData` や開発用DBは使いません。

Electronビルドでは型検査後に `prepare-preload.mjs` が単一の `preload.cjs` を生成し、旧生成物の `preload.js` / `preload.mjs` を削除します。sandboxを解除して読み込みエラーを回避せず、生成物と限定APIを上記テストで確認してください。画面のCSPと開発時例外は[設計](設計.md#画面のsandboxとcsp)を参照してください。

フォントと原ライセンス・取得元記録は `apps/web/public/fonts/` に置き、ViteのpublicアセットとしてWeb・Electron両配布へコピーします。配布時にライセンスファイルを除外しないでください。

デスクトップ配布のNode.jsはElectronに含まれ、単独では差し替えません。Electronを更新して `npm run package:desktop` で配布物を再生成します。Web/API配布版はNode.jsを同梱せず、利用者の環境のランタイムを使います。

デスクトップ配布ではbetter-sqlite3のOS/arch別Node-APIバイナリをASAR外へ展開します。`build.npmRebuild: false` で不要なElectron ABI向けの再ビルドを避け、生成後のアプリでSQLiteの読み書きを確認します。共通パッケージはルートの本番依存にも宣言し、開発用workspaceへの参照だけに依存しません。ABIに依存するネイティブ依存を追加する場合は、この設定を見直してください。

Web/API向けの `npm run package` は空の `release/data` を生成します。開発用DBはコピーしません。既存の `release/data` にデータがある場合は停止するため、既存のreleaseフォルダ全体を安全な場所へ移してから実行します。

検証値を移行するv0.2.1の変更では、移行後の旧版利用に制約があります。[v0.2.1の修正](リリースノート/v0.2.1.md)を先に確認してください。

### 変更に応じた検証

変更した範囲の試験を選びます。サービス・画面の `npm run test:*` は必要なビルドを含み、配布物の試験は生成済み成果物を使います。生成物が変わっていなければ、成功済みのビルドや試験を繰り返す必要はありません。

| 変更範囲 | コマンド |
|---|---|
| サービス・HTTP・保存・暗号・移行・復旧 | `npm run test:api` |
| WindowsのWeb配布だけ | `npm run test:windows-release`（`test:api` にも含む） |
| 入力・KDF・セッション・OS連動・コピー期限 | `npm run test:sessions` |
| sandbox・preload・IPC・CSP | `npm run test:security` |
| 更新 | `npm run test:updates` と[実更新の確認](手動更新とアイコン.md#検証) |
| 通常画面・開発画面・HTTP画面 | 対象に合わせて `test:desktop-session` / `test:desktop-dev` / `test:web-policy` |
| v2の画面・種類別入力・中断復旧 | 対象に合わせて `test:desktop-v2` / `test:desktop-item-types` / `test:desktop-maintenance` |
| 配布構成・native依存 | `package:desktop` 後に `test:desktop-package` |

表中の `test:*` / `package:*` は `npm run` で実行します。画面変更はビルドだけで完了とせず、影響する操作と表示を確認します。単体・画面・配布物では検出できる不具合が異なるため、異なる層の試験を重複扱いで削除しません。

試験は一時DB・profileを使い、利用中の保管庫を初期化・上書きしません。Coreは同じ一覧をNodeとElectronのNodeモードで実行し、失敗・起動エラー・signal終了で後続を止めます。Windows専用モードを他OSで呼ぶと失敗します。better-sqlite3 13以降はNode-APIを使い、ランタイムごとのABI切替は不要です。

暗号互換は独立した固定ベクトルも維持します。期待値を実装から再生成して通さず、形式変更時は別実装との一致を確認してください。容量・nonce上限の試験には数百MiBの一時領域、Windowsのクリーン配布試験には依存取得の通信が必要です。

`experiments/rust-crypto-compat/` は、Rust移行の可否を判断するための検証専用crateです。アプリからは使用せず、配布物にも含みません。同じ固定ベクトルをRustで検証するには `cargo test --manifest-path experiments/rust-crypto-compat/Cargo.toml` を実行します。アプリのTypeScript codecが書いた合成データも読む場合は、`npm run build:api` の後に次を実行します。Rust製の本体を実装するときは、暗号ライブラリを本番用として選び直してください。

```powershell
node experiments/rust-crypto-compat/generate-node-vectors.mjs "$env:TEMP\cipher-vault-node-vectors.json"
$env:CIPHER_VAULT_NODE_VECTORS = "$env:TEMP\cipher-vault-node-vectors.json"
cargo test --manifest-path experiments/rust-crypto-compat/Cargo.toml --test node_interop -- --ignored
```

実OS通知・実電源断・更新インストールの受入は、自動試験と分けて記録します。sandboxによるrename・junctionの拒否は実装の失敗と区別し、必要なら同じ一時データの試験を許可された環境で再実行します。

## トラブルシューティング

### `npm run start:desktop` で起動しない

以下を順に確認します。

1. 先に `npm run build:desktop` を実行しているか
2. `apps/electron/dist/apps/electron/src/main.js` が存在するか
3. 以前の `Electron` プロセスが残っていないか

### `npm run package:desktop` で失敗する

以下を確認します。

1. `npm install` をやり直す
2. `better-sqlite3` の再ビルドが通る環境か確認する
3. `build/icon.ico` が存在するか確認する
4. `npm run build:desktop` 単体が成功するか確認する

### アイコンが古いまま見える

まず `build/icon.ico` の再生成と `signAndEditExecutable: true` を確認し、配布物を作り直します。false では Electron の標準アイコンが残ります。
正しいアイコンが exe に埋め込まれていても表示が古い場合は、Windows のアイコンキャッシュの影響を切り分けます。ビルド時の winCodeSign 展開エラーについては [手動更新とアイコン](手動更新とアイコン.md) を参照してください。

# 開発・配布手順

## 目的

この手順書は、`CIPHER VAULT` のWeb/API版とElectronデスクトップ版の開発・配布方法をまとめたものです。配布版の利用方法と画面例は[README](../README.md)を参照してください。

- 開発環境で起動する
- ビルド済みデスクトップ版を起動する
- Web/API版をビルド・配布する
- Windows 向け配布パッケージを作成する

---

## 前提条件

- OS: Web/API開発はWindows / macOS / Linux、Windows配布物の生成はWindows
- Node.js: 開発・配布物の作成には `22.12.0` 以上（Electronの取得ツールとViteが要求するため）。生成済みWeb/API配布版の実行には `22` 以上
- npm: 利用可能であること
- 作業ディレクトリ: リポジトリルート

```powershell
cd "C:\path\to\CIPHER-VAULT"
```

依存関係が未導入の場合は最初に実行します。

```powershell
npm install
```

## 起動パターン

### 1. 開発用 Web 版を起動する

フロントエンドと API を個別に動かして、ブラウザで確認する方法です。

```powershell
npm run dev
```

起動後のアクセス先:

- Web: `http://localhost:5173`
- API: `http://localhost:3001`

開発用APIは `--dev` で起動し、Web画面のOriginとして `http://localhost:5173` と `http://127.0.0.1:5173` を許可します。本番の `npm run start` ではこの例外を追加しません。別のポートを使う場合は、API起動前に `PASSWORD_MANAGER_WEB_ORIGIN` へ実際の画面Originを指定します（複数の場合はカンマ区切り）。これはCORSの許可ではなく、Viteプロキシ経由のOrigin検査用です。APIへ直接変更要求を送る場合の必要なヘッダーとトークン取得手順は[設計](設計.md#web版)を参照してください。

用途:

- UI の見た目確認
- Web 側の動作確認
- API 単体の挙動確認

Web画面はファイル保存で自動反映されます。APIの変更は `Ctrl+C` で停止して `npm run dev` を再実行します。APIだけを監視起動する場合は、別のターミナルで次のコマンドを使います。

```powershell
# フロントエンド（APIは起動しない）
npm run dev:web
```

```powershell
# API（変更時に自動再起動）
npm --workspace apps/api run dev:watch
```

監視が不要なら `npm run dev:api` でAPIだけをビルド・起動できます。

### 2. 開発用 Electron 版を起動する

`Electron` ウィンドウでアプリを起動し、デスクトップ版として確認する方法です。

```powershell
npm run dev:desktop
```

このコマンドで行われること:

- `apps/api` をビルド
- `Vite` の開発サーバーを起動
- `Electron` を起動

用途:

- デスクトップアプリとしての見え方確認
- `preload + IPC` を含む実動作確認
- 変更しながらの反復開発

### 3. ビルド済み Electron 版を起動する

本番に近い構成で、ビルド済みアセットを使って起動する方法です。

まずビルドします。

```powershell
npm run build:desktop
```

次に起動します。

```powershell
npm run start:desktop
```

この方法では:

- `apps/web/dist`
- `apps/api/dist`
- `apps/electron/dist`

を使ってアプリが起動します。

用途:

- 配布前の最終動作確認
- 開発サーバーに依存しない起動確認

### 4. ビルド済みWeb/API版を起動・配布する

```powershell
npm run build
npm run start
```

APIがビルド済みWebアセットを配信します。ブラウザで `http://localhost:3001` を開きます。

WindowsでNode.jsを使う配布フォルダを生成する場合は、PowerShellから実行します。

```powershell
npm run package
```

生成された `release/` を丸ごと渡し、受け取り側はNode.js 22以上とnpmが使える環境で `start.bat` または `start.ps1` を実行します。両方とも同梱の `start.mjs` を使います。初回は `npm ci --omit=dev --no-audit --no-fund` で、同梱lockfileのランタイム依存を導入してからAPIを起動します。導入には通信が必要です。[npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) はmanifestとlockfileが一致しなければ失敗し、lockfileを更新しません。

配布物には `package.json`・`package-lock.json` と、APIのCSP生成に必要な共有パッケージの `packages/shared/package.json`・`dist/` も含みます。これらを取り除かないでください。生成時はルートlockfileを種に、npmの `--package-lock-only --ignore-scripts --offline` で配布用の依存だけを残し、各パッケージの版・取得先・integrity・依存情報が元の同じ配置の記録と一致することを検査します。新しい解決が必要になった場合は生成を止め、ソース側で依存更新・監査・検証を行ってください。開発依存やElectron更新用依存はWeb配布へ含めません。

起動処理は導入成功後だけ `node_modules/.cipher-vault-runtime` に照合値を保存します。導入失敗ではAPIを起動せず、次回に再試行します。manifest・lockfile・共有パッケージのmanifest、NodeのモジュールABI・OS・archが変わった場合も再導入します。この記録は手動のファイル削除や改変を検出する保証ではありません。依存が破損した場合は配布フォルダ内の `node_modules` だけを削除して再起動し、`data` は保持してください。

生成物は一時領域で完成・検査してから `release/` へ移します。生成失敗では以前の配布物を置き換えず、既存データの停止条件も置換直前に再確認します。lockfileはnpmパッケージの固定と取得時のintegrity検査に使い、OS別のネイティブ実行可否や、install scriptが別途取得する成果物まで同じハッシュで固定するものではありません。データ保護とネイティブ依存については[日常の保守フロー](#日常の保守フロー)を参照してください。

## デスクトップ版のパッケージ化手順

### 1. 配布物を作成する

Windows 向けの `installer` と `portable` を生成します。

```powershell
npm run package:desktop
```

このコマンドで行われること:

1. `npm run build:desktop`
2. `electron-builder --win nsis portable --publish never`（生成のみ。公開しません）
3. `dist-desktop/` へ配布物を出力

依存更新などの検証では、既存の成果物と区別できる専用フォルダを指定します。

```powershell
npm run package:desktop -- --config.directories.output=dist-desktop/validation
```

この指定も生成だけを行います。バージョンを据え置いて作った検証用の成果物は公開せず、公開時は版を揃えて通常のリリース手順で再生成してください。生成成功に加え、ASARへのDB・ログ混入がないこと、更新情報のsetup名・サイズ・SHA512、preload・ネイティブ依存・フォントとライセンスの同梱、exeへのアイコン埋め込みを確認します。アプリの起動確認は専用の一時保管庫で行い、インストール後の更新適用とは区別します。

### 2. 出力物を確認する

生成先:

```text
dist-desktop/
```

主な出力物:

- `CIPHER-VAULT-<version>-x64-setup.exe`
  Windows 向けインストーラー
- `CIPHER-VAULT-<version>-x64-portable.exe`
  展開不要で起動できる portable 実行ファイル
- `CIPHER-VAULT-<version>-x64-setup.exe.blockmap`
  更新配信用の補助ファイル
- `latest.yml`
  更新配信用メタデータ
- `win-unpacked/`
  展開済みアプリ一式

`<version>` はルート `package.json` のバージョンです。公開時の成果物と更新用メタデータの扱いは[リリース手順](リリース手順.md)を参照してください。

### 3. アイコンについて

配布時のアプリアイコンは以下を参照します。

- `build/icon.ico`
- 元画像: `build/icon.png`

`electron-builder` の設定は `package.json` の `build` セクションにあります。

原本を変更したら `./scripts/build-icons.ps1` で ICO と画面用 PNG を再生成します。exe への埋め込みには `signAndEditExecutable: true` が必要です。詳細は [手動更新とアイコン](手動更新とアイコン.md) を参照してください。

### 3.1 `setup` と `portable` の違い

- `setup`
  通常のインストーラー版です。一般ユーザー向けの標準配布形です。
- `portable`
  インストール不要でそのまま実行できる版です。検証用途や、インストール権限がない環境で使いやすいです。
- どちらもアプリデータの保存先は Electron の `userData` 配下です。
  `portable` であっても、実装上は exe と同じフォルダに DB を保存しません。

### 3.2 公開方法

- OSS として公開する場合は、`GitHub Releases` または公開ダウンロードページに `setup` と `portable` を掲載する形で問題ありません。
- 公開時の導線としては、一般ユーザー向けに `setup` を先に案内し、必要な人向けに `portable` を併記する形を推奨します。
- リポジトリ本文にはソースコード利用者向け手順、`Releases` には実行ファイル利用者向け案内を書くと分かりやすくなります。

### 4. データ保存先

デスクトップ版の DB は `apps/api/data` ではなく、実行ユーザーの `userData` 配下に保存されます。

Windows の例:

```text
C:\Users\<ユーザー名>\AppData\Roaming\CIPHER VAULT\data\password-manager.db
```

この保存先は Electron の `app.getPath("userData")` を基準に決まります。

DB接続はimport時に作らず、起動処理が明示的に開きます。未知形式や読取専用で検査できないDBでは、初期化せず停止します。DBや `-wal` / `-shm` / `-journal` を削除して再試行せず、原本を保持してください。旧形式・接続API・旧列追加・読取専用の条件は[DBの接続と形式判定](設計.md#dbの接続と形式判定)を参照してください。

### 5. 既存版からの更新

更新機能がない旧版では、アプリを終了して新しい setup を同じインストール先へ上書きします。事前のアンインストールは不要です。2026-09-15 に利用者による移行完了を確認しています。

更新機能を搭載した setup 版では「ヘルプ」→「アプリ情報 / 更新」から確認・ダウンロード・再起動して更新できます。起動時の確認や通常終了時の自動適用はありません。配布には同じビルドの setup と `latest.yml` が必要です。

## CIと依存監査

WebはVite 8とReact plugin 6を使用し、Rolldown/OxcとLightning CSSでJS・CSSを処理します。実験的なReact Compilerは有効にしていません。`apps/web/vite.config.ts` の `build.target` はVite 5相当の `chrome87` / `edge88` / `firefox78` / `safari14` を明示し、ツール更新で出力目標が変わることを避けています。この指定だけで各旧ブラウザの実機動作を確認したことにはなりません。Electronのfile画面に必要な `base: "./"` とCSPの生成も維持します。

`.github/workflows/ci.yml` はブランチへのpush・pull request・手動実行で起動します。Windows 2025 x64とNode.js 24で `npm ci --no-audit --no-fund` を実行し、`test:security`、`test:api`、`test:sessions`、`test:updates`、`test:desktop-platform`、`test:desktop-session`、`test:desktop-v2`、`test:desktop-maintenance`、`test:desktop-dev`、`test:web-policy` を順に実行します。各コマンドが必要なビルドも行うため、ローカルとCIで同じ入口を使用できます。GitHub上で実行するには、このワークフローと関連ソースをpushする必要があります。構成の追加やローカルでの成功だけでは、GitHub runner上の成功を意味しません。

依存監査は別ジョブでlockfileだけを読み、install scriptを実行しません。`npm audit --package-lock-only --omit=dev --audit-level=high` は本番扱いの依存にhigh以上があれば失敗します。全依存の `npm audit --package-lock-only --audit-level=low` も失敗条件とし、開発・ビルド依存を含むlow以上の指摘や監査エラーを成功として扱いません。新しい指摘が出た場合は依存元・到達条件・修正版を確認して対応し、検証せずに除外や強制更新で通さないでください。npmの監査件数は、到達可能な攻撃や実際の侵害件数ではありません。

ワークフローの権限は `contents: read`、checkout後の認証情報の保持は無効です。外部ActionsはコミットSHAで固定し、npmのダウンロードキャッシュだけを再利用します。配布用exeの生成・アップロード・リリース、秘密の注入、DB・profile・クリップボードの成果物保存は行いません。Linux/macOS runner、インストール済みアプリの更新適用、実OS通知は、このWindows回帰ジョブの確認範囲に含めません。

依存更新は、同じ版のパッケージが複数経路に存在する場合もあるため、`npm explain <package>` とlockfileで親と実行経路を確認してから行います。更新順は次のとおりです。

1. criticalを含む開発・ビルド経路の親パッケージを優先します。`concurrently` の固定された `shell-quote` と、`electron-builder` / `@electron/rebuild` の `tar` を、親の修正版から確認します。各変更でクリーンインストールと該当回帰を実行し、builder変更では公開しない配布物の生成・起動も確認します。
2. Babel・PostCSS・tsx等の変換・解析・取得系も、既存の許容範囲と親パッケージの互換性を確認して更新します。`fixAvailable` だけを理由に強制更新せず、更新後の全体・本番監査を取り直します。
3. Viteのmajor更新は別の変更に分けます。React plugin・Node.js要件を確認し、ビルド済みfile画面、Vite開発画面とHMR、HTTP版、CSP、フォント、バックアップを再検証します。

Viteを呼び出す検証スクリプトはWebワークスペースの `package.json` を基点に解決します。npmによる配置が変わることがあるため、ルートの `node_modules/vite` へhoistされる前提を置かないでください。

本番依存に新しいhigh以上が出た場合は、この順番より優先して到達条件と修正版を確認します。`npm audit fix --force` の一括適用や、criticalが開発依存であることだけを理由にした恒久除外は行いません。

## 日常の保守フロー

`npm run test:desktop-platform` は一時 `userData` で実Electronを起動し、保存先とOS capability、非同期safeStorageの利用可否を検査します。利用中のprofileや保管庫は使わず、鍵・パスワードの保存や暗号化・復号は行いません。利用可能と返ってもOS保護は未検証のまま、簡易解除は無効です。準備前・利用不能・例外・timeout、OS/配布形態の判定と相対保存先の拒否は `test:sessions` 内の単体テストで確認します。通常起動からこのnative検査を呼ぶ処理はありません。[OS対応基盤の契約](設計.md#デスクトップのos対応基盤)を参照してください。

`npm run test:desktop-maintenance` は、中断した一時保管庫から実Electronを起動し、復旧画面の自動表示、通常解除・完全リセットの非表示、最小ウィンドウ幅、実復旧と再解除、旧masterの入力制約を維持した従来形式からの画面操作による移行を検証します。`test:desktop-v2` は管理画面の確認不一致、鍵更新、空Vaultへの切替の確認、native KDF中の取消、入力の破棄も扱います。利用中の `userData` は使いません。

`vault-maintenance.test.mjs` は `test:api` 内で両ランタイムから実行します。通常接続の停止・ロック状態での再接続、legacy移行・v2鍵更新・安全なリセット、中断後のアプリ再起動と明示復旧、認証・世代・読取専用・未知入力、HTTPのOrigin/CSRFと切断、native KDF中の取消と終了を合成DBで確認します。`web-session.test.mjs` は操作中の世代変更と最終状態の確認失敗も扱い、`test:desktop-v2` は実preload/IPCからの鍵更新、旧DB保持、新masterでの再解除も検証します。[管理サービスの契約](設計.md#保管庫の管理サービスと復旧専用起動)を参照してください。

`v2-replacement.test.mjs` は `test:api` 内で通常Node・Electron同梱Nodeの両方から実行します。新rootへの全件再暗号化、復旧データを保持した空Vaultへの切替、旧master/旧rootの拒否、実際の2^20 nonce上限からの鍵更新、独立backup復元、旧DB保持、別プロセスwriter停止、取消とSession世代、write/flush/close/rename失敗、各切替境界の即時プロセス終了と明示復旧を一時DBで検証します。数百MiBの一時領域が必要です。保存形式と復旧時の制約は[鍵更新・安全なリセット](設計.md#v2の鍵更新と安全なリセット)を参照してください。画面・HTTP/IPCからの操作や実データでの受入確認は含みません。

`v2-runtime.test.mjs` は `test:api` 内で両ランタイムから実行します。合成legacyを実際にstaging・pointer切替したfixtureを使い、通常起動、解除、全DTOのCRUD、v1との相互復元、復元失敗の全件巻戻しとnonce保持、Context変更、idle/lock、鍵使用上限、旧DBの保持、実HTTPサーバーの再起動を確認します。legacyのロック取得前後の切替、古い準備済みSQL、失効通知中のContext置換も再現します。`npm run test:desktop-v2` は同じ移行経路から一時 `userData` を作り、実ElectronのReact画面で解除・追加・編集、preload/IPCで削除・復元・監査・再解除、終了時のroot消去と接続解放を検証します。既存の保管庫は使いません。CIにもこの画面試験を登録しています。通常操作と残る制約は[通常起動とv2サービス](設計.md#通常起動とv2サービス)を参照してください。

`vault-activation.test.mjs` は `test:api` 内で両ランタイムから実行します。保存済みcandidateの再検証、原本と移行先の別プロセスwriter停止、Session世代/idle/取消、pointer・受領記録の破損と欠落、junction/hard link、write/flush/close/rename失敗、各保存境界での即時プロセス終了と明示復旧を確認します。移行後のv2編集を旧データで上書きしないことも検証します。Windows sandboxが一時ファイルのrenameやjunction操作を拒否した場合は、同じ一時データの試験をsandbox外で再検証し、環境の拒否と実装の失敗を区別します。契約と残る永続化条件は[pointer切替と復旧](設計.md#移行pointerの切替と復旧通常起動への接続前)を参照してください。

`migration-staging.test.mjs` は `test:api` 内で通常Node・Electron同梱Nodeの両方から実行します。新password・新rootでの全項目暗号化、保存したbackup/SQLite snapshotとv2再open後の全DTO照合、DELETE/WALの別プロセスwriter停止、原本DB/WAL保持、旧master/旧鍵の拒否、flush・close・native KDF失敗、取消、nonce予約直後の即時プロセス終了を一時データで確認します。失敗したstagingは自動再利用せず、通常起動の選択先も変更しません。配置・容量と復旧制約は[移行staging](設計.md#原本を保持するv2移行staging通常起動への接続前)を参照してください。実電源断・親directoryの永続化・pointer切替の受入試験は含みません。

`migration-preflight.test.mjs` は `test:api` 内で通常Node・Electron同梱Nodeの両方から実行します。旧DBの読取専用検査、暗号化backupの実サービス復元と全DTO一致、固定vector、旧列・長文、不正UTF-8、11 MiB境界、WAL更新、取消・鍵消去、独立した現在のVaultを変更しないことを合成データで確認します。復元照合のVaultはメモリ内に作り、利用中のデータは読みません。契約と上限は[原本保持移行の読取検査](設計.md#原本保持移行の読取検査通常起動への接続前)を参照してください。

`v2-store.test.mjs` も `test:api` 内で両ランタイムから実行します。独立v2ファイルの作成・拒否・読取専用、固定ベクトル、nonce衝突・書込失敗・取消・即時プロセス終了後の非再利用、実際の2^20予約と10000件の容量境界を確認します。大きな一時DBを生成するため、一時フォルダに数百MiBの空き領域が必要です。通常の保管庫や既存の配布データは使いません。APIと適用前の条件は[v2保存層](設計.md#v2保存層)を参照してください。

`database-lifecycle.test.mjs` は `test:api` 内で通常Node・Electron同梱Nodeの両方から実行します。import時のDB作成防止、未知形式の拒否時の原本保持、読取専用・旧列追加・途中失敗の巻戻し・writer競合・再接続・WAL、実HTTP入口の起動拒否と待受失敗時の接続解放を一時DBで確認します。`test:desktop-session` では、実Electronの通常終了で接続が閉じることも確認します。

`test:api` はElectronをNodeモードで起動し、同梱ランタイムでサービスを検証します。続いて通常のNode.jsでWeb配布の起動処理と導入を検証します。ソース外の一時フォルダで `npm ci` を実行し、共有パッケージ・CSP・SQLite・CRUD・ロック・再起動、導入失敗とmanifest不一致時の停止を確認するため、配布依存の取得には通信が必要です。better-sqlite3 13以降はNode-APIを使い、NodeとElectronの固有ABIを切り替えるための再ビルドは不要です。テストは利用中の保管庫を使用しません。

同じコマンドで `crypto-compatibility.test.mjs` も実行し、独立生成した固定データから旧DB・v1バックアップの互換性を確認します。暗号処理・検証値・Salt解釈・保存形式を変更する場合は、単なる新writerとreaderのroundtripに加えて、この固定入力を維持してください。Node.jsだけで実行でき、Pythonやcryptographyの導入はテストの前提ではありません。期待値を変更する際は、実装から一括再生成してテストを通すのではなく、形式の変更理由と別実装での一致を確認します。fixtureの鍵・password・IVはすべて合成データで、本番の既定値へ流用しません。

`v2-codec.test.mjs` は同じ `test:api` の中で、Electron同梱Nodeと通常Nodeの両方から実行します。固定ベクトルとの一致、envelope・AAD・ID・容量境界、不正UTF-8、認証前の平文拒否、nonce予約、KDF中の取消と実行枠の維持、プロバイダ失敗時の秘匿と一時Bufferの消去を確認します。モジュールのimportがDBを作らないことも独立プロセスで検証します。この単体試験自体は既存保管庫を使わず、通常起動は上記runtime試験で別途検証します。呼出契約は[v2 codec](設計.md#v2-codec)を参照してください。

画面のsandbox・preload・CSP・権限を変更した場合は `npm run test:security` で境界を検査します。`npm run test:desktop-session` はビルド済みfile画面、`npm run test:desktop-dev` は専用ポートの一時Viteサーバーを使い、実Electronでフォント、保管庫操作、バックアップ書き出し・復元・Blobダウンロード、権限拒否を確認します。開発版ではHMRのWebSocket接続も確認します。`npm run test:web-policy` は一時HTTPサーバーと独立したブラウザ画面で、本番CSP、同一オリジンのAPI通信、インラインスクリプト・外部通信の拒否を検証します。いずれも専用の一時profile・DBを使用して終了時に削除し、既存の保管庫を使いません。インストール済み配布物や各OSの実機確認は別に行います。

OSイベント・コピー期限・入力契約・KDF・解除試行制御・セッションを変更した場合は `npm run test:sessions` も実行します。共通入力契約のUTF-8境界・未知項目・引数個数と、旧実装の固定出力とのKDF互換性、同時実行・試行待機を確認し、時計とタイマーを注入して期限境界・時計変更・旧世代の応答も検証します。`npm run test:desktop-session` はElectronを実起動し、独立した一時 `userData` で初期設定・登録・ロック・再解除・KDF中のIPC取消と試行待機・HTTPと共通の不正入力・旧長文の取得・OS通知によるロック・実時間30秒のコピー期限・renderer喪失・通常終了時の消去を自動確認します。クリップボードAPIは試験中ずっと差し替え、OSの実クリップボードを読み書きしません。OS通知と画面ロック状態の照会結果もElectron内で模擬し、実際の画面ロック・スリープは行いません。各OSの実通知と実クリップボードの形式・アクセス可否は、実機受入確認として区別してください。5分経過はテストプロセス内の壁時計で模擬し、実際の5分放置試験とは区別します。実時間の5分放置を確認する場合は、PowerShellで `$env:CIPHER_VAULT_QA_REAL_IDLE = "1"` を設定して同じコマンドを実行し、終了後に `Remove-Item Env:CIPHER_VAULT_QA_REAL_IDLE` で戻します。既存の `userData` や開発用DBは使いません。

Electronビルドでは型検査後に `prepare-preload.mjs` が単一の `preload.cjs` を生成し、旧生成物の `preload.js` / `preload.mjs` を削除します。sandboxを解除して読み込みエラーを回避せず、生成物と限定APIを上記テストで確認してください。画面のCSPと開発時例外は[設計](設計.md#画面のsandboxとcsp)を参照してください。

フォントと原ライセンス・取得元記録は `apps/web/public/fonts/` に置き、ViteのpublicアセットとしてWeb・Electron両配布へコピーします。配布時にライセンスファイルを除外しないでください。

デスクトップ配布のNode.jsはElectronに含まれ、単独では差し替えません。Electronを更新して `npm run package:desktop` で配布物を再生成します。Web/API配布版はNode.jsを同梱せず、利用者の環境のランタイムを使います。

Windows x64配布ではbetter-sqlite3の同梱済みNode-APIバイナリを使用します。`build.npmRebuild: false` で不要なElectron ABI向けの再ビルドを避け、生成後のアプリでSQLiteの読み書きを確認します。ABIに依存するネイティブ依存を追加する場合は、この設定を見直してください。

Web/API向けの `npm run package` は空の `release/data` を生成します。開発用DBはコピーしません。既存の `release/data` にデータがある場合は停止するため、既存のreleaseフォルダ全体を安全な場所へ移してから実行します。

検証値を移行するv0.2.1の変更では、移行後の旧版利用に制約があります。[v0.2.1の修正](リリースノート/v0.2.1.md)を先に確認してください。

UI 改善や機能追加、軽微な保守を行うときは、基本的に次の流れで進めます。

1. 変更内容を整理する
2. 影響箇所を確認する
3. コードを修正する
4. `npm run dev:desktop` で実画面を確認する
5. `npm run build:desktop` でビルド確認する
6. 必要に応じて `npm run package:desktop` で配布物を確認する
7. 差分を見直す
8. 明示的な依頼があれば、対象ファイルを確認してコミットする
9. 明示的な依頼があればプッシュする

### 小さな変更の推奨フロー

```powershell
npm run dev:desktop
npm run build:desktop
git status
git add .
git commit -m "..."
git push
```

### 配布物に影響する変更の推奨フロー

```powershell
npm run dev:desktop
npm run build:desktop
npm run package:desktop
git status
git add .
git commit -m "..."
git push
```

### 補足

- UI 修正では `build` だけでなく `dev:desktop` での見た目確認を推奨します。
- アイコン、起動フロー、保存先、Electron 設定を触った場合は `package:desktop` まで確認したほうが安全です。
- 公開済み版から更新できるようにするにはバージョン番号を上げ、新しい GitHub Release に対応する成果物と更新情報を揃えて公開します。同じ番号のファイル差し替えだけでは更新対象になりません。

## Codex を使う場合の運用フロー

このプロジェクトでは、`Codex` にコード修正を依頼し、手元で起動確認する流れが基本運用として適しています。

### 基本フロー

1. Codex に改善内容を依頼する
2. Codex がコード修正、関連ファイル更新、必要な設定変更を行う
3. 手元で `npm run dev:desktop` または `npm run build:desktop` を実行する
4. UI、動作、起動可否を確認する
5. 問題があれば再度 Codex に修正を依頼する
6. 問題がなければコミット、プッシュ、必要に応じて配布物を更新する

### 役割分担の目安

- Codex が担当しやすいもの
  実装、リファクタリング、設定変更、ドキュメント更新、エラー修正
- 人が確認したほうがよいもの
  UI の見た目、操作感、配布物としての違和感、最終的な採用判断

### 推奨コマンド

```powershell
# 見た目や挙動の確認
npm run dev:desktop

# 本番寄りのビルド確認
npm run build:desktop

# 配布物確認が必要な場合
npm run package:desktop
```

### 補足

- UI 修正や UX 改善は、Codex の修正後に必ず人が画面確認したほうが安全です。
- Electron の設定変更や配布関連修正は、`package:desktop` まで回して確認することを推奨します。

## トラブルシューティング

### `npm run start:desktop` で起動しない

以下を順に確認します。

1. 先に `npm run build:desktop` を実行しているか
2. `apps/electron/dist/apps/electron/src/main.js` が存在するか
3. 以前の `Electron` プロセスが残っていないか

### `npm run package:desktop` で失敗する

以下を確認します。

1. `npm install` をやり直す
2. `better-sqlite3` の再ビルドが通る環境か確認する
3. `build/icon.ico` が存在するか確認する
4. `npm run build:desktop` 単体が成功するか確認する

### アイコンが古いまま見える

まず `build/icon.ico` の再生成と `signAndEditExecutable: true` を確認し、配布物を作り直します。false では Electron の標準アイコンが残ります。
正しいアイコンが exe に埋め込まれていても表示が古い場合は、Windows のアイコンキャッシュの影響を切り分けます。ビルド時の winCodeSign 展開エラーについては [手動更新とアイコン](手動更新とアイコン.md) を参照してください。

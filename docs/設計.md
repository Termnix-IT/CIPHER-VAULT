# CIPHER VAULT 設計

## 設計方針

- ローカルファースト: 保管庫データは端末内の SQLite に保存する
- 単一ユーザー: マルチユーザー管理や外部認証を持たない
- UI と処理の分離: React UI は `window.passwordManager` からTauriのコマンドを呼び、保管庫の処理はRustの中核（`crates/vault-core`）が行う
- 依存関係を抑制: 暗号は同じ系統の純Rustのライブラリにそろえ、OS連携は導入済みの `windows` クレートで行う（理由は[Rust版の設計判断](#rust版の設計判断)）
- 本人の画面操作に限定: 保管庫の読み取り・検索・変更は、アプリを操作している本人の画面操作だけで行う。別のアプリ・プロセス・エージェント・ブラウザ拡張から保管庫へ要求を送る入口は持たない。v0.9.0まで提供したWeb/API版のHTTP APIは、本人の画面が使う内部経路としてこの対象外としていたが、Web/API版の廃止とともになくした。外部連携が必要になった場合は、実装の前にこの方針から見直す

## システム構成

```text
React UI（apps/web）
  └─ window.passwordManager（apps/desktop/src/desktop-api.js）
        │  Tauri IPC（許可したコマンドだけ）
        ▼
デスクトップ（apps/desktop）
  ├─ コマンドの入口（セッションの世代とロックの確認）
  └─ クリップボード・画面ロック/スリープ・多重起動・手動更新
        │
        ▼
中核（crates/vault-core）
  ├─ 保管庫・エントリ・バックアップ・監査・保守
  └─ 暗号形式・保存
        │
        ▼
      SQLite
```

| パッケージ | 役割 |
|---|---|
| `apps/web` | React + Vite のユーザーインターフェース |
| `apps/desktop` | Tauriのウィンドウ、コマンド、WebView2の設定、クリップボード、画面ロック・スリープとの連動、多重起動の防止、手動更新、setupのフック |
| `crates/vault-core` | Tauriに依存しない中核。暗号形式、保存、セッション、保管庫・エントリ・バックアップ・監査・保守 |
| `packages/shared` | 画面が使う共通の型と画面のCSP |

詳細な経路は[ワークフロー](ワークフロー/02-画面からSQLiteまで.md)を参照してください。

## 実行経路

画面は `apps/web/src/lib/api.ts` から `window.passwordManager` を呼びます。このAPIはTauriの初期化スクリプト（`apps/desktop/src/desktop-api.js`）が画面の読み込み前に用意し、各メソッドを名前の決まったコマンドへ渡します（[画面から呼べるコマンド](#画面から呼べるコマンド)）。メソッド名と引数の順はElectron版のpreloadと同じなので、画面はElectron版から変えていません。`window.passwordManager` がない環境では、画面は保管庫を操作できません。

各コマンドは、セッションIDの世代確認と操作前後のロック確認をElectron版のIPCと同じ順で行ってから中核を呼び、画面にはエラーの文言だけを返します。

保存先は `%APPDATA%\<製品名>\data` で、配布版の製品名は「CIPHER VAULT」です。環境変数 `CIPHER_VAULT_DATA_DIR` で差し替えられます（[開発・配布手順](開発・配布手順.md#データ保存先)）。

## 画面とCSP

画面はWebView2で表示します。既定のコンテキストメニュー、ステータスバー、ホストオブジェクト、ブラウザのショートカットキー、自動入力、パスワード保存、開発者ツールを無効にし、権限要求をすべて拒否します。WebView2の設定を外から変える環境変数は起動時に消し、同じ指定をするレジストリのポリシーがあれば起動しません。外部への画面遷移と新しいウィンドウは拒否します。配布ページは固定URLを、ユーザーの操作で既定のブラウザに開きます。WebView2のプロファイルはincognitoにしません。表示設定（シンプル／ルミナス）を画面の `localStorage` に保存しているためです。秘密は `localStorage` などの保存領域に書きません。

画面から呼べるコマンドは、`apps/desktop/build.rs` の一覧と `tauri.conf.json` の `capabilities` の両方に書いたものだけです。Tauriは、一覧がないと登録したコマンドをすべての画面に公開します。Tauri本体のウィンドウ操作は、画面のタイトルバーに必要な最小化・最大化・閉じる・ドラッグ移動・最大化状態の取得だけを許可し、タイトルの変更などその他の操作と、更新プラグインが画面向けに用意するコマンドは許可していません。

CSPは `packages/shared/src/renderer-policy.ts` で定め、ViteがHTMLのmetaへ書き込みます。Tauriは `tauri.conf.json` の `csp` も重ねて適用するため、両者を同じ文字列にしています（`npm run test:web` で照合）。同一オリジンのスクリプトだけを許可し、インラインスクリプトと `eval` を許可しません。`base`、frame、object、worker、フォーム送信も拒否します。Reactの既存表示で必要なstyle属性は許可し、style要素・CSSファイルは同一オリジンに制限します。通信はTauriのIPC（`ipc:` と `http://ipc.localhost`）だけに許可し、画像のdata/Blobは許可します。

画面の文字に使うNoto Sans JPと、値の表示に使うJetBrains Monoは `apps/web/public/fonts/` に原本とSIL Open Font License 1.1を同梱します。日本語はOS側にCJKフォントがない環境でも同梱フォントへfallbackします。`sources.json` に固定した取得元revisionとSHA-256を記録し、Google Fontsへの通信は行いません。フォントを差し替える場合も利用条件とライセンス同梱を確認してください。

## 入力の検証と上限

画面のコマンドは、中核の `crates/vault-core/src/input.rs` の実行時検証を通ります。型定義だけには依存せず、既知の項目だけを持つオブジェクト、各値の型、UTF-8のバイト数、配列の件数を検査します。文字列の容量は日本語等の多バイト文字も含めてUTF-8のバイト数で数えます。エラーには入力された秘密や未知の項目名を含めません。

エントリの保存・編集で受け付ける項目は `serviceName`、`loginId`、`password`、`notes`、`url`、`tags`、`group` です。取得結果の `id` や日時を含む未知の項目は400で拒否します。従来どおり、任意項目 `notes`・`url`・`group` の省略・nullは空文字、`tags` の省略・nullは空配列として扱います。パスワードはtrimやUnicode正規化を行いません。

| 対象 | 上限・条件 |
|---|---|
| 保存内容を正規化したJSON | 1 MiB。JSONのエスケープによる増加も含む |
| 復元要求のJSON | 18 MiB。`.cvault` 本体16 MiB、復号内容11 MiB、10,000件という従来の制限も維持 |
| 管理操作のJSON | 4 MiB。各masterの通常解除時の1 MiB・JSON上限を維持し、旧・新・確認とbackup用入力を含める |
| サービス名・グループ | 各1,024 byte |
| ログインID | 4,096 byte |
| パスワード | 64 KiB |
| メモ | 256 KiB |
| URL | 8 KiB。認証先としての信頼判定はこの文字列検証に含まない |
| タグ | 100件、各256 byte。配列の穴や文字列以外の値は不可 |
| 保管庫の新規登録 | 全体で10,000件まで。既存行の閲覧・削除は維持 |
| マスターパスワード | 1 MiBとJSON全体の上限内。初期設定の12文字以上という条件を維持し、旧形式の解除では新しい最小長を課さない |
| バックアップ用パスフレーズ | 従来の12〜1,024文字、UTF-8で4,096 byte以内 |
| エントリID・セッションID | 128 byte以内。エントリIDは空文字・NULを不可とする |
| クリップボード入力 | 文字列、1 MiB以内 |

型・項目・値の不正は400、容量・件数超過は413に当たるエラーとして扱い、画面には文言だけを返します（statusの値はElectron版のHTTP APIと同じ分類です）。世代やロック状態による409・423に当たる拒否は、コマンドの入口で行います。クリップボードへの書き込み前にも共通検証を通します。容量の検証は、デスクトップがデータを受け取った後に行います。

項目別の編集上限を保存済みデータの読み取りに適用しません。上限を超える既存の長文やタグも、閲覧と従来のバックアップ全体上限内での書き出し・v1復元を維持し、自動で切り詰めません。新しい編集上限を超える値を含む保存は元データを変更せずに拒否するため、編集する場合は入力を上限内へ調整する必要があります。DBスキーマや暗号形式の移行は行いません。

## 保管庫と暗号化

この章と[データモデル](#データモデル)の章の規則は、中核（`crates/vault-core/src`）が実装します。規則はElectron版のTypeScriptのサービスで定めたもので、Rust版が同じ入力に同じ結果とエラー文言を返すことを、v0.9.0までの差分試験で確かめました。移植元のファイルはタグ `v0.9.0` の `apps/api/src` にあります。主なモジュールは次のとおりです。

| モジュール | 受け持つこと |
|---|---|
| `crypto.rs` | legacyの鍵導出・検証値・暗号文と、v2のpassword slot・entryのenvelope |
| `backup.rs` | `.cvault` の作成と復元 |
| `input.rs` | 画面からの入力と、保存済みentryの検証 |
| `legacy.rs` | 従来形式（legacy）のSQLiteファイル |
| `v2.rs` | v2のSQLiteファイルとnonceの予約 |
| `selection.rs`、`files.rs` | 保存先がどの保管庫を選んでいるかの判定と、保存先のパスの検査 |
| `session.rs`、`unlock_guard.rs` | 保持中の鍵・セッション世代・無操作期限と、初期設定・解除の同時実行・試行待機 |
| `vault.rs` | 画面のコマンドから呼ばれる保管庫の操作 |
| `password.rs`、`audit.rs` | パスワード生成とパスワード監査 |
| `maintenance/`、`vault/switch.rs` | 移行・鍵更新・リセット・中断後の復旧 |

手動更新の通信は保管庫操作とは分離しています。更新確認・ダウンロード時に GitHub へ接続しますが、保管庫データは送信しません。

### マスターパスワード

マスターパスワードそのものは保存しません。

1. 16 byteのランダムSaltを生成する
2. `scrypt` で32 byteの保管庫鍵を1回導出する。パラメータはElectron版と同じN=16384、r=8、p=1で、保存済みSaltはBase64をデコードせず文字列のまま渡す
3. 鍵をキー、固定ラベル `CIPHER VAULT password verifier v1` をメッセージとするHMAC-SHA256を検証値としてSQLiteへ保存する（鍵そのものは保存しない）
4. 検証値は定数時間で比較する（`subtle`）
5. 解錠中だけ保管庫鍵をプロセスメモリに保持する

初期設定と解除は `unlock_guard.rs` の共通制御を通り、同時に1件だけ鍵導出を実行します。追加の要求は409で拒否し、パスワードを順番待ちで保持しません。導出中も状態取得・ロック・リセットを処理でき、導出開始時の世代が変わっていれば導出した鍵を破棄します。初期設定の保存や旧検証値の移行は、導出後の世代確認に通った場合だけ行います。ロック済みの現世代へのロック要求も、未完了の解除を無効にします。実行中のscrypt自体は中断せず、終わるまで実行枠を保持します。

誤パスワードによる401が5回連続すると、次の試行まで1秒、以後2・4・8・16・30秒（上限）の待機を設けます。待機中は429に当たるエラーと残り秒数を返します。拒否された連打で期限を延長せず、入力不正・取消・保存失敗は認証失敗として数えません。成功で回数と待機を解除し、手動ロックやリセットでは解除しません。状態はプロセス内だけに保持し、再起動で失われます。これはオンライン試行の負荷・頻度の制御で、DB入手後のオフライン推測に対するKDF強化とは別です。

鍵の有無、解除状態、セッション世代、5分の無操作期限は `session.rs` の1つのセッションが持ちます。鍵は `zeroize` で包み、手動ロック・自動ロックで破棄するときにゼロ埋めします。プロセスのメモリ全体（OSやWebView2が持つコピーを含む）の消去を保証するものではありません。

秘密を扱う操作の入口・暗号処理の後・結果を返す前に、期限と世代を照合します。期限を過ぎた後の操作や期限の延長は、ロックの処理がまだ動いていなくても拒否します。単調時計と壁時計の経過時間を併用し、時計の巻き戻りや不正な値もロック側へ倒します。解除中の通常の操作・状態確認・監視は無操作期限を延長しません。

画面は信頼された入力イベントの発生時だけ、最大約1秒の間隔で末尾の操作も含めて `vault_activity` コマンドで通知します。画面が渡す日時で期限を決めず、中核自身の時計を使います。これは人がいることを証明する仕組みではなく、信頼する同梱の画面を前提とします。デスクトップは下記のOSイベントにも連動します。外部のアプリやエージェントから呼べる入口は設けていません（[設計方針](#設計方針)）。

デスクトップはウィンドウを閉じたとき・画面のプロセスが落ちたときも鍵を破棄します。画面は約1秒ごとの状態確認とfocus/visibilityの変化で中核の状態に追従します。Rust版は状態の変化を画面へ通知しないので、ロックはこの状態確認で画面に届きます。状態確認が5秒以内に完了しない場合は画面の表示をロックし、同じ世代への再接続だけでは表示を戻しません。

画面と通信層はセッションの変更時に未完了のPromiseを無効にし、一覧・詳細・編集中の値・監査/バックアップ画面を破棄します。遅れて届いた応答は、再解除後の世代へ適用しません。既存のSalt文字列、scryptパラメータ、HMACラベル、DBスキーマ、暗号文と `.cvault` v1形式は維持します。

この検証値の修正はv0.2.1から適用されます。v0.2.0以前は導出鍵そのものを検証値に保存していました。旧形式は正しいパスワードでの解除時に `kdf_params.verifierAlgorithm = "hmac-sha256-v1"` を追加し、検証値を置き換えます。暗号文と鍵導出方式は維持し、移行後は旧版で解除できません。失敗した認証では移行せず、移行の書き込みに失敗した場合も解錠しません。

SQLiteの `secure_delete` を有効にしますが、既存のバックアップ、ジャーナル、ファイルシステムの過去データの消去は保証しません。旧DBに含まれた鍵はこの移行で失効しません。詳細と対応範囲は [v0.2.1の修正](リリースノート/v0.2.1.md) を参照してください。

### OSイベントとクリップボード

画面ロック・スリープ・復帰の通知は、アプリの隠しウィンドウでWindowsのウィンドウメッセージとして受け取ります（`apps/desktop/src/os_events.rs`）。Tauriはこれらの通知を公開していないためです。通知を受けると保管庫をロックし、処理中の解除も世代変更で取り消します。復帰・画面解除では保管庫を自動解除しません。画面ロック中・スリープ中・終了中は、状態確認と保管庫ロックを除く保管庫操作を拒否します。この確認は中核がElectron版の `assertAvailable` と同じ位置で呼ぶので、拒否の順番も同じです。通知で受けた画面ロック・スリープの状態は、解除・復帰の通知が届くまで保持します。操作時には現在の画面ロック状態も問い合わせ、通知が届かなかったロックも拒否します。Electron版は、この問い合わせで見つけたロックも画面解除の通知まで覚えていましたが、Rust版は問い合わせの結果を覚えずに毎回問い合わせます。問い合わせで見つけたロックについて解除の通知を取りこぼしても、再起動するまで使えなくなることがないようにするためです。実際の通知が確実に届くかは、実機でのロック・スリープによる受け入れ確認が別途必要です。

コピーはWin32のクリップボードAPIを直接使います（`apps/desktop/src/clipboard.rs`）。平文と一緒に、ランダムな所有マーカーと、クリップボード履歴・クラウド同期から外す指定を書きます。期限は `packages/shared/src/index.ts` の `CLIPBOARD_CLEAR_AFTER_MS` と同じ30秒です。保持する期限情報はマーカー・SHA-256の照合値・時刻で、タイマーのためにコピーした平文を保持しません。

期限時と保管庫ロック時に、マーカーと内容の照合値が一致する場合だけクリップボードを消去します。照合と消去はクリップボードを開いている間に行うので、別のアプリが間に書き換えた内容は消しません。手動ロック、OSイベント、ウィンドウ終了、画面のプロセス喪失、更新、通常終了もこの経路を通ります。

所有マーカーはクライアント認証ではありません。履歴・同期・他アプリが保存した過去のコピーの消去は保証しません。

### デスクトップのOS対応

同じ保存先でアプリを2つ起動すると、2つ目は保管庫を開く前に、先のウィンドウを前面に出して終了します（名前付きmutex。名前は保存先フォルダから作ります）。Electron版はこの仕組みを持たないため、Rust版はElectron版と同じ保存先を開くとき（`CIPHER_VAULT_DATA_DIR` で同じフォルダを指定したときを含む）、Electron版のプログラム（`<製品名>.exe`）が動いていれば、保管庫を開かずに理由を表示して終了します。逆に、Rust版の起動中にElectron版を起動することは防げません。Electron版はsetupで削除されるので、Electron版のportable版を併用した場合だけ起こります。

Vault鍵・マスターパスワードのOS保存、簡易解除、起動時の自動解除は追加していません。配布と検証の対象はWindowsだけです。

### エントリ暗号化

legacy形式ではパスワードとメモをAES-256-GCMで個別に暗号化します。

```text
[ IV (12 bytes) | Auth Tag (16 bytes) | 暗号文 ] → Base64
```

legacy形式のサービス名、ログインID、URL、タグ、グループ、日時は検索・一覧表示のため平文で保存します。v2では下記のcodecでentry全体を暗号化します。

現行形式の互換性は `tests/fixtures/crypto-compatibility.json` の合成固定データでも検証します。Salt文字列・Unicode・生鍵/HMAC検証値・GCMの並び・旧DB行・`.cvault` v1を、実装とは別のPython hashlib/hmacとcryptographyで生成し、`crates/vault-core/tests/fixture_compat.rs` で照合します。`draftV2` は下記codecを照合する独立した参照データであり、アプリの保管庫が新形式へ移行したことを意味しません。

### v2の暗号形式

v2の暗号処理は `crypto.rs` にあり、保存・セッション・ファイルを扱いません。v2保存層と保管庫の操作から呼ばれます。既存のlegacy DBと `.cvault` v1の形式は変えません。v2は次の2種類のenvelopeを使います。

- password slot: 保管庫ごとに1つある32 byteのroot鍵を、マスターパスワードからscryptで導出した鍵で包んだもの。`vaultId`・`keyId`・`slotRevision` を結び付け、包むたびに新しいSaltとIVを使う。scryptのパラメータは固定の一覧にあるものだけを受け付ける。
- entry envelope: entry全体のJSONを、root鍵からHKDFで導出した用途別の鍵で暗号化したもの。`vaultId`・`keyId`・`entryId`・`revision` を結び付ける。

復号では、呼び出す側が期待するID・revisionとの一致とGCMの認証を両方確かめ、envelope自身に書かれた値を期待値の代わりにしません。追加認証データ（AAD）は検証したID・版・用途から固定の形で作り、受け取ったJSONのキー順やescapeをAADに使いません。

`context` のUUIDは小文字のv4、entryIdは有効なUTF-8で128 byteまで・NUL不可、revisionは1〜4294967295です。暗号方式はAES-256-GCMで、IVは12 byte、tagは16 byteに固定します。envelopeのJSON入力は16 MiB、entryの平文は11 MiBまでです。過去の長文・null・空文字・タグ順序を新規編集の上限で切り詰めません。未知のprofileや任意のN/r/p/maxmemをKDFへ渡さず、legacyの読み方へのfallbackもしません。

IVは暗号化の前に保存層で永続的に予約します（[v2保存層](#v2保存層)）。予約が衝突したときは新しいIVで最大8回まで試し、予約できなければ暗号文を返しません。固定のSalt・IVや任意の乱数を指定する経路はありません。一時的なパスワード・KDFの出力・用途別の鍵・復号した平文は `zeroize` で消去します。エラーは形式不正・認証失敗・処理失敗などを区別し、入力値を含めません。

## データモデル

### 種類別エントリ

`VaultEntry` はログイン・APIキー・クレジットカード・銀行/証券の共用体です。既存ログインは従来のDTOを維持し、追加種類だけ必須の `type` と `apiKey` / `card` / `financial` を持ちます。追加種類にはトップレベルのダミーのログインID・passwordを保存しません。種類は更新時に変更できず、従来形式の保管庫ではログインだけを受け付けます。

APIキーはキー本体を必須とし、キーID・接続先URL・日単位の有効期限を任意とします。キー本体の空白・改行は保持します。カードは番号を必須、名義・月単位の有効期限・3〜4桁のセキュリティコードを任意とし、暗証番号は扱いません。番号はASCII空白とハイフンを除いた12〜19桁を保存し、有効性や利用可能性の認証は行いません。銀行/証券はログインIDとログインパスワードを必須、取引パスワードと、名前を付けた追加の秘密（第2暗証番号など、最大8件）を任意とします。金融機関はログイン用と取引用で秘密を分けるのが基本なので、メモではなく秘密ごとに伏せ字とコピーを提供します。追加の秘密の名前は画面上の識別子なので、重複と固定欄の名前を受け付けません。生成はログインパスワードだけに提供します。取引パスワードは数字のみなど金融機関ごとの指定が多く、既存の生成器では合わないためです。いずれの秘密も値の空白を保持します。これらの種類に名前・グループ・タグ・メモを持ち、全項目を既存のv2暗号envelopeに含めます。新しい暗号方式や依存は導入しません。

一覧は安全な共通メタデータと種類、カードの末尾4桁だけを返し、キー・キーID・番号全体・セキュリティコード・名義・銀行/証券のログインIDと秘密は返しません。契約者番号は口座に直結するため、銀行/証券はログインIDでは検索できません。秘密値は検索対象外です。秘密の表示は項目ごとに2回の操作を必要とし、選択変更・編集切替・保存・ロック時に伏せ字へ戻します。コピーには既存の期限付きクリップボードを使います。パスワード監査の母数と詳細読取りはログインに限定します。銀行/証券を対象外とするのは、数字4〜6桁の取引パスワードなどが「弱い」と判定され、点数が実態に合わなくなるためです。

鍵更新・リセット前の復旧検証も種類別DTOを全件比較します。v2バックアップは独立した一時v2保管庫へ別の鍵で実際に復元し、close・reopen・全件の認証復号後にIDごとに照合します。一時DBは暗号文だけを保存し、所有する一時ディレクトリだけを削除します。従来のv1検証は既存のメモリ内legacy復元を維持します。

### グループ

グループは各エントリの `group` 欄の値であり、別の保存先を持ちません。1項目は1グループだけに属し、最後の項目が抜けたグループは一覧から消えます。空のグループを残せないので、新規グループの作成には対象項目が1件以上必要です。「グループなし」は未所属の見出しなので、新規グループ作成と一括変更ではグループ名に使えません。

複数項目のグループ変更は `setEntriesGroup` で行います。画面が各項目を読み出して更新すると、開いていない項目の秘密まで画面側へ渡るためです。この処理は入力として項目IDとグループ名だけを受け取り、変更件数だけを返します。すでに同じグループにある項目は更新しないので、更新日時も暗号化回数も増えません。パスワード変更日はどの形式でも変わりません。

legacy形式は平文の `group_name` と `updated_at` だけを1トランザクションで更新し、既存の暗号文には触れません。v2はentryごとに暗号envelopeが独立しているため、1件ずつ復号・再暗号化して保存します。存在しないIDは書き込み前に拒否しますが、書き込み途中で失敗すると処理済みの項目は変更後のまま残ります。部分適用をなくすには全件を1トランザクションへまとめる必要があり、1件の更新を起点にした現在の書き込み経路より影響が大きいので採用していません。画面はエラーを表示したうえで一覧と開いている項目を読み直し、実際の状態を見せます。再暗号化は保管庫の暗号化回数（上限2^20回）を消費します。

### DBの接続と形式判定

保管庫は起動時に `vault.rs` が1回だけ開きます。保存先（`%APPDATA%\CIPHER VAULT\data`、または `CIPHER_VAULT_DATA_DIR`）の選択情報を `selection.rs` で調べ、pointer・受領記録・transitionのいずれもなければ従来形式の `password-manager.db` を `legacy.rs` で開きます。v2が選ばれていればv2保存層だけを開き、中断した切替が見つかれば[復旧専用の状態](#保管庫の管理サービスと復旧専用起動)で開きます。新規の保管庫の初期設定は従来形式で作り、移行やpointerの保存を起動時に自動で行いません。

既存ファイルは読み書きの接続より先に調べます。legacyは `application_id = 0`・`user_version = 0`、通常の `vault_metadata` と `password_entries` の2テーブル、既知の列・型・NULL条件・主キーを基準とします。追加のテーブル・view・trigger・独自index、未知の列や版、SQLiteでないファイルは拒否し、初期化や旧形式へのfallbackを行いません。過去版の `group_name` と `password_changed_at` の欠落は受け付け、読み書きの接続を開いた後にIMMEDIATE transactionの中で再検査してから追加します。途中で失敗したときは列の追加全体を巻き戻し、暗号文を保持します。新規ファイルは排他的に作成して上書きを防ぎます。初期化に失敗して残った空ファイルは自動で削除せず、次に開くときに再検査します。

形式判定は構造の検査であり、データの暗号認証・完全性の検査ではありません。WALの内容もSQLiteを通して検査し、主ファイルだけのコピーや `immutable` で補助ファイルを無視しません。SQLiteは読取専用の接続でもWAL用の補助ファイルを作る場合があるので、ファイルシステムが全く変わらないことは保証しません（[SQLiteの読取専用WAL条件](https://www.sqlite.org/wal.html#read_only_databases)）。読取専用で開けない場合は、読み書きの接続に切り替えて進めず停止します。原本と補助ファイルを保持し、対応する版での正常終了・復旧を確認してください。

保管庫の接続は1つのプロセスだけが持ちます。同じ保存先での2つ目の起動は[多重起動の防止](#デスクトップのos対応)で止めます。legacyの接続はv2保存層・移行のpointerを扱いません。既存DBのKDF・鍵・暗号文と `.cvault` v1は維持します。

### v2保存層

`v2.rs` は指定したファイルだけを扱い、環境変数や現在の保存先を参照しません。スキーマは `application_id = 0x43563200`、`user_version = 1`・`2`・`3` のいずれかで識別します。新規作成・ログインだけの移行先は1を維持し、最初のAPIキー・カードの保存または復元と同じtransactionで2へ、最初の銀行/証券の保存または復元と同じtransactionで3へ進めます。この値は上げるだけで、項目の削除後や下位の種類を保存した後も下げません。未対応の旧版はより大きい値を起動時に拒否するため、対応版で利用してください。特に3へ進んだ保管庫はv0.5.0以前では開けず、元に戻す手段はありません。これは暗号envelopeの `cryptoVersion = 2` とは別の版です。STRICTな3テーブルのDDL・制約を固定し、開くときに既知のDDL・単一のheader・期待するID・slot・nonceの件数と使用回数の一致を検証します。未知の形式や制約の変更、追加のオブジェクトでは初期化・修復・fallbackを行いません。

- 新規作成は、存在する親フォルダの中に排他的に行い、既存のファイルや空のファイルを上書きしない。
- 開くときは、期待するvaultId・keyIdと照合する。書き込み用に開いたときも、transactionの中で形式を検査し直す。
- 読み出しは、呼び出す側から受け取ったroot鍵で認証・復号する。保存層はroot鍵を保持しない。
- 復元は空の保管庫だけに全件を行う。全入力を検査してからnonceを予約し、暗号化した後に1つのtransactionで保存する。
- 削除は、revisionが一致するときに暗号文を除き、IDと最後のrevisionを削除の記録（tombstone）として残す。

`vault_header` は期待するID・password slot・使用回数、`vault_entries` はentry ID・revision・暗号envelopeまたはtombstone、`vault_nonces` はkey ID・12 byteのIV・entry ID・revisionを持ちます。サービス名・ログインID・password・メモ・URL・タグ・グループ・日時はentryの暗号文の内側に入ります。ID・revision・件数・削除履歴や暗号slotの情報は秘匿の対象に含みません。

書き込みでは、先にnonceの一意な予約と使用回数の加算を1つのIMMEDIATE transactionでcommitし、その後に暗号化して、別のtransactionでentryを保存します。予約はcommitしてから使うので、entryの保存の失敗・取消・削除・プロセスの終了で予約を巻き戻しません。衝突したときだけ再試行し、衝突した分の回数は加算しません。使用回数は保存できたentryの数ではなく消費した予約の数で、同じ鍵で2^20回に達したら新規の暗号化を止め、新しいrootへの再暗号化（[鍵更新](#v2の鍵更新と安全なリセット)）を求めます。暗号文のない予約も削除・再利用せず、回数をリセットする経路はありません。

書き込みの接続はDELETE journal、`synchronous=EXTRA`、外部キー制約、`secure_delete`、`trusted_schema=OFF` を使います。[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)に依存するもので、任意のファイルシステム・デバイスでの電源断への耐性とは区別します。実際の電源断は検証していません。初期化に失敗して残ったファイルも黙って上書きしません。

新規のentryはrevision 1、以後は保存済みのrevision+1だけを受け付けます。削除後もこの連番と予約を保持し、競合したときは元のentryを守り、新しい予約は消費済みのまま残します。有効なentryは10000件までで、上限に達しても既存のentryの更新・削除はできます。

新規作成に渡すslotは、新しいUUIDとCSPRNGで作った新しいrootから作ります。既存のslotを別のDBへコピーして書き込みを再開する使い方はしません。JSONの形式検査を暗号認証の代わりにしません。DB全体・nonce表・回数を一緒に巻き戻す攻撃は検出できないため、生のDBのコピーやsnapshotを書き込み用に再開しません。従来形式からの移行は[移行](#従来形式からv2への移行)を経て、新しいrootと全件の照合を必要とします。

### 通常起動とv2サービス

秘密を扱う操作と保存の前に、選択情報と保存先のパスの条件を検査し直します。legacyを選んでいる間に切替の記録が現れた場合も、その接続での操作を止めます。legacyへの書き込みは、SQLiteの書き込みロックを取ってから選択情報を確かめるので、pointerを保存した後に原本へ書き込むことはありません。この保護は保管庫の接続に限られ、旧版のアプリや別のプログラムによる原本の編集は防ぎません。破損・準備中・欠落のある選択情報を、legacyで補いません。

画面のコマンドは形式によらず同じで、v2では種類別のentryを扱います。v2の解除も共通の解除制御（`unlock_guard.rs`）を通り、誤パスワードの試行待機と同時実行の拒否を適用します。保存されたslotを開いた後、全entryを期待するID・revisionで認証してからroot鍵をセッションへ設定します。KDFの後と読み取りの途中で世代を検査し、ロック・リセット要求の後に古い解除結果でセッションを戻しません。slotの認証失敗は誤パスワードと区別できないため401です。root鍵を得た後のentryの認証や選択情報の不正では鍵を破棄して503とし、再起動・復旧を求めます。

一覧も解除後に全項目を復号してsummaryだけを返し、password・notes・URLを含めません。平文の永続的なindexや、ロック後も残るcacheは持ちません。長文・null・空文字・タグ順序は読み取りとバックアップで維持し、新規の編集時だけ既存の入力上限とtrimの方針を適用します。不正なUnicodeはnonceの予約前に拒否します。更新では作成日を維持し、passwordが変わらなければ不明な変更日もnullのまま保持します。

v2へのv1・v2バックアップの復元は、10000件・11 MiBの既存の上限と全項目の検査を通し、空の保管庫に限ります。各nonceを先にcommitして暗号化した後、1つのtransactionで全entryを保存します。保存・取消の失敗では登録した行をすべて巻き戻し、使用済みのnonceと回数は保持します。削除済みIDの復元はtombstoneの次のrevisionを使います。最後のtransactionの中でもセッションと選択情報を検査します。監査も同じ復号の経路を使い、結果に秘密を含めません。

鍵の2^20回の使用上限に達すると、新規の暗号化を409で止め、既存entryの読み取り・書き出しは続けられます。通常のv2初期化要求はセッションと未完了の処理を失効させたうえで409を返し、DB・root・nonce履歴・pointerを変えません。鍵更新・リセット・移行・復旧は[保管庫の管理](#保管庫の管理サービスと復旧専用起動)から行います。

### 暗号化バックアップ（`.cvault`）

`.cvault` の作成と読み込みは `backup.rs` にあります。ログインだけの書き出しはv1、APIキー・カードを含む書き出しはv2、銀行/証券を含む書き出しはv3を使用します。旧版が未対応のファイルと判定できるよう版を分けており、v3はv0.5.0以前では復元できません。legacyへの種類別バックアップの復元は書き込み前に拒否し、全項目を暗号化するv2への移行を求めます。

解錠中に全エントリを版付きJSONへ変換し、専用パスフレーズから導出した鍵で全項目を暗号化した `.cvault` を生成します。DBやマスターパスワードの検証値は含めません。

- 外側のJSON: `format = CIPHER-VAULT`、`version`（1〜3）、`kdf = scrypt-N131072-r8-p1`、`cipher = aes-256-gcm`、Base64の `salt` / `iv` / `tag` / `data`。
- 毎回16 byteのSaltと12 byteのIVを生成する。scrypt（N=131072、r=8、p=1）で32 byteの鍵を導出し、AES-256-GCMと16 byteの認証タグで改ざんを検出する。
- `CIPHER-VAULT:<version>:scrypt-N131072-r8-p1:aes-256-gcm` を追加認証データ（AAD）とし、外側と復号したpayloadの版も照合する。既存v1のAADは変えず、固定の形式・暗号パラメータを検証する。未知の版やファイルが指定する任意のKDFパラメータは受け付けない。
- パスフレーズは12〜1024文字。ファイルは16 MiB、暗号化前の内容は11 MiB、エントリは10000件まで。展開を伴う圧縮は使わない。
- 復元先はマスターパスワード設定済み・解錠中・エントリ0件の保管庫に限る。全件の認証・形式・ID・日時・項目を検証した後、現在の保管庫鍵で暗号化し直し、1つのトランザクションで保存する。書き込みに失敗したときは全件を巻き戻す。
- バックアップと復元の多重実行を拒否する。鍵導出中にロック・リセット・再解除された場合はセッションの変更を検出して中止する。
- 平文の一時ファイルを作らず、鍵と平文を処理後にゼロ埋めする。プロセスのメモリ全体の消去は保証しない。パスフレーズとバックアップの内容をログに出さない。

画面は `backup_export` / `backup_restore` コマンドを使います。保存は、画面が `.cvault` の暗号文をBlobのリンクにして保存する流れのまま、ウィンドウがWindowsの保存ダイアログ（`rfd`）を出して保存先を決めます。キャンセルすると保存しません。保存できるのは同梱の画面が作ったBlob（`blob:http://tauri.localhost/…`）だけで、それ以外のダウンロードはすべて拒否します。読込はファイル選択を使い、内容をコマンドへ渡します。

### 従来形式からv2への移行

従来形式（legacy）の保管庫は、管理画面から全項目を暗号化するv2へ移行できます（`maintenance/migration.rs`）。移行は次の2段階で行い、原本の `password-manager.db` は変更しません。

1. 準備: 原本を検査し、`vaults/<vaultId>/` に新しいv2の保管庫と復旧用のファイルを作って、すべて読み戻して照合する。
2. 切替: 両方のDBの書き込みロックを取り直して準備したファイルを再検証し、受領記録とpointerを書いて新しい保管庫を選ぶ。

原本は、通常の一覧と違って内容を信用せずに読みます（`maintenance/legacy_source.rs`）。旧形式の生鍵の検証値とHMACの検証値の両方を旧profileで認証し、Salt文字列をバイト列へ読み替えません。未追加の `group_name` と `password_changed_at` はNULLとして読み、原本に列を追加しません。nullableな旧URL・メモは従来どおり空文字、グループ・変更日不明はnullとし、それ以外の文字列・空白・Unicode表現・タグ順序・長文は維持します。文字列は厳密にUTF-8として読み、格納型・タグJSON・ID・日時・canonical Base64・暗号認証を確かめ、不正な値を置き換え・正規化・切り詰めずに拒否します。未知のschema・KDF項目・encodingでは停止します。上限は、entryが10000件、v1 JSONの平文が11 MiB、ファイルが16 MiB、全列の合計が32 MiB、metadataの合計が8192 byteです。新規編集の項目別の上限は旧値に適用しません。

#### 準備

新しいマスターパスワードは12文字以上で、旧マスターパスワードと異なり、確認入力と完全に一致する必要があります。文字列をtrim・正規化しません。

原本は最初に読取専用で形式・metadata・容量を検査し、その後に別の読み書きの接続で `BEGIN IMMEDIATE` を保持して、他の接続・プロセスの書き込みを止めます。原本のデータ・schemaを変えるSQLは実行せず、最後は必ずROLLBACKします。WALでは読取専用の接続の `BEGIN IMMEDIATE` だけでは書き込みを止められないため、読み書きの接続を使います。SQLiteの補助ファイルの更新や、OSの権限を持つ相手によるファイルの直接の置換は防げません。

保存先の `vaults` の下に、新しいUUIDのフォルダを排他的に作ります。

| ファイル | 内容と検証 |
|---|---|
| `<vaultId>/legacy.cvault` | 原本から作った暗号化v1バックアップ。排他作成・fsync・close後に実ファイルを読み、別の鍵のメモリ内の保管庫へ復元して全項目を照合 |
| `<vaultId>/legacy.sqlite` | 別の読取接続から[SQLite Backup API](https://www.sqlite.org/backup.html)で取得。WALの確定済みの更新を含め、保存先だけをDELETE journalへ変えてclose・fsync。読み直してquick_check・metadata・旧列・全項目を照合 |
| `<vaultId>/vault.sqlite` | 新しいvaultId・keyId・CSPRNGのrootと新しいマスターパスワードから作るv2のDB。v2保存層のnonceの先行予約で全項目を暗号化し直す |
| `<vaultId>/v2-export.cvault` | 開き直したv2のDBから読み戻した全件のv1 export。保存・fsync後、別の鍵のメモリ内の保管庫へ実際に復元して原本の項目と比べる |

SQLiteの論理ページ量は64 MiBまでとし、行が少なくても超えるDBは容量超過で停止します。VACUUMなどで原本を補正しません。新しいDBは閉じてfsyncし、読取専用で開き直した後、保存したslotを新しいマスターパスワードで認証して、生成時のrootと照合します。旧マスターパスワードでの解除の拒否、旧データ鍵による各entryの認証失敗、件数・全項目・revision・暗号化回数も確かめます。

失敗・取消・改ざん・不一致では成功を返しません。作ったファイルは失敗しても自動では削除・上書きしません。特に `legacy.sqlite` は旧形式の平文のmetadataを含むので、保存先は保護された場所にしてください。未完了の `vault.sqlite` を再開せず、やり直しは新しいUUIDと新しいrootで最初から行います。ファイルが揃っていることだけでは検証済みとみなさず、完了のマーカーは作りません。

#### 切替

開始前と各段階で、セッションの解除状態・世代・無操作期限を確認します。旧マスターパスワードを再認証し、導出した旧鍵がそのセッションの鍵と一致することも確かめます。終了時は自分が使った世代のセッションだけをロックし、後から解除された別の世代をロックしません。

原本と新しいv2のDBの両方で `BEGIN IMMEDIATE` を保持し、別の書き込みを止めます。準備の結果を信用せず、現在の原本、保存したlegacyのバックアップ、SQLiteのsnapshot、v2のDB、v2からのv1 exportを読み直し、metadata・旧列・全項目・件数・revision 1・暗号化回数、新しいマスターパスワードの認証、旧マスターパスワード・旧鍵の拒否、別の鍵のメモリ内の保管庫へのバックアップの復元を確かめ直します。準備の後に原本や新しいDBが更新されていれば停止し、どちらのDBも変えません。

pointerは `vault-current.json` に限り、内容は `{ "format": "CIPHER-VAULT-ACTIVE", "version": 1, "vaultId": "<UUID>" }` だけです。準備・完了を記録する `vault-activation.json` は `{ "format": "CIPHER-VAULT-ACTIVATION", "version": 1, "vaultId": "<UUID>", "keyId": "<UUID>", "entryCount": 0, "state": "prepared" }` の形で、最後にstateを `committed` へ変えます。entryCountは切替時点の件数です。両方のJSONは512 byteまでのBOM・改行なしのcanonical JSONとし、未知の項目、重複したキー、未知の版、不正なUUIDを拒否します。受領記録は暗号的な認可やrollbackの検出の証明ではありません。

保存先のパスは、dataフォルダの実際のパスと検証したUUIDから組み立て、相対パスや任意のファイルパスをJSONから受け取りません（`files.rs`）。dataフォルダの中の各要素で、symlink・junction、別のボリュームへの逸脱、通常ファイルのhard linkを拒否します。OSの権限を持つ相手が検査の間にファイルを直接置き換える攻撃や、dataフォルダ全体のrollbackは防げません。

切替は次の順序で行います。複数のJSONを1つの原子的なtransactionとは扱いません。

1. 復旧用のファイルとv2のDBをfsyncする。
2. 同じdataフォルダの中に新しい一時ファイルを排他的に作り、準備の記録をwrite・fsync・closeしてから `vault-activation.json` へrenameする。
3. 同様にpointerを一時ファイルへwrite・fsync・closeし、世代と保存先を確かめ直してから `vault-current.json` へrenameする。pointerを開き直してfsyncし、読み直す。
4. 完了の記録を別の一時ファイルから `vault-activation.json` へ置き換え、fsyncして読み直す。

起動時の判定（`selection.rs`）は読取専用です。transitionがなく、pointerと受領記録の両方がない場合だけlegacyを選び、両方が対応して完了していて、v2の形式を検査できた場合にv2を選びます。片方の欠落・準備中・破損・パスの逸脱・未知のDBでは旧DBへfallbackせず、復旧を求めます。選択の結果に復号の鍵は含まないので、全暗号文の認証は解除・読み取りの処理でも行います。

移行の復旧は、有効な受領記録と記録された対象が一致する場合に限り、同じ移行先を全件再検証してpointerを保存し直します。不正なpointerのバイト列は別の排他作成ファイルに残し、有効だが別のvaultIdを指すpointerは置き換えません。破損した受領記録から対象を推測せず停止します。DBの上書き・旧DBへの転記・nonceのリセット・未完了の書き込みの再開は行いません。

移行後のv2の通常の編集は保管庫の選択を妨げませんが、旧データとの一致を前提とするこの復旧では、移行後に編集されたv2を復旧できません。原本とsnapshot、失敗した一時ファイルは自動で削除しません。準備の記録を作る前の失敗ではlegacyの選択を維持し、記録がある段階でのエラーは、切替が起きた可能性を含めて復旧を求めます。完了の記録まで保存された直後にプロセスが終わった場合はv2を選び、応答がなかったことだけを理由に旧DBへ戻しません。

Windowsではフォルダをfsyncできないので、ファイルのfsyncとrenameだけで書き込みを確定させます（`maintenance/state_files.rs`）。実際の電源断や親フォルダの永続化は確かめていません（[Windowsのrename実装](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c)も参照）。

移行・鍵更新・復旧では、ハッシュの照合やflushのために開いたファイルを、SQLiteの接続を閉じるまで開いたままにします（`state_files.rs` の `Retained`）。POSIXでは同じファイルの記述子を1つ閉じるだけで、同じプロセスのSQLiteのロックが外れることがあるためです（[SQLiteの説明](https://www.sqlite.org/howtocorrupt.html#posix_close_bug)）。取消・異常時も接続を片付けた後に閉じ、閉じるのに失敗したときは成功を返さず復旧を求めます。

### v2の鍵更新と安全なリセット

選択中のv2から、別のUUID・別のrootを持つv2へ切り替えます（`maintenance/replacement.rs`）。鍵更新（rekey）は全項目を新しいrootと新しいマスターパスワードで暗号化し直し、リセット（reset）は新しい空の保管庫にします。どちらも旧保管庫はそのまま残します。開始時に通常の接続を閉じ、処理中に通常の接続が開かれた場合も停止します。

旧マスターパスワードの再認証とセッションの鍵との一致を必須とし、新しいマスターパスワードは12文字以上・旧マスターパスワードと異なる値・確認入力との完全な一致を求めます。リセットではさらに `confirmation: "RESET_ALL_DATA"` が必要です。リセットは復旧用のデータを残して新しい空の保管庫へ切り替える操作で、旧マスターパスワードを忘れた場合の回避や安全な消去の保証ではありません。旧マスターパスワードの認証は共通の解除制御を使います。全体を同時に1件だけ実行し、実行中のscryptは中断せず、終了時は自分が使った世代のセッションだけをロックします。

新しいUUIDの `vaults/<targetVaultId>/` を排他的に作ります。`source.sqlite` はSQLite Backup APIによる退避、`source.cvault` と `target.cvault` はv1の暗号化バックアップ、`source-pointer.json` と `source-receipt.json` は旧選択情報、`vault.sqlite` は新しい保管庫です。旧DBを読取専用で検査してからIMMEDIATEのロックを保持し、新しいDBも作成後に別のIMMEDIATEのロックで固定します。元のDBとnonceの履歴を変えず、失敗したフォルダを再利用しません。生のDBやsnapshotを書き込み用に再開せず、復元には全件を新しいrootで暗号化し直す経路を使います。

退避するDBは512 MiBまでで、2^20件の使用済みnonceがあるDBも対象です。全項目に従来の10000件・11 MiBのバックアップの上限を適用し、切り詰めません。旧マスターパスワードで全entryを認証し、保存したsourceのバックアップを別の鍵のメモリ内の保管庫へ復元して照合します。snapshotのslot・root・全項目・使用回数も確かめ直します。鍵更新では全項目を新しいrootでrevision 1から暗号化し直し、リセットでは新しいrootの空のDBを作ります。新しい使用回数は、鍵更新では件数、リセットでは0です。新しいDBをclose・fsyncして再検査し、新しいマスターパスワードでの解除、旧マスターパスワード・旧rootの拒否、全項目・revision・使用回数、targetのバックアップの独立した復元を照合してから切り替えます。

1. 復旧用のファイルをfsyncする。
2. `vault-transition.json` を同じdataフォルダの排他的な一時ファイルへwrite・fsync・closeした後にrenameする。mode・旧/新のcontext・件数・旧使用回数と、旧DB・snapshot・両方のバックアップ・旧選択情報・新しいDBのSHA-256を記録する。4096 byteまでの厳密なJSONとする。
3. 従来の形式の受領記録を新しいcontextの `prepared`、pointerを新しいvaultId、受領記録を `committed` の順に、それぞれ一時ファイルとrenameで保存・同期・読み直しする。
4. transitionを新しいフォルダの `replacement.json` へrenameして同期する。

複数のファイルを1つのtransactionとは扱いません。transitionがある間は、pointerと受領記録の状態にかかわらず起動を復旧専用の状態にし、実行中の接続も失効させます。両方の選択情報が欠けていてもlegacyへfallbackしません。transitionを保存する前の失敗では旧選択を維持し、保存された可能性がある段階では自動でrollbackせず、復旧を求めます。最後のrenameの後に応答や同期が失敗した場合は、すでに新しい保管庫が選ばれている可能性があるため、応答がなかったことだけを理由に旧DBへ戻してはいけません。SHA-256と署名のない記録は変更の検出用で、認可・改ざん耐性・dataフォルダ全体のrollbackの検出を保証するものではありません。

中断した鍵更新・リセットの復旧は、transitionに書かれた旧・新の保管庫を既知の対象と照合し、両方のマスターパスワードと旧セッションを再認証します。全ファイルの記録済みのハッシュ、snapshot・全項目・使用回数・両方のバックアップの独立した復元を確かめ直してから、切替を完了させます。entryの暗号化・DBの上書き・nonceのリセットを行わず、旧DBまたは新しいDBが編集されていれば停止します。不正なpointer・受領記録は、512 byte以下の安全な通常ファイルに限り、元のバイト列をBase64で別の排他作成ファイルへ残してから置き換えます。有効な別の保管庫への選択情報や、破損したtransitionから対象を推測して置き換えません。

元のDB、復旧用のファイル、失敗した移行先・一時ファイルは自動で削除しません。パス・linkの条件、OSの権限を持つ相手に対する制約、Windowsではフォルダをfsyncできないことは、上記の[切替](#切替)と同じです。

### 保管庫の管理サービスと復旧専用起動

移行・鍵更新・リセット・中断後の復旧は、`maintenance/` と `vault/switch.rs` が通常の保管庫の接続と調停します。保存先・UUID・暗号のcontextは画面から受け取らず、保存先の記録から決めます。通常のv2・legacyの操作と解除は通常の接続を使います。

`VaultStatus.maintenance` は `{ state: "ready" | "running" | "recovery-required", format: "legacy" | "v2" | "unknown", operation?, recoveryOperation?, sourceSessionId? }` です。鍵・項目・ファイルパスを含めません。起動時に既知のtransition、または再検査できるlegacyの移行の受領記録が見つかった場合は、保管庫の接続を開かず、復旧専用の状態で画面を起動します。通常の解除・初期化を拒否し、復旧だけを受け付けます。未知の形式・不正な記録を正常な保管庫として開きません。復旧の対象を特定できない場合は、すべての操作を拒否する復旧待ちの状態で開きます（[Electron版との違い](#electron版との違い)）。

操作は画面のAPIの `runVaultMaintenance(payload, sessionId)`（`vault_maintenance` コマンド）です。payloadは共有型 `VaultMaintenancePayload` に定義し、`operation` は `migrate` / `rekey` / `reset` / `recover`、認証の項目は `masterPassword`、`newMasterPassword`、`confirmNewMasterPassword`、`backupPassphrase` です。新規の操作は `confirmBackupPassphrase` の一致も必須で、リセットとリセットの復旧は `confirmation: "RESET_ALL_DATA"` を求めます。recoverの対象は保存先の記録から決めます。その他の未知の項目を拒否します。入力の文字・byteの上限と、パスワードを正規化しない条件は、中核の他の入力と共通です。

コマンドはOSの状態・世代の検査を通ります。通常の操作は解除済みの現世代だけに許可し、復旧専用の起動ではロック済みの現世代と旧マスターパスワードの再認証を必要とします。全操作を同時に1件に限り、旧マスターパスワードの認証は共通の試行制限を使います。秘密を取り出すための外部の入口は追加しません。

開始時に通常のセッションの鍵を独立した操作用のセッションへ引き継ぎ、通常の接続を閉じて、鍵と古い要求を失効させます。操作用のセッションにも5分の失効条件があります。手動ロック、OSイベント、画面の喪失、終了では操作を取り消し、実行中のscryptが終わるまで実行枠を保持します。途中の取消を、すでに確定した切替のrollbackとして扱いません。すべての終了経路で一時的な鍵を消去し、通常の接続が勝手に開き直されていないことを確かめます。

処理の後は選択情報を検査して明示的に開き直し、成功したときも必ずロック状態へ戻します。失敗する前の選択がv2だった場合、選択情報の欠落をlegacyで補いません。新しいDBやschemaを自動で作って再開することもありません。再検証できなければ、接続を閉じた復旧状態を維持します。停止中は開き直しません。終了時に取消と後片付けを待てなかった場合は、プロセスの終了と同じ復旧の条件を適用します。

画面は操作の開始時に秘密の表示を消し、処理中の世代の変更を受け入れた後に状態を読み直します。最終状態を確認できない場合に成功を表示せず、古い操作結果で新しい画面を上書きしません。入力は4 MiBまでとし、旧・新・確認の複数のパスワードが通常の解除の入力条件に収まる場合も送信できます。新しいマスターパスワードにも通常の解除と同じ入力検証を使い、設定後に通常の解除ができない入力を切替の前に拒否します。実際の電源断は確かめていません。

管理画面は通常時に「ツール」から開き、中断時は通常の解除画面を表示せず自動的に開きます。開始・閉鎖・セッションの変更時に認証の入力を消し、進行中は編集フォームを表示しません。完了後も管理画面を残し、新しいマスターパスワードでの再解除を案内します。初期化は元のデータを残す空の保管庫への切替で、旧パスワードを知らない場合の完全なリセットとは分けています。従来形式の読み取り・移行では、新規作成時の12文字の制約を旧マスターパスワードへ追加しません。

取消は公開状態の `sourceSessionId` と操作開始時のセッションを照合し、開始前の要求または自分の進行中の操作だけにロックを送ります。この値は秘密や追加の認可tokenではなく、取消の対象が新しいかを確かめるための値です。後続の別の操作・解除を古い画面からロックせず、送信直前の現世代も中核の側で照合します。画面の破棄時にも自分の処理だけに取消を求めます。データを守るため、復旧中と処理中はEscapeで画面を閉じません。

### ローカル監査

`audit.rs` が解錠中だけ解析し、画面には件数・対象ID・サービス名・ログインID・理由だけを返します。パスワード、メモ、強度推定器の生の結果は返しません。外部の漏えい照会やURLへのアクセスは行いません。解析中は定期的にセッションを確かめ、ロック・セッションの変更時に中止します。結果は解析開始時点のスナップショットです。

| 項目 | 判定 |
|---|---|
| 弱いパスワード | `zxcvbn` クレートの評価0〜2。サービス名・ログインIDも辞書に加える。強度推定は先頭100文字まで。Electron版のzxcvbn-ts v4との違いは[Electron版との違い](#electron版との違い)を参照 |
| 重複パスワード | 文字列の完全一致。同じ値を使う全件を対象にする |
| 古いパスワード | `password_changed_at` から365日以上 |
| URLなし | URLが空欄 |
| 長期間更新なし | `updated_at` から365日以上 |

スコアは `round(100 - (弱い件数 * 60 + 重複件数 * 40) / 全件数)`。0件は未採点。古さ・URL未登録・長期間更新なしは見直し項目として表示し、減点しません。スコアは製品独自の目安であり、NIST等の認証や安全性保証を意味しません。辞書に含まれない言語・パターンの推定には限界があります。

`password_entries.password_changed_at` をNULL許容で追加します。既存レコードはNULL（変更日不明）を保持し、新規作成またはパスワード自体が変わったときだけ記録します。メモだけの編集では更新しません。既存の保管庫鍵・検証値・暗号文は変更しません。v0.2.1以前は新しい日時を更新しないため、旧版で編集した後のパスワード年齢は信頼できません。`.cvault` はv0.2.2以降が対象です。

画面は `vault_audit` コマンドを使用します。

### `vault_metadata`

保管庫の検証情報を `id = 1` の1行で保持します。

| カラム | 内容 |
|---|---|
| `password_salt` | 鍵導出用Salt |
| `password_verifier` | マスターパスワードの検証器 |
| `kdf_params` | KDFパラメータ |
| `created_at`, `updated_at` | 作成・更新日時 |

### `password_entries`

| カラム | 内容 | 保存形式 |
|---|---|---|
| `service_name`, `login_id` | サービス名、ログインID | 平文 |
| `encrypted_password`, `encrypted_notes` | パスワード、メモ | AES-256-GCM |
| `url`, `tags`, `group_name` | URL、タグ、グループ | 平文 |
| `created_at`, `updated_at` | 作成・更新日時 | 平文 |
| `password_changed_at` | パスワード変更日時（旧データはNULL） | 平文 |

## 画面から呼べるコマンド

画面のAPI（`window.passwordManager`）と、それが呼ぶコマンドの対応です。コマンドは `apps/desktop/build.rs` の一覧と `tauri.conf.json` の `capabilities` の両方に書きます。

| 画面のAPI | コマンド | 用途 |
|---|---|---|
| `fetchVaultStatus` | `vault_status` | 保管庫状態取得 |
| `recordVaultActivity` | `vault_activity` | 現在の画面での操作を通知し、期限内の場合だけ無操作期限を延長 |
| `setupVault` / `unlockVault` / `lockVault` | `vault_setup` / `vault_unlock` / `vault_lock` | 初期設定・ロック解除・ロック |
| `resetVault` | `vault_reset` | 保管庫の完全リセット |
| `runVaultMaintenance` | `vault_maintenance` | 移行・鍵更新・安全なリセット・中断後の明示復旧 |
| `exportBackup` / `restoreBackup` | `backup_export` / `backup_restore` | 暗号化バックアップの書き出し・空の保管庫への復元 |
| `auditVault` | `vault_audit` | ローカルでのパスワードの点検 |
| `fetchEntries` / `fetchEntry` | `entries_list` / `entries_get` | エントリ一覧・詳細 |
| `createEntry` / `updateEntry` / `deleteEntry` | `entries_create` / `entries_update` / `entries_delete` | エントリ作成・更新・削除 |
| `setEntriesGroup` | `entries_set_group` | 複数エントリのグループ変更（`ids` と `group`、`null` で解除） |
| `generatePassword` | `password_generate` | パスワード生成 |
| `copyText` | `clipboard_write` | 30秒で消えるコピー |
| `getUpdateState` / `checkForUpdates` / `downloadUpdate` / `installUpdate` / `openReleasePage` | `update_state` / `update_check` / `update_download` / `update_install` / `update_open_releases` | 手動更新と配布ページ |
| `minimizeWindow` / `toggleMaximizeWindow` / `closeWindow` / `isWindowMaximized` | Tauri本体の `plugin:window|minimize` / `toggle_maximize` / `close` / `is_maximized` | タイトルバーのウィンドウ操作（保管庫には触れない） |

ウィンドウはWindows標準の枠とタイトルバーを持たず、画面のメニューの列がタイトルバーを兼ねます（v1.0.0から。Electron版と同じ1段の構成）。右端の最小化・最大化・閉じるのボタンは画面が描き、上の4つのAPIでTauri本体のコマンドを呼びます。列の空いた部分はTauriの `data-tauri-drag-region` でドラッグ移動とダブルクリックでの最大化ができ、これには `start_dragging` と `internal_toggle_maximize` を許可しています。これらはアプリのコマンドではないので `build.rs` の一覧には書かず、`tauri.conf.json` の `capabilities` に `core:window:allow-…` として個別に書きます。閉じるボタンも通常の終了と同じく、ウィンドウの破棄で保管庫をロックしてコピーを消します。自前のボタンなので、最大化ボタンに重ねたときのスナップレイアウトの候補は出ません（画面端へのドラッグとWin+Zは使えます）。

ダイアログ（バックアップ、パスワードの点検、バージョンと更新、保管庫の管理、グループ）は `showModal()` ではなく `show()` で開きます（`apps/web/src/lib/modal.ts`）。`showModal()` は画面のほかの部分をすべて操作できなくするので、タイトルバーのボタンとドラッグも使えなくなるためです。代わりに、ダイアログとタイトルバー以外の部分とメニューの列に `inert` を付けて操作できなくし、Escapeではダイアログへ取り消し可能な `cancel` イベントを送って、`showModal()` と同じ閉じ方の規則を保ちます。

保管庫の操作は、状態取得を除いて画面が持つセッションIDを引数に取ります。エントリ操作、バックアップ、復元、監査は保管庫の解錠を必要とします。一覧の結果にはパスワードとメモを含めず、詳細取得時だけ復号します。

## フロントエンド

```text
起動 → 保管庫状態取得
  ├─ 未設定   → LockScreen（初期設定）
  ├─ ロック中 → LockScreen（ロック解除）
  └─ 解錠済み → VaultDashboard
```

`App.tsx` が保管庫状態、エントリ一覧、選択中エントリ、入力イベントの通知とロック状態の画面反映を管理します。自動ロックの強制は共通サービスの `VaultSession` が担当します。`AppMenu.tsx` が共通メニュー、`VaultDashboard.tsx` が検索・一覧・選択、`EntryEditor.tsx` が作成・編集の入力、`EntryContextMenu.tsx` が項目の右クリックメニュー、`GroupDialog.tsx` が新規グループの設定を担当します。デスクトップのAPIの呼び出しは `lib/api.ts`、世代を跨ぐ応答の拒否は `lib/vault-client-session.ts` が担当します。

作成と編集は共通の2列フォームを使い、グループ・タグ・メモを「追加情報」に折り畳みます。折り畳み状態にかかわらず入力値を保持して保存し、未保存の変更がある状態でエントリ選択・新規作成・手動ロック・グループ変更・別の項目の削除を行う場合は破棄を確認します。保存・削除は右ペイン下部に固定し、一覧・メモ・必要時の編集内容を独立してスクロールします。閲覧中の削除は右ペイン上部の編集ボタンの隣に置きます。詳細の各行は右ペインの幅いっぱいに伸ばして空白を残しません。デスクトップの初期サイズは880×780、最小サイズは780×680です。

一覧の項目は右クリックまたはメニューキーで「グループへ追加」「グループから削除」「項目削除」を開けます。右クリックでは選択を変えず、選択していない項目を削除しても右ペインの表示は維持します。ネイティブメニューではなく画面内のメニューにしているのは、Web版があった頃に同じ操作を提供するためで、今も画面だけで操作が完結するようにこの形を保っています。「新しいグループ」ダイアログはグループ名と対象項目を一度に指定でき、作成後は結果が見えるようにグループ別の表示へ切り替えます。

UIは「Black Ops Secure Terminal」をテーマとし、色・タイポグラフィ・CSSアニメーションの定義は `apps/web/src/styles.css` に集約します。選択ラインは一覧内の位置に追従し、詳細は選択した項目の上下方向に合わせて240msで表示します。メニュー・ダイアログも短い移動と拡大で開き、保存・コピーは成功後だけチェックと光の反応を表示します。

ツールのダイアログは、編集画面と同じラベル左寄せの行で組み、見出しは細いバーにして操作を読み物に見せないようにします。枠の大きさは状態が変わっても動かさず、最も内容の多い状態に合わせて固定します。安全のための注意書きは省かず、行の下やフッターへ小さく置きます。

デザインは「シンプル」（既定、上記テーマそのもの）と「ルミナス」（丸みと奥行き、背景・選択・主要ボタンの光）を「表示」メニューで切り替えます。ルミナスの光は3色を60秒かけて循環します。常時動くため更新は毎秒5回に抑え、OSの「動きを減らす」設定では止めます。`lib/design-mode.ts` が `<html data-design>` を設定し、`styles.css` はこの属性でシンプルの定義を上書きします。ロック画面にも適用するので、設定は保管庫の外にある `localStorage` にモード名だけを保存します。コマンドや保存処理を増やさないため画面の中だけで動きます。ルミナスでは、メニューの列（タイトルバー）にも背景の光を通し、一覧と詳細のパネルの枠を背景より明るい色と影で区別します。

詳細の切り替えでは、旧編集画面や画面のスナップショットを保持せず、新しい画面だけを動かします。ロック時の非表示をアニメーション待ちで遅らせません。OSの「動きを減らす」設定ではCSSの動きを抑え、詳細のアニメーションを省略します。表示途中で設定を変更した場合も詳細の動きを停止します。

## 手動更新とアプリ情報

`AppInfo.tsx` → `window.passwordManager` → `update_*` コマンド → `apps/desktop/src/updates.rs` → `tauri-plugin-updater` の順に処理します。画面に許すのは状態・確認・取得・適用・配布ページの5つの操作だけで、更新の取得先や引数を画面から変えられないようにしています。状態はメモリに保持し、画面が0.5秒ごとに問い合わせて受け取ります。

Windowsのsetup版で、手動の確認・取得・画面なしの適用と自動再起動に対応します。起動時確認・自動取得・通常終了時の適用は行いません。未保存の編集があるときは「編集に戻る」を既定のボタンにして確認し、保存中は適用を無効化します。適用の前に保管庫をロックしてコピーを消します。インストーラーを起動できなかったときは、終了の準備が済んだ後なので、保管庫をロックしたままアプリを終了します。インストーラーはアプリを起動し直すときに元の引数だけを渡し、環境変数は引き継ぎません。portable版と開発用のビルドは、Tauri CLIがsetupの中のexeにだけ書く印（bundle type）で見分け、配布ページへ案内します。操作・配布条件と検証は[手動更新とアイコン](手動更新とアイコン.md)を参照してください。

更新情報はGitHub Releasesの最新リリースに置く `latest.json` で、`npm run package:tauri` が署名と一緒に作ります。ダウンロードした更新は署名（minisign）を `tauri.conf.json` の公開鍵で確かめてから適用し、署名がない更新や公開鍵と合わない更新は適用しません。公開鍵が空の版はアプリ内で更新しません。

変更内容のHTMLは表示中のDOMへ挿入せず、`template` で解析して段落・箇条書きを残したテキストに変換します。スクリプト・画像・埋め込みを除き、Reactの文字表示でエスケープします。更新通信は保管庫と分離し、失敗しても保管庫を利用できます。

## Rust版の設計判断

v0.9.0で、デスクトップ版をElectronとNode.jsのサービス（better-sqlite3）から、Tauri 2とRustへ置き換えました。React画面（`apps/web`）は残し、`window.passwordManager` をTauri側の初期化スクリプトで用意しています。移行の間はTypeScriptのサービス層を正解とし、Rust版が同じ入力に同じ結果とエラー文言を返すことを、同じ入力を両方に与えて比べる差分試験で確かめました。v0.9.0の後にElectron版とNode.jsのサービスを削除したので、今はRust版が正解です。配布と検証の対象はWindowsだけです。

| 決定 | 理由 |
|---|---|
| 保管庫・`.cvault`・pointer・`user_version` の形式はElectron版と同じにする | Rust版に不具合があっても、利用者がElectron版（v0.8.0）へ戻れるようにするため。形式を変えるときは、Electron版で開けなくなることを含めて別途判断する |
| 保存先はElectronと同じ `%APPDATA%\CIPHER VAULT\data` に固定し、Tauriの既定の保存先は使わない | 保管庫を移動させずに引き継ぐため。Tauriの既定はidentifierの下になり、場所が変わる |
| identifierは `io.github.termnix-it.ciphervault` に固定する | WebView2の作業フォルダと更新の識別に使われ、配布後に変えると引き継げなくなるため |
| 暗号はRustCrypto（`aes-gcm`、`scrypt`、`hkdf`、`hmac`、`sha2`）と `zeroize`・`subtle` を使う | 既存形式に必要なscryptを含む全方式を、同じ系統の純Rustのライブラリでそろえられるため。`ring` はscryptを持たず、`openssl` はOpenSSLの同梱が必要になる。AESとGHASHはCPUの専用命令を使い、ない環境では定数時間の実装に切り替わる。固定ベクトルと、TypeScript版が書いたデータとの照合（v0.9.0まで）で互換を確認した |
| Web版（Node HTTPサーバー）はv0.9.0の後に廃止した | Tauriでは提供できず、HTTPの入口をなくすことで「保管庫を操作できるのは本人の画面操作だけ」という方針に近づくため |
| Electron版の利用者は、最終版で配布ページへ案内し、Tauri版のsetupで移行する | electron-updaterでTauri版のsetupを自動適用すると、インストール先とアンインストール情報が二重になるため。Tauri版のsetupは、インストールの前にElectron版をElectron版自身のアンインストーラーで削除する。このアンインストーラーは `%APPDATA%` の保管庫を消さない |
| バックアップの保存先は `rfd` の保存ダイアログで選ばせる | Electron版はChromiumの保存ダイアログで保存先を聞くが、WebView2はダウンロードフォルダへ黙って保存するため。`rfd` はWindowsの標準ダイアログを呼ぶだけの小さなライブラリ（MIT）で、Tauriの公式dialogプラグインも内部で使っている。プラグインにすると画面から呼べるコマンドが増えるので、ウィンドウ側の処理として組み込む |
| 監査の強度判定は `zxcvbn` クレート（MIT）を使い、zxcvbn-tsは移植しない | zxcvbn-tsを同じ判定になるよう移植すると約4000行と辞書の保守が必要になるため。合成パスワードで比べると、点数は約98%、「推測されやすい」の判定は約99.5%が一致する。判定の違いは下の表に挙げる |
| クリップボードはWin32のAPIを直接使い、Tauriのclipboardプラグインは使わない | プラグインは文字列などを書くだけで、Electron版と同じ所有マーカーや、クリップボード履歴・クラウド同期から外す指定を一緒に書けないため。直接使うと、照合と消去を同じ「開いている間」に行えるので、別のアプリが間に書き換えた内容を消さずに済む |
| 画面ロック・スリープの通知は、アプリの隠しウィンドウで受け取る | TauriはWindowsのこれらの通知を公開していないため。導入済みの `windows` クレートで受け取る |
| 多重起動は名前付きmutexで防ぎ、single-instanceプラグインは使わない | プラグインは保管庫を開いた後に判定するうえ、ほかのプロセスからメッセージを受け取る窓口を持つため。mutexなら保管庫を開く前に判定でき、2つ目のアプリは先のウィンドウを前面に出して何も送らずに終了する。名前は保存先フォルダから作るので、別の試験用フォルダとは干渉しない |
| portable版は単体のexeにする | Tauriには公式のportable形式がないため。WebView2の作業フォルダは `%LOCALAPPDATA%` に作られるが、Electron版portableも保管庫は `%APPDATA%` に置いており、使い方は変わらない |
| setupはTauri CLI（`@tauri-apps/cli`）のNSISで作り、利用者ごとのインストール（`currentUser`）にする | electron-builderはTauriのアプリを扱えないため。Electron版のsetupも利用者ごとのインストールで、管理者権限を求めない点を変えない。CLIはnpmの開発用依存として版を固定し、配布物には含まれない |
| 手動更新は `tauri-plugin-updater` をRustから呼び、プラグインが画面向けに用意するコマンドは許可しない | ダウンロードした更新を署名（minisign）で確かめてから適用し、署名がない更新や公開鍵と合わない更新を適用しないため。画面に許すのはElectron版と同じ5つの操作（状態、確認、取得、適用、配布ページ）だけにし、更新の取得先や引数を画面から変えられないようにする |
| 更新の公開鍵は `tauri.conf.json` に置き、秘密鍵はリポジトリにもCIにも置かない。公開鍵が空の版はアプリ内で更新しない | 秘密鍵が漏れると、利用者に任意のsetupを実行させられるため。秘密鍵とそのパスワードは公開する人の手元だけに置き、署名はリリースのときに手元で行う。試験は実行ごとに使い捨ての鍵を作る |
| アプリ内で更新するのはsetup版だけにし、Tauri CLIがsetupの中のexeにだけ書く印（bundle type）で見分ける | portable版を更新するとsetupがインストールされ、別の場所に2つ目のアプリができるため。Electron版も、portable・開発環境は配布ページへ案内している |

### Electron版からの移行

Electron版からの移行は、次の2つのリリースで行いました。

1. v0.8.0: Electron版の最終版。アプリ内更新を無効にし（`desktop-platform.ts` の `inAppUpdates: false`）、「バージョンと更新」で配布ページだけを案内する。それより前のsetup版は、アプリ内更新でこの版になる。v0.9.0以降のリリースにもこの版の `latest.yml`・setup・`.blockmap` を添付し続けるので、古いElectron版もこの版まで更新できる（[リリース手順](リリース手順.md#electron版向けの添付)）。
2. v0.9.0: 最初のRust版。setupは、インストールの前に `HKCU` と `HKLM` から、electron-builderがElectron版のappId（`com.lugep.ciphervault`）から作るアンインストール情報のキーだけを読み、そのアンインストーラーを画面なしで実行する（`apps/desktop/windows/installer-hooks.nsh`）。アンインストーラーはインストール先から動くプログラムを起動中のアプリとみなし、自分自身でも中止するため、electron-builderが旧版を削除するときと同じく、コピーから実行する。アンインストーラーはインストール先を丸ごと削除するので、Electron版が保管庫のフォルダかその上位にインストールされていたときは実行せず、手で削除するよう案内する。画面ありのsetupは、Electron版が起動していれば、編集中の内容を保存して終了するよう求め、終了するまで先へ進まない。アンインストールできなかったときは、インストールを続けたうえで、手で削除するよう案内する。

Electron版のportable版は登録されていないので、setupでは削除されません。不要になったexeは利用者が削除します。

### Electron版との違い

v0.9.0までの差分試験（`test:rust-parity`）で確認したうえで、次の違いは許容しています。

| 違い | 許容する理由 |
|---|---|
| 既存形式の暗号文が壊れているとき、Node版はOpenSSL由来の英語の文言を返すが、Rust版は「保存済みのデータを復号できませんでした」を返す | ライブラリ固有の文言は再現できないため。どちらも500で操作は失敗する |
| pointerだけが残っているなど、Node版が起動を拒否する未知の中断状態でも、Rust版は中断した処理の種類（`recoveryOperation`）を持たない復旧待ちの状態として開く | 画面は「復旧に必要な情報が見つかりません」と表示して復旧の入力欄を出さず、Rust版も保守を含むすべての操作を拒否して保管庫を変更しないため。起動に失敗するより、ファイルを残すよう案内できる |
| 監査で「推測されやすい」とする判定は、Rust版がzxcvbn-tsより少し甘い。Rust版は日付や単語の並びのパターンを持たず、先頭100文字だけを評価する（zxcvbn-tsは256文字）。例えば `dragonorange4797` はzxcvbn-tsで1点（推測されやすい）、Rust版で3点になる | 一致しないのは約0.5%で、点検は参考の表示であり保存や解除の可否に使わないため。ほかの判定（使い回し、1年以上変更なし、URLなし、1年以上更新なし）と点数の計算は同じで、差分試験は両方が同じ強度と判定するパスワードで行った |
| pointerなどの状態ファイルは、Rust版はアプリが書き出すキー順のものだけを受け付ける | アプリ自身は常に同じ順で書くため、手で並べ替えたファイルだけが復旧扱いになる |
| v2への書き込みが重なったとき、Rust版は登録件数の上限より先に競合として拒否する | どちらも失敗し、返す文言の優先順だけが違うため |
| Tauriのコマンド引数は `null` と省略を区別しないため、パスワード生成に `null` を渡すとRust版は既定値で生成し、Electron版は400を返す | 画面は `null` を渡さないため。中核（`crates/vault-core`）は両者を区別し、差分試験ではNode版と一致した |

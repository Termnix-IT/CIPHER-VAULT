# CIPHER VAULT 設計

## 設計方針

- ローカルファースト: 保管庫データは端末内の SQLite に保存する
- 単一ユーザー: マルチユーザー管理や外部認証を持たない
- UI と処理の分離: React UI から Web 版は HTTP、Electron 版は IPC で共通サービス層を呼び出す
- 依存関係を抑制: API は Node.js 標準 `http`、暗号処理は標準 `node:crypto` を使用する

## システム構成

```text
React UI
  ├─ Web: Fetch API → Node.js HTTP Router
  └─ Electron: preload → IPC handler
                         │
                         ▼
             共通サービス層
             ├─ Vault Service
             ├─ Entry Service
             ├─ Password Service
             └─ Crypto Service
                         │
                         ▼
                       SQLite
```

| パッケージ | 役割 |
|---|---|
| `apps/web` | React + Vite のユーザーインターフェース |
| `apps/api` | HTTP入口、SQLite、暗号化、保管庫・エントリ管理 |
| `apps/electron` | デスクトップウィンドウ、preload、IPC、クリップボード、手動更新 |
| `packages/shared` | Web・API・Electronで共有するTypeScript型と画面のCSP方針 |

Web版とElectron版の詳細な経路は[ワークフロー](ワークフロー/02-Web・ElectronからSQLiteまで.md)を参照してください。

## 実行経路

### Web版

開発時はViteのプロキシが `/vault`、`/entries`、`/password` を `127.0.0.1:3001` へ転送し、HostをAPIの接続先へ変更します。本番時はNode.js APIがビルド済みのWebアセットも配信します。

HTTP入口ではHostをループバックまたは `PASSWORD_MANAGER_API_HOST` のホスト名と待受ポートに限定します。Originがある場合はAPI自身または明示したWeb画面のOriginと一致することを要求し、Fetch Metadataの `cross-site` は拒否します。`POST` / `PUT` / `DELETE` は、本文の有無にかかわらず `Content-Type: application/json` と `X-Cipher-Vault-CSRF` が必要です。トークンは `GET /vault/csrf` で取得し、Node.jsプロセスの再起動時に変わります。Web画面は変更操作の直前に取得します。応答とトークンはキャッシュしません。

この対策は外部ページからの不正操作とDNS rebindingを防ぐためのもので、外部利用者の認証ではありません。APIは単一ユーザーのローカル利用を前提とし、インターネットや共有ネットワークへ公開しません。

`GET /vault/status` は `isConfigured`、`isUnlocked` に加え、プロセスの再起動・解除・ロックごとに変わる `sessionId`、`idleTimeoutMs`、必要に応じて `lockReason` を返します。`/health`、`/vault/status`、`/vault/csrf` と静的ファイル以外の保管庫APIには、その状態取得で得た `X-Cipher-Vault-Session` を付けます。解除・初期設定・リセットでも必要です。受信本文の待機中に世代が変わった操作は409で拒否し、古い解除要求が後から保管庫を開くことを防ぎます。この値は要求の鮮度を確認するためのもので、クライアント認証用の秘密ではありません。

### Electron版

`apps/web/src/lib/api.ts` が `window.passwordManager` の有無で実行環境を判定します。Electronでは `contextBridge` で公開したAPIからIPC handlerを経由し、APIと同じサービス層を直接呼び出します。

保管庫・エントリ・バックアップ・監査・クリップボード・更新のすべてのIPCで、送信者がメインウィンドウのメインフレームであり、送信フレームとウィンドウのURLが実際に読み込んだ画面URLと一致することを確認します。別のファイルや開発サーバー上の別ページも許可しません。フラグメント変更のみ許可します。外部ページへの画面遷移・リダイレクト、サブフレームの遷移、新規ウィンドウ、webviewの追加は拒否します。リリースページは固定URLをユーザー操作で外部ブラウザへ開きます。

データベースはElectronの `userData/data` 配下に保存します。Web/API版は既定で `apps/api/data` を使用します。

## 画面のsandboxとCSP

Electronは `sandbox: true`、`contextIsolation: true`、`nodeIntegration: false` で画面を実行します。[sandboxのpreload制約](https://www.electronjs.org/docs/latest/tutorial/sandbox)に合わせ、型検査後に既存のTypeScriptコンパイラで `preload.ts` を単一の `preload.cjs` へ変換します。実行時のimportはElectronだけとし、共有型は消去します。画面には限定した `window.passwordManager` APIだけを公開し、任意のIPCやNode.js APIは渡しません。IPCの送信元・世代・入力検証も引き続き必要です。

`packages/shared/src/renderer-policy.ts` でCSPを共有し、HTMLのmetaをViteで生成します。本番は同一オリジンのスクリプトだけを許可し、インラインスクリプトと `eval` を許可しません。`base`、frame、object、worker、フォーム送信も拒否します。Reactの既存表示で必要なstyle属性は許可し、本番のstyle要素・CSSファイルは同一オリジンに制限します。

| 実行環境 | CSPの適用と通信の範囲 |
|---|---|
| Web本番 | HTML metaとHTTPヘッダー。`connect-src 'self'` で同一オリジンのAPI通信を許可。HTTPヘッダーでは `frame-ancestors 'none'` と `X-Frame-Options: DENY` も設定 |
| Electron配布画面 | `file://` でも適用されるHTML metaに加え、sessionの要求検査でrendererの通信を制限。実在するWeb配布ディレクトリ内のHTML・JS・CSS・画像・フォントだけを読み込み、外部通信やfileのXHRを拒否。UNCとディレクトリ外への参照も拒否 |
| 開発画面 | localhost・127.0.0.1・IPv6ループバックのHTTP/HTTPSだけを許可。React Refresh用のインラインスクリプト、Vite用のstyle要素と現在のポートへのローカルWebSocketを許可。Electron sessionでは画面と同じoriginへの要求に限定 |

Electron sessionのHTTP応答には専用CSPも付けます。配布画面用は `connect-src 'none'` ですが、file応答ヘッダーへの依存を避け、上記metaと要求検査を併用します。画像のdata/BlobとバックアップのBlobダウンロードは許可します。開発時の例外を本番スクリプトの許可に含めません。

Electronのpermission check・request・device permissionはすべて拒否します。クリップボードは検証済みのmainプロセスAPIを経由します。手動更新の通信は `electron-updater` の専用sessionで行い、rendererの通信制限とは分離します。

Share Tech MonoとJetBrains Monoは `apps/web/public/fonts/` に原本とSIL Open Font License 1.1を同梱します。`sources.json` に固定した取得元revisionとSHA-256を記録し、Google Fontsへの通信は行いません。フォントを差し替える場合も利用条件とライセンス同梱を確認してください。

## 入力の検証と上限

HTTPとElectron IPCの保管庫操作は、サービス層から `apps/api/src/lib/input-validation.ts` の同じ実行時検証を呼びます。TypeScript型だけには依存せず、既知の項目だけを持つオブジェクト、各値の型、UTF-8のバイト数、配列の件数を検査します。文字列の容量はNode標準の [Buffer.byteLength](https://nodejs.org/docs/latest-v24.x/api/buffer.html#static-method-bufferbytelengthstring-encoding) で数え、日本語等の多バイト文字も含めます。エラーには入力された秘密や未知の項目名を含めません。

エントリの保存・編集で受け付ける項目は `serviceName`、`loginId`、`password`、`notes`、`url`、`tags`、`group` です。取得結果の `id` や日時を含む未知の項目は400で拒否します。従来どおり、任意項目 `notes`・`url`・`group` の省略・nullは空文字、`tags` の省略・nullは空配列として扱います。パスワードはtrimやUnicode正規化を行いません。

| 対象 | 上限・条件 |
|---|---|
| HTTPの通常JSON本文、IPCの保存内容を正規化したJSON | 1 MiB。JSONのエスケープによる増加も含む |
| 復元要求のJSON | 18 MiB。`.cvault` 本体16 MiB、復号内容11 MiB、10,000件という従来の制限も維持 |
| サービス名・グループ | 各1,024 byte |
| ログインID | 4,096 byte |
| パスワード | 64 KiB |
| メモ | 256 KiB |
| URL | 8 KiB。認証先としての信頼判定はこの文字列検証に含まない |
| タグ | 100件、各256 byte。配列の穴や文字列以外の値は不可 |
| 保管庫の新規登録 | 全体で10,000件まで。既存行の閲覧・削除は維持 |
| マスターパスワード | 1 MiBとJSON全体の上限内。初期設定の12文字以上という条件を維持し、旧形式の解除では新しい最小長を課さない |
| バックアップ用パスフレーズ | 従来の12〜1,024文字、UTF-8で4,096 byte以内 |
| エントリID・セッションID | 128 byte以内。エントリIDは空文字・NULを不可とする |
| Electronのクリップボード入力 | 文字列、1 MiB以内 |

型・項目・値の不正は400、容量・件数超過は413を返します。世代やロック状態による409・423の拒否は引き続き入口で行います。HTTPのロック・操作通知・監査・削除は本文なし、または空オブジェクトだけを受け付けます。不正UTF-8や不正JSONは400、Content-Lengthまたは受信中の本文が上限を超えれば413で拒否します。IPCでは保管庫操作の引数個数も確認し、クリップボードへの書き込み前にも共通検証を通します。IPCの容量検証はmain側でデータを受信した後に行います。

項目別の編集上限を保存済みデータの読み取りに適用しません。上限を超える既存の長文やタグも、閲覧と従来のバックアップ全体上限内での書き出し・v1復元を維持し、自動で切り詰めません。新しい編集上限を超える値を含む保存は元データを変更せずに拒否するため、編集する場合は入力を上限内へ調整する必要があります。DBスキーマや暗号形式の移行は行いません。

## 保管庫と暗号化

手動更新の通信は保管庫操作とは分離しています。更新確認・ダウンロード時に GitHub へ接続しますが、保管庫データは送信しません。

### マスターパスワード

マスターパスワードそのものは保存しません。

1. 16 byteのランダムSaltを生成する
2. 非同期 `scrypt` で32 byteの保管庫鍵を1回導出する。従来の既定値と同じN=16384、r=8、p=1、maxmem=32 MiBを明示し、保存済みSaltはBase64文字列のまま渡す
3. 鍵をキー、固定ラベル `CIPHER VAULT password verifier v1` をメッセージとするHMAC-SHA256を検証値としてSQLiteへ保存する（鍵そのものは保存しない）
4. 比較には `timingSafeEqual` を使用する
5. 解錠中だけ保管庫鍵をプロセスメモリに保持する

初期設定と解除は `vault-unlock-guard.ts` の共通制御を通り、HTTP・IPCを合わせて同時に1件だけ鍵導出を実行します。追加要求は409で拒否し、パスワードをキューに溜めません。導出中も状態取得・ロック・リセットを処理でき、導出開始時の世代が変わった場合は一時鍵をゼロ埋めして破棄します。初期設定の保存や旧検証値の移行は、導出後の世代確認に通った場合だけ行います。ロック済みの現世代へのロック要求も、未完了の解除を無効化します。Nodeの実行中scrypt自体は中断せず、コールバックが戻るまで実行枠を維持します。

誤パスワードによる401が5回連続すると、次の試行まで1秒、以後2・4・8・16・30秒（上限）の待機を設けます。待機中は429と残り秒数を返し、HTTPでは `Retry-After` も付けます。拒否された連打で期限を延長せず、入力不正・取消・保存失敗は認証失敗として数えません。成功で回数と待機を解除し、手動ロックやリセットでは解除しません。状態はプロセス内だけに保持し、再起動で失われます。これはオンライン試行の負荷・頻度の制御で、DB入手後のオフライン推測に対するKDF強化とは別です。

鍵の有無、解除状態、セッション世代、5分の無操作期限は `vault-session.ts` の1つの `VaultSession` が所有します。手動ロックまたは自動ロックで保持中の鍵Bufferをゼロ埋めして参照を破棄します。JavaScriptランタイム全体のメモリ消去を保証するものではありません。

サービス側のタイマーに加え、秘密操作の入口・暗号処理後・非同期処理の再開後・結果返却前でも期限と世代を照合します。タイマーが未発火でも、期限後の操作や期限延長は拒否します。単調時計と壁時計の経過時間を併用し、時計の巻戻りや不正値もロック側へ倒します。解除中の通常API呼び出し・状態確認・監視は無操作期限を延長しません。

画面は信頼された入力イベントの発生時だけ、最大約1秒の間隔で末尾の操作も含めて `POST /vault/activity` または対応IPCへ通知します。クライアントが渡す日時で期限を決めず、Core自身の時計を使います。これは人の存在をサーバーが証明する仕組みではなく、信頼するローカルUIを前提とします。Electronは下記のOSイベントにも連動します。Agentごとの認可はまだ追加していません。

ElectronはCoreの状態変更をpreload経由で画面へ通知し、ウィンドウ終了・renderer喪失時も鍵を破棄します。macOSでも最後のウィンドウを閉じた時点でロックします。Webは約1秒ごとの状態確認とfocus/visibility変更で追従します。状態確認が5秒以内に完了しない場合はローカル表示をロックし、同じ世代への再接続だけでは表示を復帰させません。バックエンドの通信断時に、その時点で鍵が消えたことまで保証するものではありません。

画面と通信層はセッションの変更時に未完了Promiseを無効化し、一覧・詳細・編集中の値・監査/バックアップ画面を破棄します。遅い応答は再解除後の世代へ適用しません。既存のSalt文字列、scryptパラメータ、HMACラベル、DBスキーマ、暗号文と `.cvault` v1形式は維持します。

この検証値の修正はv0.2.1から適用されます。v0.2.0以前は導出鍵そのものを検証値に保存していました。旧形式は正しいパスワードでの解除時に `kdf_params.verifierAlgorithm = "hmac-sha256-v1"` を追加し、検証値を置き換えます。暗号文と鍵導出方式は維持し、移行後は旧版で解除できません。失敗した認証では移行せず、移行の書き込みに失敗した場合も解錠しません。

SQLiteの `secure_delete` を有効にしますが、既存のバックアップ、ジャーナル、ファイルシステムの過去データの消去は保証しません。旧DBに含まれた鍵はこの移行で失効しません。詳細と対応範囲は [v0.2.1の修正](リリースノート/v0.2.1.md) を参照してください。

### ElectronのOSイベントとクリップボード

`vault-power-guard.ts` がElectron標準の [powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor) を監視します。Windows/macOSでは `lock-screen` と `unlock-screen`、各OSでは `suspend` と `resume` の通知時に保管庫をロックし、処理中の解除も世代変更で取り消します。復帰・OSの画面解除では保管庫を自動解除しません。通知でロック・スリープ中と判定している間は、状態確認と保管庫ロックを除く保管庫操作IPCを拒否します。起動時・操作時にも、対応OSで現在の画面ロック状態を取得できれば確認します。

`lock-screen` のLinux対応は仮定せず、未対応・取得不能な状態では既存のCore側5分期限、suspend/resume、ウィンドウ/renderer喪失の対策を維持します。Web/API単独実行にはElectronのOS監視を追加しません。各OSの実通知が確実に届くかは、実際のロック・スリープ・ユーザー切替による受入確認が別途必要です。

Electronのコピーは `expiring-clipboard.ts` と `clipboard-port.ts` を通り、`packages/shared/src/index.ts` の `CLIPBOARD_CLEAR_AFTER_MS`（30秒）を期限とします。導入済みElectron 45の [ClipboardItemとclipboard.write](https://www.electronjs.org/docs/latest/api/clipboard#clipboardwritedata) で、平文とランダムな所有マーカーを1回の書き込みにまとめます。保持する期限情報はマーカー・SHA-256の照合値・時刻であり、タイマーのためにコピーした平文を保持しません。マーカーを付けた書き込みができない場合はコピー失敗として扱います。

期限時と保管庫ロック時に、マーカーと内容の照合値が一致する場合だけ標準クリップボードを消去します。別のコピーやリッチな内容への差し替えは保持します。手動ロック、OSイベント、ウィンドウ終了、renderer喪失、更新、通常終了もこの経路を通ります。コピー中にセッションが変わった場合は成功を返さず、遅れて書き込まれた自分の内容も消去対象とします。通常終了は鍵を先に破棄し、クリップボード処理を最大1.5秒待ちます。重複コピーはキューに溜めず、処理完了後の再操作を求めます。

所有マーカーはクライアント認証ではありません。標準APIの読み取り照合と消去はOSに対して不可分ではないため、同時書換えとの競合やアクセス失敗を完全には排除できません。読取失敗・1秒の読取タイムアウト時には消去せず、後続のロック・復帰・終了時に再試行できます。履歴・同期・他アプリが保存した過去のコピーの消去は保証せず、LinuxのselectionクリップボードとWeb版のコピー動作も変更しません。

### エントリ暗号化

legacy形式ではパスワードとメモをAES-256-GCMで個別に暗号化します。

```text
[ IV (12 bytes) | Auth Tag (16 bytes) | 暗号文 ] → Base64
```

legacy形式のサービス名、ログインID、URL、タグ、グループ、日時は検索・一覧表示のため平文で保存します。v2では下記のcodecでentry全体を暗号化します。

現行形式の互換性は `tests/fixtures/crypto-compatibility.json` の合成固定データでも検証します。Salt文字列・Unicode・生鍵/HMAC検証値・GCMの並び・旧DB行・`.cvault` v1を、実装とは別のPython hashlib/hmacとcryptographyで生成し、`tests/crypto-compatibility.test.mjs` から実サービスの解除・検証値移行・復号・別鍵への復元を確認します。誤passwordやIV/tag/dataの改変で原本・復元先が変わらないこと、書き出した形式をWeb Cryptoでも復号できることを含みます。`draftV2` は下記codecを照合する独立した参照データであり、アプリの保管庫が新形式へ移行したことを意味しません。

### v2 codec

`apps/api/src/crypto/v2-codec.ts` はNode標準cryptoだけを使う独立した暗号モジュールです。`v2-format.ts` が入力の型・項目・版・容量・canonical Base64、ID・revision、UTF-8とentry DTOの内容を検証します。DB・ファイル・Electron・HTTP・`VaultSession` をimportせず、v2保存層とv2サービスから呼ばれます。既存legacy DBと `.cvault` v1の形式は維持します。

| API | 契約 |
|---|---|
| `createRootKey()` | CSPRNGで32 byteの新rootを生成。返したBufferの所有者は呼出元 |
| `wrapRootKey(root, password, context, options?)` | 新しいSaltとIVでrootを保護する。contextは `vaultId, keyId, slotRevision`。scryptのSaltは復号済み16 byte、profileは固定のallowlistのみ |
| `unwrapRootKey(envelope, password, expectedContext, options?)` | 呼出元が期待するID・revisionとの一致とGCM認証を通ったroot Bufferだけを返す。envelope自身を期待値の代わりにしない |
| `sealEntry(root, plaintext, context, reserveNonce, options?)` | UTF-8 JSON文字列またはBufferのentry全体を暗号化。contextは `vaultId, keyId, entryId, revision`。nonce予約callbackは必須 |
| `openEntry(root, envelope, expectedContext, options?)` | GCM認証、厳密なUTF-8、全DTO項目と内外IDの一致を検証後、平文JSONのBufferを返す |
| `parseEntryEnvelope` / `parsePasswordSlotEnvelope` | JSON文字列・Bufferまたはデータ属性だけのオブジェクトから、検証済みの不変snapshotを返す |
| `entryAad` / `passwordSlotAad` | 検証したID・版・用途等から固定のJSON配列を生成する。受信JSONのキー順・escapeをAADとして使わない |

`context` のUUIDは小文字v4、entryIdは有効UTF-8で128 byteまで・NUL不可、revisionは1〜4294967295です。暗号方式はAES-256-GCM、IV12 byte・tag16 byteを固定し、`authTagLength: 16` を明示します。envelopeのJSON入力は16 MiB、entryの平文は11 MiBまでです。過去の長文・null・空文字・タグ順序を新規編集上限で切り詰めません。未知profileや任意のN/r/p/maxmemをKDFへ渡さず、legacy readerへのfallbackもしません。

KDFはこのモジュール内で同時に1件だけ実行します。`options.signal` は `AbortSignal` を受け取り、処理・awaitの前後と結果返却前で取消を検査します。取消時も実行中scrypt自体を中断せず、callback完了まで実行枠を保持します。外部nonce予約callbackの中断も行いません。通常のv2サービスは下記のSession世代検査・signalと共通解除試行制御を適用し、独立した移行APIの認可はその呼出元が担当します。

`reserveNonce(keyId, iv)` は永続予約を終えたときだけ `true`、衝突なら `false` を返す契約です。codecは自分で生成したIVのコピーを渡し、衝突時は最大8回で打ち切ります。例外やboolean以外の戻り値でも暗号文を返しません。DB予約・書込回数上限・復旧後のnonce状態は保存層の責任であり、このcallbackの存在だけで永続化が保証されたことにはなりません。通常APIに固定Salt/IVや任意の乱数関数を指定する引数はありません。

入力鍵・平文・context・envelopeはawait前にsnapshotを取り、呼出元の鍵Bufferを変更しません。一時password、KDF出力、用途別鍵、未認証の復号断片、失敗した平文Bufferを消去します。返されたroot・平文Bufferは呼出元が必要最小の期間だけ保持して消去してください。JavaScript文字列やOpenSSLを含むプロセスメモリ全体の消去保証はありません。`VaultCodecError.code` で形式不正・認証失敗・処理失敗・busy・取消・nonce失敗を区別し、入力値やネイティブ例外の本文はエラーへ含めません。

## データモデル

### DBの接続と形式判定

DBモジュールはimport時に保存先を開きません。Web/APIは `server.ts`、Electronは `main.ts` が保存先を設定し、サービスの利用開始前に `vault-context.ts` の `openVaultStorage()` を呼びます。Contextはpointerと受領記録を検査し、legacyなら下記 `database.ts`、v2ならv2保存層だけを開きます。SQLは利用時に準備し、再接続後に古いStatementを再利用しません。終了時は `closeVaultStorage()` でSessionと処理を失効させてから接続を閉じます。HTTPの待受失敗、Electronのサービス・画面読込失敗でも同じ経路で解放します。

| API | 契約 |
|---|---|
| `openDatabase({ dataDirectory?, readonly?, createIfMissing? } = {})` | プロセスが所有する1接続を開く。保存先は呼出時に解決し、旧来の保存先・ファイル名を維持。`createIfMissing: false` は新規ファイル作成を禁止 |
| `getDatabase()` / `getDatabasePath()` | 開いている接続・パスを返す。未接続・終了後は `NOT_OPEN` で失敗し、自動再接続しない |
| `closeDatabase()` | 重複呼出を許可する。実行中のtransactionやclose失敗では `CLOSE_FAILED` とし、接続を成功扱いで破棄しない |
| `inspectDatabaseFile(path)` | 読取専用の一時接続でsnapshotを調べ、`missing` / `empty` / `legacy` と旧列追加の要否を返す。存在しない保存先・ディレクトリを作らない |

既存ファイルはRW接続より先に調べます。legacyは `application_id = 0`・`user_version = 0`、通常の `vault_metadata` と `password_entries` の2テーブル、既知の列・型・NULL条件・主キーを基準とします。追加のテーブル・view・trigger・独自index、未知の列や版、非SQLiteファイルは拒否し、初期化や旧形式へのfallbackを行いません。過去版の `group_name` と `password_changed_at` の欠落は受け付け、RW接続後のIMMEDIATE transaction内で再検査してから追加します。途中失敗時は列追加全体を巻き戻し、暗号文を保持します。新規ファイルは排他的に作成して上書きを防ぎます。初期化失敗時の空ファイルを自動削除せず、次の明示openで再検査します。

`readonly: true` は現在の列が揃ったlegacyだけを開けて、空DBや旧列追加が必要なDBでは `MIGRATION_REQUIRED` になります。読取専用ではschema追加や `secure_delete` の変更を行いません。これは保存接続の指定であり、サービス全体を読取専用にする機能ではありません。解除時の旧検証値移行等を含む書込みはSQLiteに拒否されます。通常のRW接続では従来どおり `secure_delete` を有効にします。

形式判定は構造検査であり、データの暗号認証・完全性検査ではありません。WALの内容もSQLiteを介して検査し、主ファイル単独のコピーや `immutable` で補助ファイルを無視しません。SQLiteの読取専用接続でもWAL用の補助ファイルを作成する場合があり、任意のDBに対するファイルシステム全体の無変更は保証しません。[SQLiteの読取専用WAL条件](https://www.sqlite.org/wal.html#read_only_databases)を参照してください。hot journalの復旧やアクセス権等により読取専用で開けない場合は、RWへ切り替えて進めず停止します。原本と補助ファイルを保持し、対応する版での正常終了・復旧を確認してください。

接続の所有者は単一プロセスとし、切替・終了前のSession失効は呼出元が担当します。生の接続やStatementを再接続をまたいで保持しないでください。このlegacy接続は下記v2保存層・移行pointerを扱いません。既存DBのKDF・鍵・暗号文と `.cvault` v1は維持します。

### v2保存層

`apps/api/src/db/v2-store.ts` は明示したファイルだけを扱い、環境変数や現在の保存先を参照しません。通常起動ではContextが所有し、HTTP・IPCは同じサービスを通して利用します。スキーマは `v2-schema.ts` の `application_id = 0x43563200`、`user_version = 1` で識別します。これは暗号envelopeの `cryptoVersion = 2` と別の版です。STRICTな3テーブルのDDL・制約を固定し、読取専用preflightで既知のDDL・単一header・期待ID・slot・nonce件数と使用回数の一致を検証します。未知形式や制約変更、追加オブジェクトでは初期化・修復・fallbackを行いません。

| API | 契約 |
|---|---|
| `createV2Store(path, passwordSlot)` | 存在する親ディレクトリ内に排他的に新規作成。既存ファイル・空ファイルを上書きしない。検証済みの暗号化root slotを受け取る |
| `openV2Store(path, expectedSlotContext, { writable? } = {})` | 既存v2だけを開く。既定は読取専用。writer再開は `writable: true` を明示し、RW接続後もtransaction内で再検査 |
| `readPasswordSlot()` / `getUsage()` | 暗号化root slot、使用回数・上限を返す。生のSQLite接続やroot鍵は公開しない |
| `listEntryContexts()` / `readEntry(id)` | ID・revisionの一覧、検証した暗号envelopeを返す。平文の認証・復号は呼出元が `openEntry` で行う |
| `writeEntry(root, plaintext, context, options?)` | codecで全DTOを暗号化して保存。外部のentry暗号文や固定IVを受け付けない。`options.signal` と保存直前の `assertCurrent` で取消・Contextを検査 |
| `restoreEntries(root, entries, options?)` | 空の保管庫だけに全件復元。全入力をsnapshot・検査してからnonceを予約し、暗号処理後に同期transactionで一括保存 |
| `deleteEntry(context, options?)` / `close()` | revision一致時に暗号文を除去し、ID・最終revisionをtombstoneとして保持。削除transactionの前後にもguardを適用。closeは重複可、未完了writeは保存前に閉鎖を検出して失敗 |

`vault_header` は期待ID・password slot・使用回数、`vault_entries` はentry ID・revision・暗号envelopeまたはtombstone、`vault_nonces` はkey ID・12 byte IV・entry ID・revisionを保持します。サービス名・ログインID・password・メモ・URL・タグ・グループ・日時はentry暗号文の内側に入ります。ID・revision・件数・削除履歴や暗号slotの情報は秘匿対象に含みません。

書込みは、先にnonceの一意予約と使用回数の加算を1個のIMMEDIATE transactionでcommitし、その後に暗号化、別のtransactionでentryを保存します。予約成功を返す前にcommitが完了するため、entry保存の失敗・取消・削除・close・プロセス終了で予約を巻き戻しません。衝突時だけcodecが再試行し、衝突分の回数は加算しません。使用回数は成功entry数ではなく消費した予約数で、同一鍵の2^20件に達したら `KEY_LIMIT` で新しいrootへの再暗号化を要求します。暗号文の無い予約も削除・再利用せず、回数リセットやroot切替のAPIは追加していません。

writerはDELETE journal、`synchronous=EXTRA`、外部キー制約、`secure_delete`、`trusted_schema=OFF` を使います。[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)に依存し、任意のfilesystem・デバイスの電源断保証とは区別します。予約後の即時 `process.exit` による再開試験を行い、実際の電源断は未検証です。IO失敗や保存データの構造不正後はhandleを `FAULTED` として再利用せず、closeと明示openを要求します。初期化失敗で残ったファイルも黙って上書きしません。

新規entryはrevision 1、以後は保存済みrevision+1だけを受け付けます。削除後もこの連番と予約を保持し、競合時には原entryを保護して新予約を消費済みのまま残します。有効なentryは10000件までで、上限時も既存entryの更新・削除は可能です。単一handleの未完了writeは `BUSY` で多重実行を拒否します。SQLiteの競合試験は、同期・複数writerの製品サポートを意味しません。

新規作成へ渡すslotは、呼出元が新しいUUID・CSPRNGの新rootから生成してください。既存slotを別DBへコピーしてwriterを開始する用途には対応しません。通常のrootは認証したslotから得て、呼出元がslotとの一致・Session世代・認可・利用後の消去を管理します。保存層はrootを保持せず、JSONの形式検査を暗号認証の代わりにしません。`V2StoreError` とcodecのエラーは入力値やネイティブ例外本文を含めません。DB全体・nonce表・counterを一緒に巻き戻す攻撃の検出は保証せず、raw DBコピー・snapshot復元後にwriterを再開する判断をこのAPIだけで行わないでください。移行は下記の[staging](#原本を保持するv2移行staging通常起動への接続前)と[pointer切替・復旧](#移行pointerの切替と復旧通常起動への接続前)を経て、新rootと全件照合を必要とします。

### 通常起動とv2サービス

`db/vault-context.ts` は、1プロセスで使用する保存形式と接続を管理します。`openVaultStorage({ dataDirectory?, readonly?, createIfMissing? })` の保存先解決は従来どおりで、pointer・受領記録・transitionがない場合だけlegacyを開きます。legacy初期化も、SQLiteのtransactionロックを取得した後にContextのguardを呼び、形式選択後の切替を検出してから旧列の追加へ進みます。完了状態のv2を選んだ場合は、保持した期待IDで `openV2Store` を開き、原本の `password-manager.db` を開きません。破損・準備状態・欠落のある切替をlegacyで補わず、起動を停止します。新規保管庫の初期設定は引き続きlegacy形式です。移行やpointer保存を起動時に自動実行しません。

Contextは、秘密操作と保存前にpointer・受領記録・保存先のlink条件・device/inode・Contextの同一性を検査します。legacy選択中に切替記録が現れた場合も失効させます。閉鎖・失効時にはsignalとSessionを失効させ、鍵を破棄します。旧Contextの未完了処理は、後から開いたContextや新しいSessionを失効させません。`getVaultStoragePath()` は選択中のパスを返し、v2選択中にlegacy専用の `getDatabase()` を使っても `NOT_OPEN` になります。自動再接続や旧形式へのfallbackは行いません。

legacyの通常接続には、metadataとentryのINSERT/UPDATE/DELETEを検査する接続ローカルのTEMP triggerを追加します。SQLiteの書込ロック待ちの後にguardを実行するため、切替前に準備されたSQLでも、pointer保存後に原本へ書き込めません。TEMP領域はMEMORYで、原本のschema・形式にはtriggerを保存しません。この保護はContextで開いた当該接続に限り、旧バイナリや別の生接続による原本編集を禁止するものではありません。[SQLiteのTEMP trigger](https://www.sqlite.org/lang_createtrigger.html#temp_triggers_on_non_temp_tables)を使います。

公開サービスは `entry-service.ts` / `vault-service.ts` / `backup-service.ts` / `audit-service.ts` のままで、v2選択時だけ `v2-vault-service.ts` を使います。HTTPとElectronのpreload APIのDTO・呼出名は変更せず、追加・更新・復元の非同期完了を両入口で待ちます。legacyの直接サービス呼出では、従来の同期CRUDを維持します。

v2の解除は、既存の共通 `VaultUnlockGuard` を通し、誤passwordの試行待機と同時実行拒否を適用します。保存されたslotをunwrapした後、全entryを期待ID・revisionで認証してからrootのコピーをSessionへ設定します。KDF後と読取途中で世代を検査し、lock・reset要求・再接続後に古い解除結果でSessionを復活させません。slotの認証失敗は誤passwordとの区別ができないため401です。root取得後のentry認証やContextの不正は鍵を破棄して503とし、明示的な再起動・復旧を要求します。

一覧も解除後に全DTOを復号してsummaryだけを返し、password・notes・URLを含めません。plaintextの永続indexや、lock後も残すサービス側cacheは追加しません。長文・null・空文字・タグ順序は読取とbackupで維持し、新規編集時だけ既存の入力上限とtrim方針を適用します。不正Unicodeはnonce予約前に拒否します。更新では作成日を維持し、passwordが変わらなければ不明な変更日もnullのまま保持します。

v2のv1復元は、10000件・11 MiBの既存上限と全DTO検査を通し、空の保管庫に限ります。全入力とrootをsnapshotし、各nonceを先行commitして暗号化した後、同期transactionで全entryを保存します。保存・取消の失敗では全登録行を巻き戻し、使用済みnonceと回数は保持します。削除済みIDの復元はtombstoneの次revisionを使います。暗号処理中は定期的に制御を戻し、最後のtransaction内でもSession・Contextを検査します。監査も同じ復号経路を使い、結果に秘密を含めません。

`readonly: true` のv2は解除・読取・exportを許可し、変更は403で拒否します。鍵の2^20使用上限では新規暗号化を409で止め、既存entryの読取・exportを維持します。通常のv2初期化要求はSessionと未完了処理を失効させたうえで409を返し、DB・root・nonce履歴・pointerを変更しません。[鍵更新・安全なリセット](#v2の鍵更新と安全なリセット)は独立した内部coordinatorとして実装しています。移行・復旧・鍵更新・リセットのHTTP/IPC入口は下記の管理サービスへ接続しています。UI接続と実データへの適用は未実装・未実施です。Windowsのdirectory永続化・実電源断後の確認など、下記の移行受入条件も引き続き必要です。

### v0.2.2 暗号化バックアップ

旧KDF・検証値・GCMの純粋な処理は `crypto/legacy-codec.ts`、v1ファイルの暗号化・復号・DTO検証は `crypto/backup-v1.ts` に置きます。サービス層はSessionと世代を検査し、形式別の復元処理が完了するまで鍵と実行枠を保持します。legacyは `db/legacy-entry-writer.ts`、v2は保存層の一括復元を使い、v1ファイル形式を共有します。移行検査は現在のSessionや接続を切り替えず、別のメモリ内Vaultで同じlegacy復元処理を利用します。

解錠中に全エントリを版付きJSONへ変換し、専用パスフレーズから導出した鍵で全項目を暗号化した `.cvault` を生成します。DBやマスターパスワードの検証値は含めません。暗号化はNode.js標準 `node:crypto`、保存の一括処理は既存のbetter-sqlite3を使用します。

- 外側のJSON: `format = CIPHER-VAULT`、`version = 1`、`kdf = scrypt-N131072-r8-p1`、`cipher = aes-256-gcm`、Base64の `salt` / `iv` / `tag` / `data`。
- 毎回16 byteのSaltと12 byteのIVを生成。非同期scrypt（N=131072、r=8、p=1、maxmem=256 MiB）で32 byteの鍵を導出し、AES-256-GCMと16 byteの認証タグで改ざんを検証。
- `CIPHER-VAULT:1:scrypt-N131072-r8-p1:aes-256-gcm` を追加認証データ（AAD）とし、固定の形式・暗号パラメータを検証。未知の版やファイル指定の任意KDFパラメータは受け付けない。
- パスフレーズは12〜1024文字。ファイルは16 MiB、暗号化前の内容は11 MiB、エントリは10000件まで。展開を伴う圧縮は使用しない。
- 復元先はマスターパスワード設定済み・解錠中・エントリ0件の保管庫に限定。全件の認証・形式・ID・日時・項目の検証後、現在の保管庫鍵で再暗号化し、単一トランザクションで保存する。書き込み失敗時は全件巻き戻す。
- バックアップと復元の多重実行を拒否。鍵導出中にロック・リセット・再解除された場合はセッション変更を検出して中止する。
- 平文の一時ファイルを作らず、鍵・平文Bufferを処理後にゼロ埋めする。JavaScriptの文字列を含むプロセスメモリ全体の消去は保証しない。パスフレーズとバックアップ内容をログに出さない。

Webは `/vault/backup/export`、`/vault/backup/restore`、Electronは `backup:export` / `backup:restore` から同じサービスを使用します。保存はブラウザ/Electronのダウンロード機能、読込はファイル選択を使用します。

### 原本保持移行の読取検査（通常起動への接続前）

`migration/preflight.ts` の `verifyLegacyMigrationSource(path, { masterPassword, backupPassphrase }, { signal? } = {})` は、明示したlegacyファイルを読取専用で検査します。HTTP・IPC・通常起動には公開せず、現在の保管庫・Session・接続を利用先として切り替えません。初期化・ALTER・検証値の更新・v2への保存・pointer変更を行いません。

戻り値は凍結した `{ report, backup }` です。reportはlegacy検証値の種類、entry件数、平文・暗号化backupのbyte数、未追加の旧列、`backupVerified: true` を含み、backupはv1のファイル名と暗号化済みcontentを含みます。鍵、password、平文DTO、原本パスを返しません。ファイルへの保存自体は行わず、原本のSQLite snapshotも作りません。

処理は明示的な読取transactionの同じsnapshotを使います。旧形式の生鍵検証値とHMACの両方を旧profileで認証し、Salt文字列をbytesへ読み替えません。未追加の `group_name` と `password_changed_at` はSQL上のNULLとして読み、原本へ列を追加しません。nullableな旧URL・notesは従来DTOと同じ空文字、group・変更日不明はnullとし、それ以外の文字列・空白・Unicode表現・タグ順序・長文は維持します。

通常の一覧が行う不正タグの読み飛ばしは使いません。UTF-8のDB文字列をBLOBとして取得して厳密にdecodeし、格納型、不正UTF-8、タグJSON、ID、日時、canonical Base64、暗号認証、v1復元とv2 DTOの受入条件を確認します。不正値を置換・正規化・切り詰めず拒否します。現在はUTF-8のlegacy DBだけを扱い、未知schema・KDF項目・encodingでは停止します。

entryは10000件、v1 JSON平文は11 MiB、ファイルは16 MiBまでです。行をJSへ展開する前にSQLで件数と全raw列の合計32 MiB上限を確認し、metadataの合計は8192 byteまでに制限します。新規編集の項目別上限は旧値に適用しません。32件ごとに制御を戻し、`AbortSignal` を確認します。

全DTOの検査後、専用passphraseでv1 backupを生成し、`migration/backup-recovery.ts` の共通処理で出力ファイルのSaltから鍵を導出し直して復号します。さらに別のランダムpassword・Salt・鍵を持つ `:memory:` の一時legacy Vaultへ共通の復元処理で再暗号化して保存し、再読取した全DTOを照合します。`createMemoryDatabase()` は現在の接続とは独立し、SQLiteの一時領域もMEMORYに指定します。原本DTOとの不一致、保存失敗、取消では成功結果を返しません。

KDFを含む検査全体をモジュール内で同時1件に制限し、実行中KDFが完了するまで取消後も実行枠を保持します。password、導出鍵、復号Bufferを消去して接続を閉じ、エラーには入力値やネイティブ例外本文を含めません。JavaScript文字列を含むメモリ全体の消去保証ではありません。将来の呼出元はSession世代とsignal、認可、共通試行制御を結び付けてください。

読取transactionを終えた後、同じ接続の `data_version` を比較し、途中の外部commitを検出したら `SOURCE_CHANGED` で拒否します。DELETE journalでは検査中のreaderが他writerのcommitを待たせ、WALでは並行commitが可能です。これは全writerの停止や、検査終了後の原本の固定を保証しません。SQLiteのWAL補助ファイル・hot journalに関する[読取専用の条件](#dbの接続と形式判定)も適用します。reportを後続stagingの許可証や `snapshot-verified` 状態として再利用せず、実移行ではwriter停止、暗号化backupの保存と復元確認、一貫したSQLite snapshot、新password、新root、全件検証、pointer切替・復旧を別途完了する必要があります。

### 原本を保持するv2移行staging（通常起動への接続前）

`migration/staging.ts` の `stageLegacyVault(sourcePath, vaultsDirectory, { masterPassword, newMasterPassword, confirmNewMasterPassword, backupPassphrase }, { signal? } = {})` は、明示したlegacy原本から別のv2 DBを作成・検証する内部APIです。通常起動・HTTP・IPC・現在のSessionへは接続していません。旧masterの再利用、確認値の不一致、12文字未満の新master、不正Unicodeを拒否し、文字列をtrim・正規化しません。既存preflightの結果を許可証として受け取らず、書込ロックを取得して検査し直します。

原本は最初に読取専用で形式・metadata・容量を検査し、その後に専用RW接続で `BEGIN IMMEDIATE` を保持します。DELETE/WALに限り、他接続・他プロセスのSQLite writerを止めます。原本のデータ・schemaを変更するSQLは実行せず、最後は必ずROLLBACKします。WALでは読取専用接続の `BEGIN IMMEDIATE` だけではwriterを排除できないため、RW接続が必要です。別の読取接続をRW接続より後まで保持して閉じ、最後のRW接続を閉じる際の原本WALのcheckpointも避けます。SQLite補助ファイルの更新や、OS権限を持つ相手によるファイルの直接置換を防ぐ保証ではありません。

指定した既存の `vaultsDirectory` をcanonical pathへ解決し、新しいUUIDを使う子ディレクトリを排他的に作ります。配置は次の通りです。

| ファイル | 内容と検証 |
|---|---|
| `<vaultId>/legacy.cvault` | 原本から作った暗号化v1 backup。排他作成・fsync・close後に実ファイルを読み、別鍵のメモリ内Vaultへ復元して全DTOを照合 |
| `<vaultId>/legacy.sqlite` | 別の読取接続から[SQLite Backup API](https://www.sqlite.org/backup.html)で取得。WALの確定済み更新を含め、保存先だけをDELETE journalへ変換してclose・fsync。再読取でquick_check・metadata・旧列・全DTOを照合 |
| `<vaultId>/vault.sqlite` | 新しいvaultId・keyId・CSPRNG rootと新masterから作るv2 DB。既存v2保存層のnonce先行予約で全項目を再暗号化 |
| `<vaultId>/v2-export.cvault` | 再openしたv2 DBから読み戻した全件のv1 export。保存・fsync後、別鍵のメモリ内Vaultへ実復元して原本DTOと比較 |

件数・backup・文字列の上限はpreflightを継承します。さらにSQLiteの論理ページ量を64 MiBまでに制限し、行が少なくてもfreelist等で超過するDBは `CAPACITY` で停止します。VACUUMや切り詰めによる原本の補正はしません。backupの転送中もページ量とsignalを検査します。

新DBはclose・fsync・読取専用reopen後、保存されたslotを新masterで認証して生成時rootと照合します。旧masterの解除拒否、旧データ鍵による各entryの認証失敗、件数・全DTO・revision・使用した暗号回数も確認します。全件を読み戻してからv1 exportの復元を検証し、鍵と接続を解放できた場合だけ、凍結した `{ state: "v2-verified", vaultId, keyId, slotRevision: 1, entryCount, files }` を返します。鍵・password・平文DTOは返しません。

取消・native KDF失敗・書込/flush/close失敗・改ざん・比較不一致では成功結果を返しません。KDFのcallbackが終わるまで同時1件の枠を保持し、一時鍵・password Buffer・復号Bufferを消去します。JavaScript文字列やOS・OpenSSL内の全コピーの消去保証ではありません。エラーは静的なcodeだけを持ち、パスや秘密、ネイティブ例外本文を含めません。

作成したファイルは失敗時も自動削除・上書きしません。特に `legacy.sqlite` は旧形式の平文metadataを含むため、保護されたデータ領域へ配置してください。POSIXの作成modeはdirectory 0700・backup 0600を指定しますが、WindowsのACL管理をこのAPIで置き換えるものではありません。未完了の `vault.sqlite` をwriterとして再開せず、再試行は必ず新UUID・新rootで最初から行います。ファイルが揃っているだけでは検証済みと判断できず、永続的な完了マーカーは作りません。

成功結果はこの実行時点の照合結果です。`stageLegacyVault` 自体は `vault-current.json` を作成・変更せず、ロック解放後の原本を固定し続けるものでもありません。後続の[pointer切替処理](#移行pointerの切替と復旧通常起動への接続前)は、書込ロックを取り直して保存済みデータを再検証します。通常操作の認可・共通試行制御とCoreの停止・再接続は下記の管理サービスが担当します。ファイルのfsyncは親directoryの永続化や実電源断後の状態を保証せず、移行全体の完了・本番適用を意味しません。

### 移行pointerの切替と復旧（通常起動への接続前）

`migration/activation.ts` の `activateStagedVault(dataDirectory, context, credentials, authorization, { signal? } = {})` は、固定の `password-manager.db` と `vaults/<vaultId>/` を使う内部coordinatorです。contextは `{ vaultId, keyId, slotRevision: 1 }`、credentialsは `{ masterPassword, newMasterPassword, backupPassphrase }`、authorizationは `{ session: VaultSession, sessionId }` です。新masterの設定確認は先行するstagingが担当します。通常操作からは下記の管理サービスを通して呼び出します。

開始前とawait後、pointer保存の各再開点で、明示したSessionの解除状態・世代・idle期限とsignalを確認します。旧masterを再認証し、導出した旧鍵がそのSessionの鍵と一致することも確認します。終了時は所有していた世代のSessionをlockし、後から解除された別世代を古い処理のcleanupでlockしません。プロセス内の同時実行は1件で、取消後もnative KDFのcallbackが完了するまで枠を保持します。通常操作では下記の管理サービスを通し、共通の試行制御と要求世代の検査を適用します。

原本と移行先v2 DBの両方に専用接続の `BEGIN IMMEDIATE` を保持し、別writerを排除します。stagingのreportや実行時オブジェクトだけを信用せず、現在の原本、保存済みlegacy backup、SQLite snapshot、v2 DB、v2からのv1 exportを読み直します。metadata・旧列・全DTO・件数・revision 1・暗号回数、新masterの認証、旧master/旧鍵の拒否、別鍵のメモリ内Vaultへのbackup復元を再確認します。staging後に原本やcandidateが更新された場合は停止し、いずれのDBも変更しません。

pointerは既定の `vault-current.json` に限定し、内容は `{ "format": "CIPHER-VAULT-ACTIVE", "version": 1, "vaultId": "<UUID>" }` だけです。準備・完了を記録する `vault-activation.json` は `{ "format": "CIPHER-VAULT-ACTIVATION", "version": 1, "vaultId": "<UUID>", "keyId": "<UUID>", "entryCount": 0, "state": "prepared" }` の形で、最後にstateを `committed` へ変更します。entryCountは切替時点の件数です。両JSONは512 byteまでのBOM・改行なしのcanonical JSONとし、未知項目、重複キー、未知版、不正UUIDを拒否します。受領記録は暗号認可やrollback検出の証明ではありません。

保存先はcanonicalなdataルートと検証したUUIDから構成し、相対パス・任意ファイルパスをJSONから受け取りません。ルート内の各構成要素でsymlink/junction、別deviceへの逸脱、通常ファイルのhard linkを拒否します。OS権限を持つ相手が検査の間に直接ファイルを置換する攻撃や、dataルート全体のrollbackを防ぐ保証ではありません。

切替は次の順序です。複数JSONを一つの原子的なtransactionとは扱いません。

1. 復旧用ファイルとv2 DBをfsyncし、対応OSではcandidate・vaults・dataのdirectoryも同期する。
2. 同じdataルート内に新規一時ファイルを排他作成し、準備記録をwrite・fsync・closeしてから `vault-activation.json` へrenameする。
3. 同様にpointerを一時ファイルへwrite・fsync・closeし、世代と保存先を再確認してから `vault-current.json` へrenameする。pointerを再openしてfsync・再読取する。
4. 完了記録を別の一時ファイルから `vault-activation.json` へ置換し、fsync・再読取する。鍵と接続を解放できた場合だけ `{ state: "v2-selected", context, entryCount, database, durability }` を返す。これは候補選択の結果であり、本番Coreの利用開始を意味しない。

`inspectVaultSelection(dataDirectory)` は読取専用です。transitionが存在せず、pointerと受領記録が両方ない場合だけlegacyを選び、両方の対応・完了状態・v2の形式を検査できた場合にv2候補を返します。片方の欠落、準備状態、破損、path逸脱、未知DBでは `RECOVERY_REQUIRED` で停止し、旧DBへfallbackしません。選択結果には復号鍵を含めず、全暗号文の認証は利用側の解除・読取処理でも必要です。

`recoverVaultActivation` は同じ引数で呼ぶ明示的な復旧処理です。有効な受領記録と指定contextが一致する場合に限り、同じ候補を全件再検証してpointerを再保存します。不正なpointerのbytesは別の排他作成ファイルに保持し、有効だが別vaultIdを指すpointerは置換しません。破損した受領記録から対象を推測せず停止します。DBの上書き・旧DBへの転記・nonceのリセット・未完了writerの再開は行いません。

完了済みv2の通常編集は候補選択を妨げませんが、旧データとの一致を前提とするこの復旧処理では、移行後に編集されたv2を復旧できません。新版の最新backup確保と明示的な復元・鍵交換の手順は別途必要です。原本とsnapshot、失敗した一時ファイルは自動削除しません。準備記録の作成前の失敗ではlegacyの選択を維持し、記録が存在する段階でのエラーは切替が起きた可能性を含め `RECOVERY_REQUIRED` とします。完了記録まで保存された直後のプロセス終了ではv2を選び、未応答だったことだけを理由に旧DBへ戻しません。

`durability` はWindowsで `file-sync`、directoryのfsyncも成功した環境で `file-and-directory-sync` です。Node/libuvのWindows経路ではdirectoryをfsyncしたと報告しません。[fsyncのOS・device依存性](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsfsyncsyncfd)と[Windowsのrename実装](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c)を踏まえ、実電源断、親directoryの永続化、別filesystem・各OS実機の受入確認を完了条件として残します。検証は合成データでのwrite/flush/close/rename障害とプロセス即時終了です。pointerの読取は通常起動のContextへ接続しましたが、移行操作のUIや実データへの適用は行っていません。

### v2の鍵更新と安全なリセット

`migration/v2-replacement.ts` の `replaceV2Vault(dataDirectory, sourceContext, request, authorization, { signal? } = {})` は、選択中のv2から別UUID・別rootのv2へ切り替える内部処理です。通常Contextと直接のlegacy接続を閉じ、別に保持した旧保管庫の解除済み `VaultSession` と `sessionId` をauthorizationに渡します。処理中に通常Contextが開かれた場合も停止します。sourceContextは `{ vaultId, keyId, slotRevision: 1 }` で、現在の完了済み選択情報と一致する必要があります。

requestは `{ mode: "rekey" | "reset", masterPassword, newMasterPassword, confirmNewMasterPassword, backupPassphrase }` です。旧masterの再認証とSessionの鍵の一致を必須とし、新masterは12文字以上・旧masterと異なる値・確認入力との完全一致を要求します。resetではさらに `confirmation: "RESET_ALL_DATA"` が必要です。resetは復旧用データを保持して新しい空Vaultへ切り替える操作で、旧master紛失の回避や安全な消去の保証はありません。旧master認証は共通 `VaultUnlockGuard` を使います。全処理は同時1件で、取消後もnative KDF完了まで実行枠を保持し、終了時は所有したSession世代だけをlockします。

新UUIDの `vaults/<targetVaultId>/` を排他作成します。`source.sqlite` はSQLite Backup APIによる退避、`source.cvault` と `target.cvault` はv1暗号化backup、`source-pointer.json` と `source-receipt.json` は旧選択情報、`vault.sqlite` は新保管庫です。旧DBを読取専用で検査してから専用IMMEDIATEロックを保持し、新DBも作成後に別のIMMEDIATEロックで固定します。元DBとnonce履歴を変更せず、失敗したdirectoryを再利用しません。raw DBやsnapshotをwriterとして再開せず、復元には全件を新rootへ再暗号化する経路を使ってください。

退避DBは512 MiBまでで、2^20件の使用済みnonceがあるDBも対象です。全DTOは従来の10000件・11 MiBのbackup上限を適用し、切り詰めません。旧masterで全entryを認証し、保存したsource backupを別鍵のメモリ内Vaultへ復元して照合します。snapshotのslot・root・全DTO・使用回数も再確認します。rekeyでは全DTOを新rootでrevision 1から再暗号化し、resetでは新rootの空DBを作ります。新使用回数はrekey時の件数、reset時は0です。新DBをclose・fsyncして再検査し、新masterの解除、旧master・旧rootの拒否、全DTO・revision・使用回数、target backupの独立復元を照合してから切り替えます。

1. 復旧用ファイルをfsyncし、対応OSでは親directoryも同期する。
2. `vault-transition.json` を同じdataルートの排他一時ファイルへwrite・fsync・closeした後にrenameする。mode・旧/新context・件数・旧使用回数と、旧DB・snapshot・両backup・旧選択情報・新DBのSHA-256を記録する。4096 byteまでの厳密なJSONとする。
3. 従来形式の受領記録を新contextの `prepared`、pointerを新vaultId、受領記録を `committed` の順に、個別の一時ファイルとrenameで保存・同期・再読取する。
4. transitionを新directoryの `replacement.json` へrenameして同期する。鍵と接続の解放が成功した場合だけ `{ state: "v2-selected", mode, source, target, sourceCount, targetCount, files, durability }` を返す。

複数ファイルを単一transactionとは扱いません。transitionが存在する間は、pointerと受領記録の状態にかかわらず通常起動を `RECOVERY_REQUIRED` で停止し、実行中のContextも失効させます。両選択情報が欠落してもlegacyへfallbackしません。transition保存前の失敗では旧選択を維持し、保存された可能性のある段階では自動rollbackせず明示復旧を要求します。最後のrename後に応答や同期が失敗した場合は既に新保管庫が選択され得るため、無応答だけを理由に旧DBへ戻してはいけません。SHA-256と署名のない記録は変更検出用で、認可・改ざん耐性・dataルート全体のrollback検出を保証するものではありません。

`inspectV2Replacement(dataDirectory)` はtransitionから `{ source, target, mode }` の候補を返します。既知の対象と照合し、`recoverV2Replacement(dataDirectory, expected, request, authorization, { signal? } = {})` に渡します。両master・旧Sessionの再認証、全ファイルの記録済みhash、snapshot・全DTO・使用回数・両backupの独立復元を再確認してから切替を完了します。entryの暗号化・DB上書き・nonceリセットを行わず、旧DBまたは新DBが編集されていれば停止します。不正なpointer/受領記録は512 byte以下の安全な通常ファイルに限り、元bytesをbase64で別の排他作成ファイルへ保持してから置換します。有効な別保管庫への選択情報や、破損したtransitionから対象を推測して置換しません。

元DB、復旧用ファイル、失敗したcandidate・一時ファイルは自動削除しません。path・linkの条件、OS権限を持つ相手に対する制約、Windowsでの `file-sync`、directory永続化・実電源断の未確認は、上記の[pointer切替](#移行pointerの切替と復旧通常起動への接続前)と同じです。直接のUI/API公開は行わず、下記の管理サービスから呼び出します。実データへの適用は行っていません。

### 保管庫の管理サービスと復旧専用起動

`services/vault-maintenance-service.ts` は、移行・鍵更新・安全なリセット・中断後の復旧を、通常の保管庫接続と調停します。アプリ入口は `openApplicationVault(options)` / `closeApplicationVault()` を使い、dataルートと読取専用設定を固定します。管理操作はこの初期化が必要で、呼出元から保存先、UUID、暗号contextを受け取りません。通常のv2・legacy CRUDと解除は従来のContextを使います。

`VaultStatus.maintenance` は `{ state: "ready" | "running" | "recovery-required", format: "legacy" | "v2" | "unknown", operation?, recoveryOperation? }` です。鍵・DTO・ファイルパスを含めません。通常起動で既知のtransition、または再検査できるlegacy移行の受領記録が見つかった場合は、保管庫接続を開かず復旧専用の状態でUI/APIを起動します。通常の解除・初期化を拒否し、明示的な復旧だけを受け付けます。未知形式・不正な記録を正常な保管庫として開かず、復旧対象を特定できない起動は従来どおり失敗します。HTTPの `/health` は通信の生存確認で、保管庫の利用可否は `/vault/status` で確認します。

操作はHTTPの `POST /vault/maintenance` またはpreloadの `runVaultMaintenance(payload, sessionId)` です。payloadは共有型 `VaultMaintenancePayload` に定義し、`operation` は `migrate` / `rekey` / `reset` / `recover`、認証項目は `masterPassword`、`newMasterPassword`、`confirmNewMasterPassword`、`backupPassphrase` です。新規操作は `confirmBackupPassphrase` の一致も必須で、resetとresetの復旧は `confirmation: "RESET_ALL_DATA"` を要求します。recoverの対象はサーバー側の記録から決めます。その他の未知項目を拒否します。入力の文字・byte上限、パスワードを正規化しない条件は内部coordinatorと共通です。

HTTPは既存のHost/Origin・CSRF・Session世代と本文容量の検査を通り、本文読取後も世代を照合します。IPCは既存の信頼したrenderer・引数個数・OS状態・世代の検査を通ります。通常操作は解除済みの現世代だけに許可し、復旧専用起動ではロック済みの現世代と旧masterの再認証を必要とします。全操作を同時1件に限定し、旧masterの認証は共通の試行制限を使います。新しい暗号APIや秘密取得用の外部入口は追加しません。

開始時に通常Sessionの鍵を独立した操作用Sessionへ引き継ぎ、通常の接続を閉じて鍵と古い要求を失効させます。操作用Sessionにも5分の失効条件があります。手動lock、OSイベント、画面喪失、終了、HTTP通信の切断では操作を取り消し、native KDFが終わるまで実行枠を保持します。途中の取消を、既に確定した切替のrollbackとして扱いません。全ての終了経路で一時鍵を消去し、通常接続が勝手に開き直されていないことを確認します。

処理後は選択情報を検査して明示的に再接続し、成功時も必ずロック状態へ戻します。失敗前の選択がv2だった場合、選択情報の欠落をlegacyで補いません。新しいDBやschemaを自動作成して再開することもありません。再検証できなければ接続を閉じた復旧状態を維持します。停止中は再接続しません。Electronは終了時に取消とcleanupを待ち、既存の1500ms待機上限を超えた場合はプロセス終了相当の復旧条件を適用します。

Webクライアントは操作開始時に秘密表示を消し、処理中の世代変更を受け入れた後に状態を読み直します。最終状態を確認できない場合に成功を返さず、古い操作結果で新しい画面を上書きしません。通常CRUDの30秒timeoutとは別に、この操作のHTTP待機は315秒までです。UIの操作接続と実データでの受入、実電源断・各OSの検証は別途必要です。

### v0.2.2 ローカル監査

`audit-service.ts` が解錠中のみ解析し、UIには件数・対象ID・サービス名・ログインID・理由だけを返します。パスワード、メモ、強度推定器の生の結果は返しません。外部の漏えい照会やURLへのアクセスは行いません。解析中は定期的にイベント処理へ制御を戻し、ロック・セッション変更時に中止します。結果は解析開始時点のスナップショットです。

| 項目 | 判定 |
|---|---|
| 弱いパスワード | zxcvbn-ts v4の評価0〜2。共通・英語辞書、サービス名・ログインIDを使用。強度推定は先頭256文字まで |
| 重複パスワード | 文字列の完全一致。同じ値を使う全件を対象にする |
| 古いパスワード | `password_changed_at` から365日以上 |
| URLなし | URLが空欄 |
| 長期間更新なし | `updated_at` から365日以上 |

スコアは `round(100 - (弱い件数 * 60 + 重複件数 * 40) / 全件数)`。0件は未採点。古さ・URL未登録・長期間更新なしは見直し項目として表示し、減点しません。スコアは製品独自の目安であり、NIST等の認証や安全性保証を意味しません。辞書に含まれない言語・パターンの推定には限界があります。

`password_entries.password_changed_at` をNULL許容で追加します。既存レコードはNULL（変更日不明）を保持し、新規作成またはパスワード自体が変わったときだけ記録します。メモだけの編集では更新しません。既存の保管庫鍵・検証値・暗号文は変更しません。v0.2.1以前は新しい日時を更新しないため、旧版で編集した後のパスワード年齢は信頼できません。`.cvault` はv0.2.2以降が対象です。

Webは `POST /vault/audit`、Electronは `vault:audit` を使用します。

### `vault_metadata`

保管庫の検証情報を `id = 1` の1行で保持します。

| カラム | 内容 |
|---|---|
| `password_salt` | 鍵導出用Salt |
| `password_verifier` | マスターパスワードの検証器 |
| `kdf_params` | KDFパラメータ |

| カラム | 内容 | 保存形式 |
|---|---|---|
| `service_name`, `login_id` | サービス名、ログインID | 平文 |

## フロントエンド

```text
起動 → 保管庫状態取得
  ├─ 未設定   → LockScreen（初期設定）
  ├─ ロック中 → LockScreen（ロック解除）
  └─ 解錠済み → VaultDashboard
```

`App.tsx` が保管庫状態、エントリ一覧、選択中エントリ、入力イベントの通知とロック状態の画面反映を管理します。自動ロックの強制は共通サービスの `VaultSession` が担当します。`AppMenu.tsx` が共通メニュー、`VaultDashboard.tsx` が検索・一覧・選択、`EntryEditor.tsx` が作成・編集の入力を担当します。通信切替は `lib/api.ts`、世代を跨ぐ応答の拒否は `lib/vault-client-session.ts` が担当します。

作成と編集は共通の2列フォームを使い、グループ・タグ・メモを「追加情報」に折り畳みます。折り畳み状態にかかわらず入力値を保持して保存し、未保存の変更がある状態でエントリ選択・新規作成・手動ロックを行う場合は破棄を確認します。保存・削除は右ペイン下部に固定し、一覧・メモ・必要時の編集内容を独立してスクロールします。デスクトップの初期サイズは1200×780、最小サイズは1000×680です。

UIは「Black Ops Secure Terminal」をテーマとし、色・タイポグラフィ・CSSアニメーションの定義は `apps/web/src/styles.css` に集約します。選択ラインは一覧内の位置に追従し、詳細は選択した項目の上下方向に合わせて240msで表示します。メニュー・ダイアログも短い移動と拡大で開き、保存・コピーは成功後だけチェックと光の反応を表示します。

詳細の切り替えでは、旧編集画面や画面のスナップショットを保持せず、新しい画面だけを動かします。ロック時の非表示をアニメーション待ちで遅らせません。OSの「動きを減らす」設定ではCSSの動きを抑え、詳細のアニメーションを省略します。表示途中で設定を変更した場合も詳細の動きを停止します。

## 手動更新とアプリ情報

`AppInfo.tsx` が「ヘルプ」→「アプリ情報 / 更新」から利用できる更新画面を提供します。`preload.ts` の専用 API から `update-service.ts` へ要求し、`ManualUpdater` が `electron-updater` の状態と操作を管理します。更新要求の IPC はメインウィンドウのメインフレームからの呼び出しだけを受け付けます。

Windows の setup 版向けに、確認・ダウンロード・適用を個別の操作に分けます。起動時の確認、ダウンロードの自動開始、通常終了時の自動適用はありません。未保存入力は更新前に確認し、保存処理中は適用ボタンを無効化します。適用時に保管庫をロックし、終了時に DB を閉じます。更新処理に DB スキーマ変更はありません。

更新状態はメモリに保持し、IPC イベントで UI に通知します。HTML形式の変更内容は、画面に挿入しない `template` 内で解析し、段落・箇条書きを残したテキストへ変換して表示します。スクリプト・画像・埋め込みなどを除外し、Reactの文字表示でエスケープします。通信失敗でも保管庫を利用できます。portable 版と開発モードは配布ページへ案内します。

画像の原本は `build/icon.png`、Windows 用は `build/icon.ico`、アプリ情報・favicon 用は `apps/web/public/icon.png` です。
詳細は [手動更新とアイコン](手動更新とアイコン.md) と [更新フロー](ワークフロー/04-手動更新.md) を参照してください。
